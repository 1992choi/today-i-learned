## OSI 7계층과 TCP/IP 4계층
- OSI 7계층과 TCP/IP 4계층
  - <img width="837" height="679" alt="image" src="https://github.com/user-attachments/assets/ba9ad29a-efee-4a92-8a4c-7bff30c95d19" />
- OSI 7계층이란?
  - 네트워크 통신이 일어나는 과정을 7단계로 나눈 국제 표준화 기구(ISO)에서 정의한 네트워크 표준 모델이다.
  - 이 모델은 프로토콜을 기능별로 나눈 것이다.
- OSI 7계층 - 계층별 특징
  - 물리 계층(Physical)
    - 전기적, 기계적, 기능적인 특성을 이용하여 통신 케이블로 데이터를 전송한다.
    - 사용되는 통신 단위는 비트(bit)이며, 0또는 1만 나타낼 수 있다.
    - 단지 데이터를 전달만 할 뿐 전송하려는, 또는 받으려는 데이터가 무엇인지는 전혀 신경쓰지 않는다.
    - 대표적인 장치로 통신 케이블, 리피터, 허브 등이 있다.
  - 데이터 링크 계층(Data Link)
    - 물리 계층을 통해 송수신되는 정보의 오류와 흐름을 관리하여 안전한 정보의 수행을 도와주는 역할을 한다.
    - 맥 주소(MAC Address)를 가지고 통신한다.
    - 전송되는 단위를 프레임(frame)이라고 하며, 대표적인 장비로는 브리지, 스위치 등이 있다.
  - 네트워크 계층(Network)
    - 경로를 선택하고 주소를 정하고 경로에 따라 패킷을 전달해주는 역할을 한다.
    - 데이터를 목적지까지 효율적인 경로로 전달하는 기능(라우팅)을 한다.
    - 대표적인 장비로 라우터, (라우팅 기능이 포함된)스위치가 있으며, IP 주소를 사용한다.
    - 데이터를 연결하는 다른 네트워크를 통해 전달함으로써 인터넷이 가능하게 만드는 계층이다.
  - 전송 계층(Transport)
    - 통신을 활성화하기 위한 계층이다. 보통 TCP 프로토콜을 사용하며, 포트를 열어서 응용 프로그램을 전송한다.
    - 양 끝단의 사용자들이 신뢰성 있는 데이터를 주고 받을 수 있게 해 주어, 상위 계층들이 데이터 전달의 유효성이나 효율성을 생각하지 않도록 한다.
  - 세션 계층(Session)
    - 데이터가 통신하기 위한 논리적인 연결을 한다.
    - 세션 설정, 유지, 종료, 전송 중단시 복구 등의 기능이 있다.
    - 양 끝단의 응용 프로세스가 통신을 관리하기 위한 방법을 제공한다.
    - TCP/IP 세션을 만들고 없애는 책임을 진다.
  - 표현 계층(Presentation)
    - 데이터 표현이 상이한 응용 프로세스의 독립성을 제공하고, 암호화한다.
    - 코드 간의 번역을 담당하여 사용자 시스템에서 데이터의 형식상 차이를 다루는 응용 계층의 부담을 덜어준다.
    - 해당 데이터가 텍스트인지, 그림인지, GIF인지, JPG인지의 구분 등의 역할을 한다.
  - 응용 계층(Application)
    - 최종 목적지로서 HTTP, FTP, SMTP, Telnet 등과 같은 프로토콜이 있다.
    - 응용 프로세스와 직접 관계하여 일반적인 응용 서비스를 수행한다.
- TCP/IP 4계층이란?
  - 네트워크 전송 시 데이터 표준을 정리한 것이 OSI 7계층이었다면, 이 이론을 실제로 사용하는 인터넷 표준이 TCP/IP 4계층이다.
- TCP/IP 4계층 - 계층별 특징
  - 네트워크 인터페이스 계층(Network Access/Network Interface)
    - OSI 계층의 1,2 계층에 해당된다.
    - TCP/IP 패킷을 네트워크 매체로 전달하는 것과 네트워크 매체에서 TCP/IP 패킷을 받아들이는 과정을 담당한다.
    - 에러 검출 기능과 패킷의 프레임화 기능을 수행한다.
    - 트레일러(Trailer)의 CRC를 통해 오류를 검출(Error Control)한다.
  - 인터넷 계층(Internet)
    - OSI 계층에서 3계층에 해당된다.
    - 어드레싱(addressing), 패키징(packaging), 라우팅(routing) 기능을 제공한다.
    - 논리적 주소인 IP를 이용한 노드간 전송과 라우팅 기능을 처리하게 된다.
    - 네트워크상 최종 목적지까지 정확하게 연결되도록 연결성을 제공한다.
    - 핵심 프로토콜은 IP, ARP, ICMP, IGMP 등이 있다.
  - 전송 계층(Transport)
    - OSI 계층에서 4계층에 해당된다.
    - 자료의 송수신을 담당한다.
    - 어플리케이션 계층의 세션과 데이터그램 통신서비스를 제공한다.
    - TCP/UDP가 핵심 프로토콜이다. TCP/UDP에 대한 구분을 하고 데이터에 대한 제어 정보가 여기에 포함된다.
  - 응용 계층(Application)
    - 다른 계층의 서비스에 접근할 수 있게 하는 어플리케이션을 제공한다.
    - 어플리케이션들이 데이터를 교환하기 위해 사용하는 프로토콜을 정의한다.
    - TCP/IP 네트워크를 사용하거나 관리하는 것을 도와주는 프로토콜이다.

## TCP vs UDP
- TCP(Transmission Control Protocol)
  - TCP는 신뢰성 있는 데이터 전송을 지원하는 연결 지향형 프로토콜이다.
  - 일반적으로 TCP와 IP가 함께 사용되는데, IP가 데이터의 전송을 처리한다면 TCP는 패킷을 추적하고 관리하는 역할을 한다.
  - 연결 지향형인 TCP는 3-way handshaking이라는 과정을 통해 연결 후 통신을 시작하는데, 흐름 제어와 혼잡 제어를 지원하며 데이터의 순서를 보장한다.
  - UDP에 비하여 전송속도가 느리다.
  - 신뢰성이 높다.
- UDP(User Datagram Protocol)
  - UDP는 비연결형 프로토콜이다.
  - 인터넷상에서 서로 정보를 주고받을 때, 신호 절차를 거치지 않고 보내는 쪽에서 일방적으로 데이터를 전달하는 통신 프로토콜이다.
  - TCP와는 다르게 연결 설정이 없으며, 혼잡 제어를 하지 않기 때문에 TCP보다 전송 속도가 빠르다.
  - 데이터 전송에 대한 보장을 하지 않기 때문에 패킷 손실이 발생할 수 있다.
  - 패킷 오버헤드가 적어 네트워크 부하가 감소한다.
  - 신뢰성이 낮다.

## 3-Way handshake & 4-Way hadnshake
- 3-Way Handshake란?
  - TCP/IP 프로토콜을 이용해서 통신을 하는 응용프로그램이 데이터를 전송하기 전에 먼저 정확한 전송을 보장하기 위해 상대방 컴퓨터와 사전에 세션을 수립하는 과정을 뜻한다.
- 3-Way Handshake의 동작 순서
  - <img width="965" height="607" alt="image" src="https://github.com/user-attachments/assets/d97c52dd-7bd7-484e-a3b8-f8de155cd69a" />
  - Step1. SYN
    - Client가 Server에게 접속을 요청하는 SYN플래그를 보낸다.
  - Step2. SYN + ACK
    - Server는 Listen상태에서 SYN이 들어온 것을 확인하고 SYN_RECV상태로 바뀌어 SYN + ACK플래그를 Client에게 전송한다.
    - 그 후 Server는 다시 ACK 플래그를 받기 위해 대기상태로 변경된다.
  - Step3. ACK
    - SYN + ACK 상태를 확인한 Client는 서버에게 ACK를 보내고 연결 성립(Established)이 된다.
- 4-Way Handshake란?
  - 3-Way handshake가 연결확립을 위해 진행했다면 4way handshake는 세션을 종료하기 위해 수행되는 절차를 뜻한다.
- 4-Way Handshake의 동작 순서
  - <img width="952" height="800" alt="image" src="https://github.com/user-attachments/assets/c2484c3f-ce09-4eb4-b3ec-cb31000ef53e" />
  - Step1. FIN
    - Client가 연결을 종료하겠다는 FIN플래그를 전송한다.
    - 보낸 후에 FIN-WAIT-1 상태로 변한다.
  - Step2. ACK
    - FIN 플래그를 받은 Server는 확인메세지인 ACK를 Client에게 보내준다.
    - 그 후 CLOSE-WAIT상태로 변한다.
    - Client도 마찬가지로 Server에서 종료될 준비가 됐다는 FIN을 받기위해 FIN-WAIT-2 상태가 된다.
  - Step3. FIN
    - Close준비가 다 된 후 Server는 Client에게 FIN 플래그를 전송한다.
  - Step4. ACK
    - Client는 해지 준비가 되었다는 정상응답인 ACK를 Server에게 보내준다. 이 때, Client는 TIME-WAIT 상태로 변경된다.
    - 여기서 TIME-WAIT 상태는 의도치않은 에러로 인해 연결이 데드락으로 빠지는 것을 방지하기 위해 변경 되는 것인데, 만약 에러로 인해 종료가 지연되다가 타임이 초과되면 CLOSED 상태로 변경된다.

## HTTP와 HTTPS
- HTTP(HyperText Transfer Protocol)란?
  - 웹에서 클라이언트와 서버가 데이터를 주고받기 위해 사용하는 애플리케이션 계층 프로토콜이다.
  - 기본적으로 포트 80을 사용하며, 데이터를 평문(암호화되지 않은 텍스트)으로 전송한다.
  - Stateless(무상태) 프로토콜로, 각 요청은 독립적이며 이전 요청의 상태를 기억하지 않는다. (상태 유지가 필요하면 쿠키, 세션, 토큰 등을 별도로 사용한다.)
  - HTTP/1.1은 커넥션당 순차적으로 요청을 처리해 HOL(Head-of-Line) Blocking 문제가 있고, HTTP/2는 하나의 TCP 커넥션에서 여러 요청을 멀티플렉싱해 이를 해결한다. 다만 HTTP/2도 TCP 계층의 패킷 손실에는 HOL Blocking이 남아있는데, HTTP/3는 TCP 대신 UDP 기반의 QUIC 프로토콜을 사용해 이 문제까지 해결한다.
- HTTPS(HTTP Secure)란?
  - HTTP 통신에 SSL/TLS(Secure Sockets Layer / Transport Layer Security) 계층을 추가하여 데이터를 암호화해 전송하는 프로토콜이다.
  - 기본적으로 포트 443을 사용한다.
  - 인증기관(CA, Certificate Authority)이 발급한 인증서를 통해 서버(또는 클라이언트)의 신원을 검증하고, 이 인증서를 이용해 대칭키를 안전하게 교환한 뒤, 이후 통신은 대칭키로 암호화한다. 비대칭키(공개키/개인키) 암호화는 안전하지만 연산 비용이 크기 때문에, 초기 연결 시에만 비대칭키로 대칭키(세션키)를 교환하고 실제 데이터 통신은 연산이 빠른 대칭키로 처리한다.
  - 브라우저와 OS에는 신뢰할 수 있는 루트 CA 목록이 미리 내장되어 있고, 서버 인증서는 루트 CA(또는 그 하위 CA)의 개인키로 서명되어 있다. 브라우저는 이 서명을 CA의 공개키로 검증해 인증서가 위변조되지 않았음을 확인한다.
- HTTP와 HTTPS의 차이
  - 보안: HTTP는 평문 전송이라 중간자 공격(Man-in-the-Middle Attack)에 취약하지만, HTTPS는 암호화로 기밀성과 무결성을 보장한다. 다만 HTTPS도 전송 구간만 보호할 뿐, XSS나 SQL Injection 같은 애플리케이션 레벨의 취약점이나 단말 자체의 악성코드 감염까지 막아주지는 못한다.
  - 포트: HTTP는 80번, HTTPS는 443번을 기본 포트로 사용한다.
  - 인증서: HTTPS는 CA가 발급한 SSL/TLS 인증서가 필요하지만, HTTP는 필요하지 않다.
  - 성능: HTTPS는 TLS Handshake 과정이 추가되어 초기 연결 시 약간의 지연(Latency)이 발생하지만, TLS 1.3이나 세션 재사용(Session Resumption) 등으로 많이 개선되었다.
- TLS Handshake 과정 (간단히)
  - 1. 클라이언트가 지원하는 암호화 방식 목록과 함께 ClientHello를 전송한다.
  - 2. 서버는 인증서와 선택된 암호화 방식을 담은 ServerHello를 응답한다.
  - 3. 클라이언트는 인증서를 CA 공개키로 검증하고, 대칭키(세션키)를 생성하기 위한 정보를 서버의 공개키로 암호화해 전달한다.
  - 4. 양측이 세션키를 공유하게 되면, 이후 모든 통신은 이 대칭키로 암호화하여 주고받는다.

## HTTP 상태코드
- HTTP 상태 코드는 서버가 클라이언트의 요청을 처리한 결과를 나타내는 세 자리 숫자이며, 첫 자리 숫자에 따라 5가지 클래스로 구분된다.
- 1xx (정보성, Informational)
  - 요청을 받았고 처리 중임을 나타낸다. (예: 100 Continue)
- 2xx (성공, Success)
  - 200 OK: 요청이 성공적으로 처리되었다.
  - 201 Created: 요청이 성공했고, 새로운 리소스가 생성되었다. (주로 POST)
  - 204 No Content: 요청은 성공했지만 응답 본문에 반환할 데이터가 없다. (주로 DELETE)
  - GET, PUT, DELETE는 여러 번 호출해도 결과가 동일한 멱등(Idempotent) 메서드이고, POST는 호출할 때마다 새로운 리소스를 생성할 수 있어 멱등하지 않은데, 이런 메서드의 의미가 201/204 같은 상태 코드 설계와도 연결된다.
- 3xx (리다이렉션, Redirection)
  - 301 Moved Permanently: 요청한 리소스가 영구적으로 다른 URI로 이동했다. 도메인 이전처럼 URL이 영구히 바뀐 경우 사용하며, 이후 요청은 새로운 URI로 보내야 하고 검색엔진도 URL을 갱신한다.
  - 302 Found: 리소스가 일시적으로 다른 URI에 있다. 점검 페이지로의 리다이렉션처럼 일시적인 변경에 사용하며, 다음 요청에도 원래 URI를 사용해야 한다.
  - 304 Not Modified: 클라이언트가 If-None-Match(ETag) 또는 If-Modified-Since(Last-Modified) 헤더를 담아 조건부 요청을 보냈을 때, 서버가 리소스가 바뀌지 않았음을 확인하면 본문 없이 304만 응답해 캐시된 데이터를 그대로 쓰게 한다.
- 4xx (클라이언트 오류, Client Error)
  - 400 Bad Request: 요청 자체의 문법이나 파라미터가 잘못되었다.
  - 401 Unauthorized: "누구인지 확인이 안 됨(인증 실패)"을 의미하는, 인증되지 않은 사용자의 요청이다.
  - 403 Forbidden: "누구인지는 확인됐지만 권한이 없음(인가 실패)"을 의미한다. 즉 인증은 되었지만 해당 리소스에 접근할 권한이 없는 경우다.
  - 404 Not Found: 요청한 리소스가 서버에 존재하지 않는다.
  - 429 Too Many Requests: 정해진 시간 내에 너무 많은 요청을 보내 Rate Limit에 걸렸다. 서버가 함께 내려주는 Retry-After 헤더를 참고해 일정 시간 후 재시도하거나, Exponential Backoff로 재시도 간격을 점차 늘려가며 재시도하는 것이 일반적이다.
- 5xx (서버 오류, Server Error)
  - 500 Internal Server Error: 서버 내부에서 예상치 못한 오류가 발생했다.
  - 502 Bad Gateway: 게이트웨이나 프록시 서버가 백엔드 서버로부터 잘못된 응답을 받았다.
  - 503 Service Unavailable: 서버가 일시적으로 요청을 처리할 수 없는 상태이다. (과부하, 점검 등)
<br><br><br>

## DNS
- DNS(Domain Name System)란?
  - 사람이 기억하기 쉬운 도메인 이름(예: google.com)을 컴퓨터가 통신에 사용하는 IP 주소로 변환해주는 분산 이름 해석 시스템이다.
  - 전 세계에 계층적, 분산적으로 구성되어 있어 특정 서버 하나가 다운되어도 전체 시스템이 마비되지 않는다.
- DNS 조회 과정
  - 1. 브라우저/OS의 로컬 캐시를 먼저 확인한다. 있으면 바로 사용하고 없으면 다음 단계로 진행한다.
  - 2. Local DNS Resolver(주로 ISP 또는 설정된 DNS 서버, 예: 8.8.8.8)에 질의한다.
  - 3. Local Resolver에도 캐시가 없다면, Root DNS 서버에 질의해 최상위 도메인(.com, .net 등)을 관리하는 TLD(Top Level Domain) 서버의 주소를 받는다.
  - 4. TLD 서버에 질의해 해당 도메인을 관리하는 Authoritative(권한 있는) DNS 서버의 주소를 받는다.
  - 5. Authoritative 서버에 질의해 최종적으로 도메인에 대응하는 IP 주소를 받아온다.
  - 6. 이 과정을 재귀적 질의(Recursive Query)라고 하며, 조회된 결과는 브라우저, OS, Local Resolver 등 각 단계에서 TTL(Time To Live) 동안 캐싱되어 매번 Root부터 질의하지 않고도 빠르게 응답할 수 있다. TTL이 짧으면 서버 IP 변경(장애 조치, 배포 전환 등)이 빠르게 전파되지만 질의가 잦아져 부하가 늘고, TTL이 길면 캐싱 효율은 좋지만 변경 전파가 느려지는 트레이드오프가 있다.
  - 일반적인 질의/응답은 크기가 작고 빠른 응답이 중요하기 때문에 연결 설정 과정이 없는 UDP(53번 포트)를 사용하지만, 응답 크기가 512바이트를 초과하거나 Zone Transfer처럼 신뢰성이 중요한 경우에는 TCP를 사용하기도 한다.
- 주요 DNS 레코드 타입
  - A: 도메인을 IPv4 주소로 매핑한다.
  - AAAA: 도메인을 IPv6 주소로 매핑한다.
  - CNAME: 도메인을 다른 도메인(별칭)으로 매핑한다. (예: www.example.com → example.com)
  - MX: 해당 도메인의 메일 서버 주소를 지정한다.
  - NS: 해당 도메인을 관리하는 네임서버를 지정한다.
  - TXT: 도메인 소유권 검증, SPF 등 임의의 텍스트 정보를 저장한다.
- 보안과 활용
  - 공격자가 위조된 DNS 응답을 캐시에 주입해 사용자를 악성 사이트로 유도하는 DNS Spoofing(캐시 포이즈닝) 공격이 있는데, DNSSEC(DNS 서명 검증)을 통해 응답의 무결성과 출처를 검증함으로써 방어할 수 있다.
  - CDN은 GeoDNS 방식으로, 동일한 도메인에 대해 요청자의 위치(IP 기반)에 따라 지리적으로 가장 가까운 캐시 서버의 IP를 다르게 응답해줌으로써 트래픽을 분산하고 지연을 줄인다.

## 로드밸런서
- 로드밸런서(Load Balancer)란?
  - 여러 대의 서버로 들어오는 트래픽(요청)을 분산시켜, 특정 서버에 부하가 집중되지 않도록 하는 장치 또는 소프트웨어이다.
  - 서버의 가용성(Availability), 확장성(Scalability), 무중단 배포 등을 가능하게 해준다.
  - 로드밸런서 자체가 SPOF(단일 장애점)가 되지 않으려면 이중화(Active-Standby 또는 Active-Active)하고, VRRP/Keepalived 같은 방식으로 가상 IP를 공유해 하나가 죽어도 다른 하나가 즉시 트래픽을 이어받도록 구성해야 한다.
  - 헬스 체크(Health Check)를 통해 각 서버의 상태(응답 여부, 응답 시간 등)를 주기적으로 점검하고, 장애가 발생한 서버는 분산 대상에서 즉시 제외시켜 사용자가 죽은 서버로 요청을 보내는 것을 방지한다.
- 부하 분산 알고리즘
  - 라운드 로빈(Round Robin): 서버 목록에 순서대로 요청을 균등하게 분배한다. 서버 스펙이 동일할 때 적합하다.
  - 가중 라운드 로빈(Weighted Round Robin): 서버 성능에 따라 가중치를 부여해, 성능이 좋은 서버에 더 많은 요청을 분배한다.
  - 최소 연결(Least Connections): 현재 연결(처리 중인 요청)이 가장 적은 서버로 요청을 보낸다. 요청 처리 시간 편차가 클 때 유리하다.
  - IP 해시(IP Hash): 클라이언트 IP를 해싱해 항상 같은 서버로 요청을 보낸다. 세션 정보를 특정 서버 메모리에만 저장하는 구조처럼 세션 유지(Sticky Session)가 필요할 때 사용하는데, 특정 서버에 트래픽이 몰리거나 그 서버 장애 시 세션이 유실될 수 있어 Redis 같은 외부 세션 저장소를 쓰는 편이 근본적인 해결책이다.
- L4 로드밸런서
  - OSI 4계층(전송 계층)의 정보, 즉 IP와 포트(TCP/UDP)만을 기준으로 트래픽을 분산한다.
  - 패킷의 내용을 들여다보지 않기 때문에 처리 속도가 빠르지만, URL이나 HTTP 헤더 기반의 세밀한 라우팅은 불가능하다. TCP/UDP 트래픽(DB, 게임 서버 등)이나 단순한 IP/포트 기반 분산이 목적일 때 적합하다.
- L7 로드밸런서
  - OSI 7계층(애플리케이션 계층)의 정보, 즉 HTTP 헤더, URL 경로, 쿠키 등을 기준으로 트래픽을 분산한다.
  - "/api"는 API 서버로, "/static"은 정적 파일 서버로 보내는 등 세밀한 라우팅이 가능하지만, 패킷 내부를 분석해야 하므로 L4보다 처리 비용이 크다.
  - HTTPS 암/복호화를 로드밸런서 단에서 처리하고 이후 내부 서버들과는 암호화되지 않은 HTTP로 통신하는 SSL Termination을 지원해, 각 서버가 개별적으로 TLS를 처리할 필요 없이 서버 부하를 줄이고 인증서 관리를 중앙화할 수 있다.

## 웹 캐시
- 웹 캐시(Web Cache)란?
  - 자주 요청되는 리소스(HTML, 이미지, API 응답 등)의 사본을 저장해두고, 동일한 요청이 다시 왔을 때 원본 서버까지 가지 않고 빠르게 응답해주는 기법이다.
  - 응답 속도 향상, 원본 서버(Origin Server)의 부하 감소, 네트워크 트래픽 절감 효과가 있다.
  - 인기 있는 캐시 항목이 동시에 만료되면 다수의 요청이 한꺼번에 원본 서버로 몰리는 캐시 스탬피드(Cache Stampede) 현상이 발생할 수 있는데, 만료 시간을 무작위로 분산시키거나(jitter) 락을 걸어 하나의 요청만 갱신하도록 하는 방식으로 완화한다.
- 캐시의 종류
  - 브라우저 캐시(Browser Cache): 사용자의 브라우저에 리소스를 저장해두는 캐시로, 같은 사용자가 같은 사이트를 재방문할 때 유용하다.
  - 프록시 캐시(Proxy Cache): 클라이언트와 서버 사이의 중간 서버(Forward/Reverse Proxy)에 저장되는 캐시로, 여러 사용자가 공유해서 사용할 수 있다.
  - CDN(Content Delivery Network): 전 세계 여러 지역에 분산된 캐시 서버(Edge Server)에 정적 리소스를 저장해, 사용자와 지리적으로 가까운 서버에서 응답하도록 하여 지연 시간을 최소화한다. 콘텐츠가 갱신되면 CDN 제공자의 API로 특정 경로의 캐시를 강제로 삭제(Purge/Invalidate)하거나, 파일명에 버전/해시를 포함시켜(Cache Busting) URL 자체를 바꿔 새 리소스로 인식시키는 방식으로 무효화한다.
- 캐시 제어 헤더
  - Cache-Control
    - no-cache: 캐시를 저장은 하되, 사용하기 전에 매번 서버에 유효성을 재검증해야 한다. 이름과 달리 캐시를 완전히 막는 것은 아니다.
    - no-store: 캐시를 아예 저장하지 않는다. (민감한 정보에 사용)
    - max-age: 캐시가 유효한 시간(초)을 지정한다. 이 시간 동안은 서버에 재검증 없이 캐시를 그대로 사용한다.
    - public/private: public은 프록시/CDN을 포함해 누구나 캐싱 가능, private은 브라우저 등 특정 사용자 전용 캐시만 허용한다.
  - ETag: 리소스의 버전을 식별하는 고유한 해시 값이다. 클라이언트가 If-None-Match 헤더로 이전 ETag를 보내면, 서버는 리소스가 바뀌지 않았을 경우 304 Not Modified로 응답해 본문 전송을 생략한다.
  - Last-Modified: 리소스가 마지막으로 수정된 시각이다. 클라이언트가 If-Modified-Since 헤더로 이 값을 보내 조건부 요청을 할 수 있는데, ETag보다 정밀도가 낮아(초 단위) 두 헤더가 모두 있으면 일반적으로 ETag가 우선하지만, Last-Modified는 구현이 단순하고 서버 리소스 소모가 적어 함께 쓰이기도 한다.
  - 이미지, JS, CSS 같은 정적 자원은 파일명에 해시를 넣어 max-age를 매우 길게(사실상 불변으로) 설정하고, API 응답 같은 동적 자원은 변경 빈도에 맞춰 짧은 max-age를 주거나 ETag 기반의 재검증(no-cache)을 사용하는 것이 일반적인 전략이다.

## 소켓
- 소켓(Socket)이란?
  - 네트워크 상에서 두 프로그램(프로세스) 간에 데이터를 주고받기 위한 통신의 종착점(Endpoint)이다.
  - IP 주소와 포트 번호의 조합으로 식별되며, 애플리케이션이 TCP/IP와 같은 하위 프로토콜 스택을 직접 다루지 않고도 네트워크 통신을 할 수 있게 해주는 OS 레벨의 인터페이스이다. IP는 네트워크 상의 특정 호스트를 식별할 뿐이고, 한 호스트에서는 여러 프로세스가 동시에 통신하므로 포트로 어떤 프로세스에게 데이터를 전달할지 구분한다.
  - TCP 소켓(Stream Socket)은 연결 지향적이며 순서와 신뢰성을 보장하고, UDP 소켓(Datagram Socket)은 비연결형으로 순서/신뢰성을 보장하지 않는 대신 빠르다.
  - 서버가 다루는 동시 연결 수를 늘리려면, 연결마다 스레드를 하나씩 쓰는 전통적인 방식은 Context Switching 비용이 커지므로 I/O 멀티플렉싱(select/epoll/kqueue)이나 비동기 이벤트 기반(Netty, Node.js 등) 모델로 적은 스레드로 많은 연결을 효율적으로 처리한다. 이런 대규모 동시 연결 처리 문제를 C10K 문제라고 부른다.
- HTTP 통신과 소켓
  - HTTP는 요청-응답(Request-Response) 기반의 단방향성 통신 모델이다. 클라이언트가 요청을 보내야만 서버가 응답을 줄 수 있고, 서버가 클라이언트에게 먼저 데이터를 보낼 수 없다.
  - 매 요청마다(HTTP/1.0 기준) 또는 커넥션을 재사용하더라도(Keep-Alive) 기본적으로 요청-응답의 흐름을 따르기 때문에, 실시간으로 서버가 클라이언트에게 데이터를 push하는 데는 한계가 있다. 이를 보완하기 위해 클라이언트가 주기적으로 새 데이터 유무를 확인하는 Polling, 서버가 새로운 데이터가 생길 때까지 응답을 지연시켰다가 응답하는 Long Polling 같은 기법이 쓰이지만 여전히 불필요한 요청이 많다.
- 웹소켓(WebSocket)과 소켓
  - 웹소켓은 클라이언트가 `Upgrade: websocket` 헤더를 포함한 HTTP 요청을 보내고 서버가 이를 수락하는 101 Switching Protocols 응답을 반환하면, 이후 해당 TCP 커넥션이 지속적인(persistent) 양방향 통신 채널로 업그레이드되는 프로토콜이다.
  - 한 번 연결이 수립되면 클라이언트와 서버 모두 언제든지 먼저 데이터를 보낼 수 있어, 실시간 채팅, 알림, 주식 시세와 같이 서버가 능동적으로 데이터를 전달해야 하는 서비스에 적합하다. HTTP처럼 매 요청마다 헤더를 주고받지 않아 오버헤드가 적고, Polling/Long Polling 대비 가장 실시간성이 높다.
  - TCP 소켓 위에서 동작하며, 연결을 유지하는 동안 지속적인 데이터 교환이 가능하다.

## 네트워크 성능 지표와 캡슐화
- 네트워크 성능을 나타내는 주요 지표
  - 대역폭(Bandwidth): 단위 시간당 전송할 수 있는 최대 데이터의 양을 뜻하며, 흔히 도로의 차선 수에 비유된다. (예: 100Mbps)
  - 처리량(Throughput): 실제로 단위 시간당 성공적으로 전송된 데이터의 양을 뜻한다. 대역폭은 이론적인 최대치이고, 처리량은 네트워크 혼잡, 오류 등의 영향을 받은 실제 수치라는 점에서 다르다.
  - 지연 시간(Latency): 데이터가 송신 측에서 수신 측까지 도달하는 데 걸리는 시간을 뜻하며, 전파 지연(물리적 거리), 전송 지연(데이터 크기/대역폭), 처리 지연(라우터 등 중간 장비의 처리 시간), 큐잉 지연(대기열에서 기다리는 시간) 등으로 구성된다.
  - RTT(Round Trip Time): 데이터를 보내고 그에 대한 응답을 받기까지 걸리는 왕복 시간을 뜻하며, TCP 연결 수립이나 응답 속도를 가늠하는 지표로 많이 사용된다.
  - 패킷 손실률(Packet Loss): 전송한 패킷 중 목적지에 도달하지 못하고 유실된 패킷의 비율을 뜻하며, 손실률이 높아지면 TCP는 재전송을 수행해 처리량이 저하될 수 있다.
- 캡슐화(Encapsulation)와 역캡슐화(Decapsulation)
  - 캡슐화란, 상위 계층에서 전달된 데이터에 각 계층을 지날 때마다 해당 계층에 필요한 제어 정보(헤더)를 덧붙이는 과정을 말한다.
  - 예를 들어 응용 계층의 데이터는 전송 계층을 지나며 TCP/UDP 헤더가 붙어 세그먼트(Segment)가 되고, 네트워크 계층을 지나며 IP 헤더가 붙어 패킷(Packet)이 되며, 데이터 링크 계층을 지나며 이더넷 헤더/트레일러가 붙어 프레임(Frame)이 된다.
  - 수신 측에서는 반대로 각 계층을 올라가면서 해당 계층의 헤더를 하나씩 제거(역캡슐화)해, 최종적으로 원본 데이터만 응용 계층에 전달한다.
  - 각 계층은 자신의 헤더만 해석하면 되고 하위/상위 계층의 세부 사항을 알 필요가 없기 때문에, 계층 간 독립성이 보장되고 프로토콜 설계/유지보수가 용이해진다.

## 데이터 링크 계층 (이더넷, 허브/CSMA-CD, 스위치와 VLAN)
- 데이터 링크 계층의 역할
  - 물리 계층을 통해 전달되는 비트(bit) 스트림을 프레임(Frame) 단위로 묶고, 같은 네트워크(링크) 내에서 MAC 주소를 이용해 오류 검출과 흐름 제어를 수행하는 계층이다.
- 이더넷(Ethernet)
  - 유선 LAN 환경에서 가장 널리 사용되는 데이터 링크 계층 프로토콜로, 각 장치를 고유하게 식별하는 MAC(Media Access Control) 주소를 기반으로 통신한다.
  - 이더넷 프레임은 목적지/출발지 MAC 주소, 타입, 실제 데이터(Payload), 오류 검출을 위한 FCS(Frame Check Sequence)로 구성된다.
- 허브(Hub)와 CSMA/CD
  - 허브는 물리 계층 장비로, 입력으로 들어온 신호를 연결된 모든 포트에 그대로 전달(Broadcast)한다. 같은 허브에 연결된 모든 장치는 하나의 충돌 도메인(Collision Domain)을 공유한다.
  - 여러 장치가 동시에 신호를 보내면 충돌(Collision)이 발생할 수 있는데, 이를 감지하고 처리하기 위한 방식이 CSMA/CD(Carrier Sense Multiple Access with Collision Detection)이다.
    - 전송 전에 회선이 비어있는지 확인(Carrier Sense)하고, 비어있으면 데이터를 전송한다.
    - 전송 도중 충돌이 감지되면 즉시 전송을 중단하고, 임의의 시간(Backoff)을 기다린 후 재전송을 시도한다.
  - 현대의 스위치 기반 네트워크(Full-Duplex)에서는 충돌이 발생하지 않기 때문에 CSMA/CD는 사실상 사용되지 않지만, 이더넷 동작 원리를 이해하는 데 여전히 중요한 개념이다.
- 스위치(Switch)
  - 데이터 링크 계층 장비로, 각 포트에 연결된 장치의 MAC 주소를 MAC 주소 테이블에 학습해두고, 프레임이 들어오면 목적지 MAC 주소에 해당하는 포트로만 전달한다(허브와 달리 불필요한 Broadcast를 줄인다).
  - 포트별로 별도의 충돌 도메인을 형성하기 때문에, 허브에 비해 충돌 가능성이 크게 줄어들고 대역폭을 효율적으로 사용할 수 있다.
- VLAN(Virtual LAN)
  - 물리적으로는 하나의 스위치에 연결되어 있어도, 논리적으로 서로 다른 네트워크(브로드캐스트 도메인)로 분리하는 기술이다.
  - 부서별/용도별로 네트워크를 분리해 불필요한 브로드캐스트 트래픽을 줄이고 보안성을 높일 수 있으며, 서로 다른 VLAN 간 통신을 위해서는 라우터나 L3 스위치가 필요하다.

## IP, ARP, ICMP와 라우팅
- IP(Internet Protocol)
  - 네트워크 계층의 핵심 프로토콜로, 출발지와 목적지를 IP 주소로 식별하고 데이터를 패킷 단위로 전달하는 역할을 한다.
  - 비연결형(Connectionless)이며, 전달 여부를 보장하지 않는(Best-Effort) 프로토콜이다. 신뢰성 있는 전달은 상위 계층인 TCP가 담당한다.
- ARP(Address Resolution Protocol)
  - 같은 네트워크(LAN) 내에서, 목적지의 IP 주소는 알지만 실제로 프레임을 전달하는 데 필요한 MAC 주소를 모를 때 이를 알아내기 위한 프로토콜이다.
  - 송신 측이 "이 IP 주소를 가진 장치의 MAC 주소가 무엇이냐"고 네트워크 전체에 브로드캐스트로 질의(ARP Request)하면, 해당 IP를 가진 장치가 자신의 MAC 주소로 응답(ARP Reply)한다.
  - 조회한 IP-MAC 매핑 정보는 ARP 캐시(테이블)에 일정 시간 저장해두어, 매번 브로드캐스트하지 않고 빠르게 재사용한다.
- ICMP(Internet Control Message Protocol)
  - IP 통신 과정에서 발생하는 오류를 보고하거나, 네트워크 상태를 진단하기 위해 사용하는 프로토콜이다.
  - 대표적으로 `ping` 명령어는 ICMP Echo Request/Reply 메시지를 이용해 목적지까지의 도달 여부와 응답 시간을 확인하고, `traceroute`는 TTL(Time To Live)을 하나씩 증가시키며 ICMP Time Exceeded 메시지를 유도해 경로상의 각 라우터를 파악한다.
- IP 주소의 분류
  - IP 주소는 네트워크를 식별하는 네트워크 부분과, 그 네트워크 내의 특정 호스트를 식별하는 호스트 부분으로 구성되며, 서브넷 마스크(Subnet Mask)로 이 둘의 경계를 구분한다.
  - 공인 IP(Public IP)는 인터넷 상에서 유일하게 식별되는 주소이고, 사설 IP(Private IP, 예: 192.168.x.x)는 내부 네트워크에서만 사용되며 NAT(Network Address Translation)를 통해 공인 IP로 변환되어 외부와 통신한다.
- 라우팅(Routing)
  - 라우터가 목적지 IP 주소를 보고, 다음으로 어느 경로(다음 홉, Next Hop)로 패킷을 전달할지 결정하는 과정이다.
  - 라우터는 라우팅 테이블을 참조해 목적지 네트워크에 대한 최적의 경로를 찾으며, 이 테이블은 관리자가 수동으로 설정(Static Routing)하거나 RIP, OSPF, BGP 같은 라우팅 프로토콜을 통해 동적으로 구성(Dynamic Routing)될 수 있다.

## TCP 흐름 제어와 혼잡 제어
- 흐름 제어(Flow Control)란?
  - 송신 측과 수신 측의 처리 속도 차이로 인해, 수신 측이 미처 처리하지 못한 데이터가 쌓여 유실되는 것을 방지하기 위한 메커니즘이다.
  - TCP는 슬라이딩 윈도우(Sliding Window) 방식을 사용한다. 수신 측은 자신이 받을 수 있는 버퍼의 여유 공간을 윈도우 크기(Window Size)로 매 ACK마다 송신 측에게 알려주고, 송신 측은 그 범위 내에서만 데이터를 한꺼번에 전송한다.
  - 수신 버퍼가 가득 차면 윈도우 크기를 0으로 알려 송신을 잠시 멈추게 하고(Zero Window), 버퍼에 여유가 생기면 다시 윈도우 크기를 늘려 전송을 재개하도록 한다.
- 혼잡 제어(Congestion Control)란?
  - 흐름 제어가 수신 측의 처리 능력을 고려하는 것이라면, 혼잡 제어는 네트워크 자체(중간 경로)의 혼잡 상태를 고려해 전송 속도를 조절하는 메커니즘이다.
  - 송신 측 혼자만 빠르게 데이터를 보내면 네트워크 중간(라우터 등)에 병목이 생겨 패킷 손실과 지연이 급증할 수 있기 때문에, 네트워크 상태에 맞춰 전송량을 동적으로 조절한다.
- 혼잡 제어의 주요 알고리즘 (TCP Reno 기준)
  - 느린 시작(Slow Start): 연결 초기에는 혼잡 윈도우(Congestion Window, cwnd)를 작게 시작해, ACK를 받을 때마다 지수적으로 늘려가며 네트워크 상태를 탐색한다.
  - 혼잡 회피(Congestion Avoidance): 혼잡 윈도우가 특정 임계값(ssthresh)에 도달하면, 이후로는 지수적이 아닌 선형적으로 조금씩 늘려가며 혼잡을 조심스럽게 피한다.
  - 혼잡 발생 시 대응: 패킷 손실(타임아웃 또는 중복 ACK)이 감지되면, 네트워크가 혼잡하다고 판단해 혼잡 윈도우 크기를 큰 폭으로 줄인 뒤 다시 천천히 늘려간다. (빠른 재전송, 빠른 회복 등의 기법으로 완화)
- 최종 전송 가능한 데이터 양
  - 실제로 송신 측이 한 번에 보낼 수 있는 데이터의 양은, 수신 측이 알려준 흐름 제어 윈도우와 네트워크 상태에 따른 혼잡 윈도우 중 더 작은 값으로 결정된다.

## 웹 서버와 WAS
- 웹 서버(Web Server)란?
  - HTTP 프로토콜을 기반으로 클라이언트의 요청을 받아, 정적 컨텐츠(HTML, CSS, JS, 이미지 등)를 그대로 응답해주는 서버이다. (예: Nginx, Apache HTTP Server)
  - 별도의 동적 처리 없이 파일을 그대로 전달하는 역할에 특화되어 있어, 정적 자원 처리 속도가 빠르고 가볍다.
- WAS(Web Application Server)란?
  - 데이터베이스 조회, 비즈니스 로직 처리 등 동적인 요청을 처리하고, 그 결과를 클라이언트에게 응답할 수 있는 서버이다. (예: Tomcat, Node.js 런타임)
  - 웹 서버의 기능(정적 컨텐츠 응답)도 수행할 수 있지만, 동적 컨텐츠 처리에 특화되어 있다.
- 웹 서버와 WAS를 함께 사용하는 이유
  - 정적 컨텐츠는 웹 서버가 처리하고, 동적 컨텐츠 요청만 WAS로 전달함으로써 각 서버가 자신이 잘하는 역할에 집중하게 해 전체 처리량을 높일 수 있다.
  - 웹 서버를 여러 WAS 앞단에 두어 로드밸런싱을 수행하거나, SSL 인증서 처리(SSL Termination)를 웹 서버에서 전담시켜 WAS의 부하를 줄일 수 있다.
  - 웹 서버가 앞단에서 요청을 받기 때문에, WAS에 장애가 발생해도 정적 페이지(점검 안내 등)는 계속 응답할 수 있어 시스템 안정성이 높아진다.
  - 여러 대의 WAS를 두고 웹 서버가 트래픽을 분산시킴으로써 시스템을 수평적으로 확장(Scale-Out)하기 쉬워진다.

## 컨텐츠 협상 (Content Negotiation)
- 컨텐츠 협상(Content Negotiation)이란?
  - 동일한 URI(자원)에 대해, 클라이언트가 선호하는 표현 형식(언어, 인코딩, 미디어 타입 등)으로 서버가 다른 응답을 제공할 수 있도록 하는 HTTP의 메커니즘이다.
  - 클라이언트는 요청 헤더를 통해 자신이 선호하는 형식을 서버에게 알리고, 서버는 그 중 가능한 형식으로 응답한다.
- 주요 협상 관련 요청 헤더
  - Accept: 클라이언트가 응답으로 받고 싶은 미디어 타입을 지정한다. (예: `application/json`, `text/html`)
  - Accept-Language: 클라이언트가 선호하는 언어를 지정한다. (예: `ko-KR`, `en-US`)
  - Accept-Encoding: 클라이언트가 지원하는 압축 인코딩 방식을 지정한다. (예: `gzip`, `br`)
  - Accept-Charset: 클라이언트가 선호하는 문자 인코딩을 지정한다. (예: `utf-8`)
  - 각 헤더에는 `q`(quality) 값을 이용해 선호도의 우선순위를 함께 표현할 수 있다. (예: `Accept-Language: ko-KR,ko;q=0.9,en-US;q=0.8`)
- 서버 주도 협상 vs 클라이언트 주도 협상
  - 서버 주도 협상(Server-Driven Negotiation): 서버가 클라이언트의 요청 헤더를 분석해 가장 적합한 표현을 선택해 응답하는 방식으로, 가장 일반적으로 사용된다.
  - 클라이언트 주도 협상(Agent-Driven Negotiation): 서버가 여러 선택지를 제시하고, 클라이언트가 그 중 하나를 선택해 다시 요청하는 방식이다.
- 응답과 캐시
  - 컨텐츠 협상으로 인해 같은 URI라도 클라이언트에 따라 다른 응답이 내려갈 수 있으므로, 서버는 응답에 `Vary` 헤더(예: `Vary: Accept-Language`)를 포함시켜, 캐시 서버나 브라우저가 어떤 요청 헤더 값에 따라 캐시를 구분해서 저장해야 하는지 알려준다.
