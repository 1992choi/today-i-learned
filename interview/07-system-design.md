## 대용량 트래픽 처리와 시스템 설계
- 수직적 확장(Scale-Up)과 수평적 확장(Scale-Out)
  - 수직적 확장 : 서버 한 대의 성능(CPU, 메모리)을 높이는 방식으로, 구조 변경 없이 간단하게 적용할 수 있지만 물리적인 한계가 있고 단일 장애점(SPOF)이 된다는 단점이 있다.
  - 수평적 확장 : 서버의 대수를 늘려 트래픽을 분산 처리하는 방식으로, 이론적으로는 더 유연하게 확장할 수 있지만 여러 서버 간의 상태 공유(세션, 데이터 일관성 등)를 고려한 설계가 필요하다.
- 로드밸런싱
  - 여러 대의 서버에 트래픽을 고르게 분산시켜, 특정 서버에 부하가 쏠리는 것을 방지하고 가용성을 높인다.
- 캐싱(Caching)
  - 자주 조회되지만 자주 바뀌지 않는 데이터를 Redis 같은 캐시에 저장해두어, DB에 매번 접근하지 않고도 빠르게 응답하고 DB 부하를 줄인다.
  - CDN을 이용해 정적 리소스(이미지, JS, CSS)를 사용자와 가까운 엣지 서버에서 제공하면, 원본 서버의 부하를 크게 줄일 수 있다.
- 비동기 처리와 메시지 큐
  - 즉각적인 응답이 필요 없는 작업(알림 발송, 통계 집계 등)은 메시지 큐를 통해 비동기로 처리하여, 순간적으로 몰리는 트래픽을 큐에 버퍼링하고 소비자가 처리 가능한 속도로 안정적으로 처리할 수 있게 한다.
- 데이터베이스 확장 전략
  - 읽기 요청이 많은 경우 Replication(복제)을 통해 읽기 전용 서버를 여러 대 두어 읽기 트래픽을 분산시킬 수 있다.
  - 데이터 자체가 너무 커서 하나의 DB 서버로 감당할 수 없다면 Sharding을 통해 데이터를 여러 DB에 분산 저장한다.
- 장애 대응 설계
  - 서킷 브레이커(Circuit Breaker) 패턴을 적용해, 특정 서비스에 장애가 발생했을 때 그 장애가 연쇄적으로 전체 시스템에 전파되는 것(Cascading Failure)을 막을 수 있다.
  - 레이트 리미팅(Rate Limiting)을 통해 특정 클라이언트(또는 IP)가 과도한 요청을 보내는 것을 제한하여, 비정상적인 트래픽으로부터 시스템을 보호한다.

## 모놀리식과 MSA
- 모놀리식 아키텍처(Monolithic Architecture)란?
  - 애플리케이션의 모든 기능(주문, 결제, 회원 등)이 하나의 코드베이스, 하나의 배포 단위로 구성된 전통적인 아키텍처이다.
  - 장점 : 초기 개발/배포가 단순하고, 하나의 프로세스 내에서 메서드 호출로 기능 간 연동이 이루어지므로 트랜잭션 관리가 쉽다.
  - 단점 : 애플리케이션이 커질수록 코드베이스가 비대해져 유지보수가 어려워지고, 기능 하나를 수정해도 전체를 다시 빌드/배포해야 하며, 특정 기능만 트래픽이 몰려도 애플리케이션 전체를 함께 스케일 아웃해야 한다.
- MSA(Microservice Architecture)란?
  - 하나의 큰 애플리케이션을 비즈니스 기능 단위의 작은 서비스들로 나누고, 각 서비스가 독립적인 프로세스로 배포되어 API(REST, gRPC 등)나 메시징을 통해 서로 통신하는 아키텍처이다.
  - 장점 : 서비스마다 독립적으로 개발/배포/스케일링이 가능해 특정 서비스의 장애가 전체로 전파되는 것을 막을 수 있고(장애 격리), 팀마다 서비스를 나누어 독립적으로 개발하기 용이하다.
  - 단점 : 서비스 간 네트워크 통신이 필요해 지연과 장애 가능성이 늘어나고, 분산 트랜잭션 관리(SAGA 패턴 등), 서비스 간 데이터 정합성, 배포/모니터링 인프라의 복잡도가 크게 증가한다.
- 모놀리식 vs MSA 선택 기준
  - 초기 스타트업이나 서비스 규모가 작을 때는 빠른 개발/배포가 가능한 모놀리식으로 시작하고, 조직과 트래픽이 커져 팀별 독립 배포와 부분적 확장성이 필요해지는 시점에 MSA로 점진적으로 전환하는 것이 일반적인 접근으로 권장된다.

## 신뢰성, 확장성, 유지보수성
- 신뢰성(Reliability)
  - 하드웨어 결함, 소프트웨어 버그, 사람의 실수 등 결함(Fault)이 발생하더라도 시스템이 올바르게(사용자가 기대하는 성능으로) 계속 동작하는 것을 의미한다.
  - 결함(Fault)과 장애(Failure)는 구분된다. Fault는 시스템을 구성하는 하나의 요소가 정상 범위를 벗어난 상태를 뜻하고, Failure는 그 Fault로 인해 시스템 전체가 사용자에게 서비스를 제공하지 못하는 상태를 뜻한다. 신뢰성이 높은 시스템은 Fault가 발생해도 Failure로 이어지지 않도록 설계(Fault-Tolerant)한다.
- 확장성(Scalability)
  - 시스템의 부하(Load)가 증가했을 때 이에 대응할 수 있는 능력을 의미한다.
  - 부하는 하나의 숫자가 아니라 부하 매개변수(Load Parameter)로 기술한다. 예) 초당 요청 수, 읽기/쓰기 비율, 동시 접속자 수 등.
  - 성능은 보통 처리량(Throughput, 단위 시간당 처리 건수)과 응답 시간(Response Time)으로 측정하며, 부하가 커졌을 때 이 지표들이 어떻게 변하는지로 확장성을 평가한다.
- 유지보수성(Maintainability)
  - 운영 용이성(Operability) : 시스템을 안정적으로 운영하기 쉽게 만드는 것. 모니터링, 로깅, 배포 자동화 등이 포함된다.
  - 단순성(Simplicity) : 불필요한 복잡성(Accidental Complexity)을 제거하여 시스템을 이해하기 쉽게 만드는 것. 좋은 추상화를 통해 복잡한 시스템의 일부를 숨기는 것이 대표적인 방법이다.
  - 발전성(Evolvability) : 요구사항 변화에 맞춰 시스템을 쉽게 수정/확장할 수 있는 것. 테스트 커버리지, 느슨한 결합(Loose Coupling) 등이 영향을 준다.

## 응답 시간과 백분위(p95, p99), 꼬리 지연
- 평균(Average)이 아닌 백분위를 쓰는 이유
  - 응답 시간은 요청마다 크게 달라질 수 있고, 일부 매우 느린 요청(Outlier)이 평균을 왜곡시키기 때문에 평균 응답 시간만으로는 사용자가 실제로 체감하는 성능을 제대로 파악하기 어렵다.
  - 그래서 응답 시간을 정렬한 뒤, 특정 비율의 요청이 그 값보다 빠르게 처리되었는지를 나타내는 백분위(Percentile)를 사용한다.
- 주요 백분위 지표
  - p50(중앙값, Median) : 요청의 절반이 이 시간보다 빠르게 처리된다.
  - p95, p99, p999 : 각각 상위 5%, 1%, 0.1%에 해당하는 느린 요청의 응답 시간이다. 이 값들이 느린 요청, 즉 "꼬리(Tail)"에 해당하는 사용자 경험을 대표한다.
  - SLA/SLO는 흔히 이 백분위 값을 기준으로 정의한다. (예: "99%의 요청은 300ms 이내에 응답해야 한다")
- 꼬리 지연 증폭(Tail Latency Amplification)
  - 하나의 사용자 요청을 처리하기 위해 내부적으로 여러 백엔드 호출(병렬 호출)을 수행하는 경우, 최종 응답은 그 중 가장 느린 호출이 끝날 때까지 기다려야 한다.
  - 개별 호출이 p99 기준으로 1%의 확률로만 느려지더라도, 호출 수가 많아질수록 "적어도 하나는 느릴" 확률이 커지기 때문에, 전체 요청의 지연은 개별 호출보다 훨씬 더 자주 꼬리 지연의 영향을 받게 된다.
  - 이로 인해 상위 백분위(p99 등)를 개선하는 것은 평균을 개선하는 것보다 어렵고, 느린 하나의 다운스트림 서비스가 전체 시스템의 체감 성능을 크게 떨어뜨릴 수 있다.
- 큐잉 지연(Queueing Delay)과의 관계
  - 서버가 동시에 처리할 수 있는 요청 수를 초과하면, 느린 일부 요청(Head-of-line Blocking)이 그 뒤에 도착한 빠른 요청들까지 대기시켜 전체적인 꼬리 지연을 악화시킬 수 있다.

## 팬아웃(Fan-out)과 타임라인 설계
- 문제 상황 (예: 트위터형 타임라인)
  - 사용자가 자신이 팔로우하는 사람들의 게시물을 시간순으로 모아보는 타임라인 기능을 구현할 때, 글을 쓰는 시점(쓰기)과 타임라인을 조회하는 시점(읽기) 중 어느 쪽에서 데이터를 조합할지를 결정해야 한다.
- Fan-out on Write (쓰기 시 팬아웃, Push 방식)
  - 사용자가 글을 게시하면, 그 즉시 해당 사용자를 팔로우하는 모든 사람의 타임라인 캐시(또는 저장소)에 글을 미리 복사해 넣어둔다.
  - 조회 시에는 이미 만들어진 캐시를 그대로 읽기만 하면 되므로 읽기 성능이 매우 빠르다.
  - 하지만 팔로워가 매우 많은 사용자(유명인)가 글을 쓸 때마다 수백만 건의 쓰기가 발생해야 하므로(Fan-out 쓰기 비용), 쓰기 부하가 크고 자원 낭비가 발생할 수 있다(팔로워가 로그인하지 않아도 미리 써둬야 함).
- Fan-out on Read (읽기 시 팬아웃, Pull 방식)
  - 글을 쓸 때는 자신의 저장소에만 기록하고, 타임라인을 조회할 때 팔로우하는 모든 사용자의 최근 글을 그때 가져와서 시간순으로 병합한다.
  - 쓰기는 가볍지만, 팔로우하는 사람이 많은 사용자가 조회할 때마다 여러 사용자의 데이터를 모아 병합해야 하므로 읽기 비용이 커진다.
- 혼합(Hybrid) 방식
  - 대부분의 대규모 서비스는 두 방식을 혼합해서 사용한다. 일반 사용자는 Fan-out on Write(Push)로 처리해 빠른 읽기를 제공하고, 팔로워가 매우 많은 유명인은 Fan-out on Read(Pull)로 처리하여 쓰기 폭증을 방지한 뒤, 조회 시점에 유명인의 글만 별도로 병합해준다.
  - 즉 트래픽 패턴(팔로워 수의 분포, 쓰기/읽기 비율)에 따라 Push와 Pull 전략을 적절히 혼합하는 것이 실무에서의 접근 방식이다.

## 상위 호환성과 하위 호환성
- 왜 필요한가
  - 롤링 배포 등으로 신버전과 구버전 코드가 동시에 운영되는 동안, 서로 다른 버전이 쓴 데이터를 읽어야 하는 상황이 반드시 발생한다. 이때 데이터 형식(스키마)이 양쪽 버전 모두와 호환되어야 장애 없이 배포를 진행할 수 있다.
- 하위 호환성(Backward Compatibility)
  - 새 코드가 과거(구버전) 코드가 쓴 데이터를 읽을 수 있는 능력이다. 일반적으로 신경 쓰기 쉬운 방향으로, 새로 추가된 필드에 기본값을 두는 등의 방식으로 비교적 쉽게 지킬 수 있다.
- 상위 호환성(Forward Compatibility)
  - 과거(구버전) 코드가 새 코드가 쓴 데이터를 읽을 수 있는 능력이다. 구버전 코드는 아직 존재하지 않는 필드를 모르기 때문에, 그 필드를 무시하고도 정상 동작할 수 있어야 한다는 점에서 상대적으로 신경 쓰기 어렵다.
- 스키마 변경 시 지켜야 할 규칙
  - 필드를 추가할 때는 기존 레코드와의 호환을 위해 선택적(Optional)이거나 기본값(Default)을 갖도록 추가해야 한다.
  - 필드를 제거할 때는 하위 호환을 지키려면 선택적 필드만 제거 가능하며, 같은 필드 식별자(태그, 이름)를 다른 의미로 재사용해서는 안 된다.
  - 이러한 규칙을 지키는 것이 앞서 정리한 `롤링 배포 중 스키마 변경 (Expand-Contract)` 패턴과 `스키마 기반 부호화` 방식의 스키마 진화 규칙의 기반이 된다.

## 스키마 기반 부호화 (Protocol Buffers, Avro)와 스키마 레지스트리
- 텍스트 기반 포맷의 한계
  - JSON, XML 같은 텍스트 기반 포맷은 사람이 읽기 쉽고 범용적이지만, 필드 이름을 매번 문자열로 반복해서 포함하기 때문에 데이터 크기가 커지고, 숫자/날짜 등의 타입이 명확하지 않아 파싱 비용과 모호함이 발생한다.
  - 스키마 기반 바이너리 포맷은 데이터 구조를 미리 스키마로 정의해두고, 그 스키마를 바탕으로 데이터를 훨씬 작고 빠르게 직렬화/역직렬화한다.
- Protocol Buffers (Protobuf)
  - 각 필드에 이름이 아닌 숫자 태그(Tag)를 부여하고, 부호화된 데이터에는 필드 이름 대신 이 태그 번호와 값만 저장하기 때문에 데이터 크기가 작다.
  - 스키마 진화 규칙 : 새 필드는 반드시 선택적(Optional)으로 추가해야 하고(하위 호환), 기존 필드의 태그 번호는 절대 재사용하면 안 되며, 필수(Required) 필드는 추가하지 않는 것이 안전하다.
- Avro
  - Protobuf처럼 태그 번호를 쓰지 않고, 데이터를 쓸 때 사용한 스키마(Writer's Schema)와 읽을 때 사용하는 스키마(Reader's Schema)가 다를 수 있다는 전제로 설계되었다. 두 스키마를 비교해 필드를 이름으로 매칭하여 호환성을 해결한다.
  - 태그 번호 관리가 필요 없어 동적으로 생성되는 스키마(예: DB 테이블 구조를 그대로 매핑)에 적합하며, 하둡 생태계에서 널리 사용된다.
- 스키마 레지스트리(Schema Registry)
  - 데이터를 주고받을 때마다 전체 스키마를 함께 보내면 오히려 데이터보다 스키마가 커질 수 있으므로, 스키마 자체는 중앙 저장소(Schema Registry)에 버전별로 등록해두고, 실제 메시지에는 그 스키마를 가리키는 작은 ID(버전 번호)만 포함시킨다.
  - 메시지를 받는 쪽은 메시지에 담긴 스키마 ID로 레지스트리에서 해당 버전의 스키마를 조회해 디코딩한다. Kafka와 Avro를 함께 사용할 때 Confluent Schema Registry가 대표적인 예시이며, 새 스키마를 등록할 때 기존 스키마와의 호환성을 자동으로 검사해준다.

## 분산 시스템의 부분 장애와 타임아웃
- 전체 장애(Total Failure)와 부분 장애(Partial Failure)
  - 하나의 컴퓨터에서 동작하는 단일 프로그램은 보통 "완전히 동작"하거나 "완전히 멈춤" 둘 중 하나이고(결정적), 하드웨어가 멀쩡하면 같은 연산은 항상 같은 결과를 낸다.
  - 반면 여러 노드가 네트워크로 연결된 분산 시스템에서는 일부 노드/네트워크 경로만 문제가 생기고 나머지는 정상 동작하는 부분 장애가 흔하게 발생한다. 게다가 부분 장애는 비결정적(Nondeterministic)이라, 같은 요청이 어떤 때는 성공하고 어떤 때는 느리거나 실패한다.
- 네트워크를 신뢰할 수 없는 이유
  - 요청이 네트워크를 통해 전달되는 과정에서 요청 자체가 손실될 수도 있고, 요청은 전달되었지만 응답이 손실될 수도 있으며, 응답은 왔지만 매우 늦게 도착할 수도 있다.
  - 더 큰 문제는, 요청을 보낸 쪽은 응답이 오지 않았을 때 "요청이 처리되지 않은 것"과 "요청은 처리됐지만 응답만 오지 않은 것"을 구분할 방법이 없다는 점이다. 이로 인해 요청을 재시도하면 중복 처리(예: 같은 결제가 두 번 실행)로 이어질 위험이 있다.
- 타임아웃(Timeout)으로의 대응과 그 딜레마
  - 응답이 오지 않는 상태를 무한정 기다릴 수 없으므로 타임아웃을 두어 일정 시간 후 실패로 간주하지만, 적절한 타임아웃 값을 정하기가 근본적으로 어렵다.
  - 타임아웃을 너무 길게 잡으면 실제 장애를 감지하는 데 오래 걸려 사용자가 느린 응답을 오래 기다리게 되고, 너무 짧게 잡으면 일시적으로 느린(죽지 않은) 노드를 장애로 오판하여 불필요한 작업 전환(Failover)을 일으킬 수 있다. 특히 이미 부하가 높은 상황에서 성급한 Failover는 그 부하를 다른 노드로 떠넘겨 연쇄 장애(Cascading Failure)로 이어질 수 있다.
  - 네트워크 지연시간(Latency) 자체도 가변적이라 고정된 하나의 타임아웃 값으로는 느린 정상 상태와 실제 장애를 명확히 구분하기 어렵다는 것이 핵심 딜레마이다.
- 설계상의 함의
  - 분산 시스템을 설계할 때는 "노드는 언제든 느려지거나 죽을 수 있고, 네트워크는 언제든 요청/응답을 지연시키거나 잃어버릴 수 있다"는 것을 기본 전제로 삼아, 이런 부분 장애를 감지하고 견뎌내는(Fault-Tolerant) 메커니즘을 소프트웨어 레벨에서 구축해야 한다.

## 신뢰할 수 없는 시계 (일 기준 시계와 단조 시계)
- 왜 분산 시스템의 시계는 신뢰할 수 없는가
  - 각 노드는 자신만의 하드웨어 시계(쿼츠 시계)를 가지고 있는데, 이 시계는 정확한 시간보다 빠르거나 느리게 흐르는 시계 드리프트(Clock Drift)가 존재한다.
  - 보통 NTP(Network Time Protocol)로 다른 서버의 시간과 동기화해 드리프트를 보정하지만, NTP 동기화 자체도 네트워크 지연에 영향을 받고, 서버마다 동기화 시점/빈도가 달라 노드 간 시계가 정확히 일치한다고 보장할 수 없다.
- 일 기준 시계(Time-of-Day Clock)
  - 현재 날짜와 시각(예: `2024-01-01 12:00:00`)을 반환하는, 사람이 이해하는 실제 시간과 동기화된 시계이다. NTP로 과거/미래 시점으로 시간이 갑자기 뛰어오를 수 있어(Forward/Backward Jump), 두 이벤트 사이의 경과 시간을 재는 데 사용하면 음수 경과 시간이 나오는 등 예상치 못한 문제가 생길 수 있다.
  - 서로 다른 두 노드에서 측정한 타임스탬프를 비교해 "어느 이벤트가 먼저 발생했는가"를 판단하는 것은, 두 노드의 시계가 어긋나 있을 수 있으므로 위험하다. (앞서 정리한 다중 리더 복제의 LWW가 바로 이 문제에 취약하다.)
- 단조 시계(Monotonic Clock)
  - 항상 앞으로만 흐르도록 보장되는 시계로, 특정 시점을 기준으로 한 경과 시간을 재는 데 적합하다. (예: 타임아웃 측정, 응답 시간 측정)
  - 일 기준 시계처럼 갑자기 뒤로 가거나 앞으로 뛰지 않지만, 서로 다른 두 컴퓨터의 단조 시계 값은 애초에 의미 있게 비교할 수 없다(각자 임의의 기준점에서 시작). 따라서 같은 컴퓨터 내에서의 시간 간격 측정에만 사용해야 한다.
- 실무에서의 함의
  - 날짜/시각을 보여주거나 기록하는 용도(일 기준 시계)와, 경과 시간을 측정하는 용도(단조 시계)를 명확히 구분해서 사용해야 한다.
  - 분산 시스템에서 이벤트의 순서를 신뢰성 있게 정해야 한다면, 물리적 시계의 타임스탬프 대신 논리적 시계(램포트 타임스탬프 등 `인과적 일관성과 램포트 타임스탬프` 참고)를 사용하는 것이 더 안전하다.

## 프로세스 중단(GC)과 임차권(Lease), 펜싱 토큰
- 프로세스가 예기치 않게 멈추는 상황들
  - GC(Garbage Collection) : 특히 Stop-the-World 방식의 GC가 발생하면, 그 순간 프로세스의 모든 스레드가 수백 밀리초에서 수 초간 완전히 멈춘다. 이 프로세스는 스스로는 멈췄다는 사실을 인지하지 못하며, 깨어난 뒤에는 마치 멈춘 적이 없던 것처럼 이어서 실행을 계속한다.
  - 그 외에도 가상머신의 일시 정지(VM Pause, 클라우드 환경에서의 라이브 마이그레이션 등), 디스크 I/O 지연, 스왑(디스크 페이징), OS의 다른 프로세스에 의한 CPU 스케줄링 지연 등도 비슷하게 프로세스를 멈출 수 있다.
  - 이런 중단이 매우 길어지면, 다른 노드들은 해당 프로세스가 죽었다고 (타임아웃으로) 오판할 수 있지만, 멈췄던 프로세스는 자신이 죽었다 깨어났다는 사실을 모른 채 자신이 여전히 리더/락 소유자라고 믿고 이전 작업을 이어서 수행할 수 있다.
- 임차권(Lease)
  - 락(Lock)을 영구적으로 소유하는 대신, 일정 시간(TTL)만 유효한 임차권 형태로 부여하는 방식이다. 임차권을 가진 프로세스는 만료 전에 주기적으로 갱신(Renew)해야 하고, 갱신하지 못하면 다른 프로세스가 그 자원을 가져갈 수 있다.
  - 문제는 임차권을 가진 프로세스가 임차권 만료 시각 이전에 "자신이 여전히 유효하다"고 판단해 작업을 수행하더라도, 그 판단과 실제 작업 수행 사이에 긴 GC 중단 등이 끼어들면 실제로는 임차권이 이미 만료된 뒤에 작업이 실행될 수 있다는 것이다. 즉 임차권만으로는 "지금 이 순간 내가 유효한 소유자다"를 완벽히 보장할 수 없다.
- 펜싱 토큰(Fencing Token)
  - 락/임차권을 부여할 때마다 단조 증가(Monotonically Increasing)하는 숫자(토큰)를 함께 발급하고, 자원(공유 저장소 등)에 쓰기를 요청할 때마다 이 토큰을 함께 전달하도록 강제하는 방식이다.
  - 자원을 관리하는 쪽(저장소 등)은 이미 더 큰 토큰 번호로 쓰기가 일어난 적이 있다면, 더 작은 (오래된) 토큰을 가진 요청은 거부한다. 이렇게 하면 GC 등으로 지연되어 늦게 도착한, 더 이상 유효하지 않은 락 소유자의 쓰기 요청을 안전하게 차단할 수 있다.
  - 앞서 정리한 `리더 장애 복구(Failover)와 스플릿 브레인`에서의 펜싱도 이와 동일한 원리이며, 이 방식이 동작하려면 락 자체가 아니라 그 락을 사용해 접근하는 자원(저장소) 쪽에서 토큰을 검증해야 한다는 점이 핵심이다.

## 시스템 모델과 안전성·활동성, 비잔틴 결함
- 시스템 모델(System Model)이란?
  - 분산 시스템 알고리즘을 설계/검증할 때, 노드와 네트워크가 어떤 식으로 동작/실패할 수 있는지를 단순화해 가정한 모델이다. 타이밍 가정과 노드 장애 가정 두 축으로 나눌 수 있다.
- 타이밍 가정 (네트워크/프로세스 지연에 대한 모델)
  - 동기 모델(Synchronous Model) : 네트워크 지연, 프로세스 멈춤, 시계 오차에 항상 정해진 상한선이 있다고 가정한다. 실제 분산 시스템(인터넷, 범용 OS)에서는 거의 성립하지 않는 현실적이지 않은 가정이다.
  - 부분 동기 모델(Partially Synchronous Model) : 대부분의 시간 동안은 상한선 안에서 동작하지만, 가끔 그 상한선을 넘어서는 경우(네트워크 지연 폭증, GC 중단 등)가 있을 수 있다고 가정한다. 현실의 시스템과 가장 비슷해 실무에서 많이 참고하는 모델이다.
  - 비동기 모델(Asynchronous Model) : 지연 시간에 대해 아무런 가정도 하지 않는다. 가장 현실적이지만 그만큼 알고리즘을 설계하기 어렵다.
- 노드 장애 가정 (노드가 어떻게 실패할 수 있는지에 대한 모델)
  - 크래시 정지(Crash-Stop) : 노드는 멈추면 그대로 영원히 멈춰있고, 다시는 응답하지 않는다고 가정한다.
  - 크래시 복구(Crash-Recovery) : 노드가 예고 없이 멈출 수 있지만, 이후 다시 응답을 시작(복구)할 수 있다고 가정하며, 멈춰있던 동안의 메모리 상태는 유실된다고 본다. 일반적으로 가장 현실적인 가정으로 널리 쓰인다.
  - 비잔틴 결함(Byzantine Fault) : 노드가 단순히 멈추는 것을 넘어, 버그나 공격으로 인해 잘못된 응답, 모순된 응답, 심지어 다른 노드를 속이기 위한 악의적인 응답까지 보낼 수 있다고 가정한다. 이를 견뎌내는 알고리즘을 비잔틴 결함 감내(Byzantine Fault Tolerance, BFT)라 부르며, 참여자를 완전히 신뢰할 수 없는 환경(블록체인 등)에서 주로 사용되고, 신뢰할 수 있는 조직 내부 시스템에서는 구현 복잡도 대비 실익이 낮아 잘 쓰이지 않는다.
- 안전성(Safety)과 활동성(Liveness)
  - 안전성 : "나쁜 일이 결코 일어나지 않는다"는 속성이다. (예: 선형성, 원자성, 유일성 보장) 안전성이 깨지면 특정 시점에 위반이 발생한 것이 확인되며, 한번 깨지면 되돌릴 수 없다.
  - 활동성 : "좋은 일이 결국에는 일어난다"는 속성이다. (예: 가용성, 종료 보장) 활동성은 특정 시점에서는 아직 만족되지 않았더라도, 미래의 어느 시점엔가 만족될 수 있는 여지가 남아있다는 차이가 있다.
  - 좋은 분산 알고리즘은 "시스템 모델의 가정이 깨지더라도(네트워크 단절, 노드 중단) 안전성은 항상 지키고, 그 가정이 다시 성립하면 활동성(진행)이 보장된다"는 식으로 설계하는 것이 일반적이다.

## CAP 이론
- CAP 이론이란?
  - 분산 시스템은 Consistency(일관성), Availability(가용성), Partition Tolerance(분할 내성) 3가지 속성을 동시에 모두 만족할 수 없고, 최대 2가지만 보장할 수 있다는 이론이다.
  - 캘리포니아 버클리대 교수 에릭 브루어(Eric Brewer)가 제시했다고 해서 브루어의 정리(Brewer's Theorem)라고도 불린다.
- CAP의 3요소
  - Consistency(일관성)
    - 모든 노드가 동일한 시점에 동일한 데이터를 보여주는 것을 의미한다. 즉, 어느 노드에 요청을 보내도 가장 최근에 쓰여진 데이터를 응답받을 수 있어야 한다.
  - Availability(가용성)
    - 일부 노드에 장애가 발생하더라도, 살아있는 노드는 항상 정상적으로 응답(성공/실패 여부와 무관하게 응답 자체)을 반환할 수 있어야 한다.
  - Partition Tolerance(분할 내성)
    - 네트워크 장애로 인해 노드 간 통신이 단절(네트워크 파티션)되더라도, 시스템 전체는 계속 정상적으로 동작해야 한다.
- 왜 3가지를 동시에 만족할 수 없는가?
  - 분산 시스템에서는 네트워크 장애(노드 간 통신 단절)가 언제든 발생할 수 있으므로, 사실상 Partition Tolerance는 선택이 아니라 필수로 감수해야 하는 전제에 가깝다.
  - 네트워크 파티션이 발생했다고 가정했을 때, 분리된 두 노드 그룹이 계속 요청에 응답(Availability를 지키는 선택)하면 서로 다른 데이터를 반환할 수 있어 Consistency가 깨지고, 반대로 데이터가 동기화될 때까지 응답을 거부(Consistency를 지키는 선택)하면 그 사이 요청한 클라이언트는 응답을 받지 못해 Availability가 깨진다.
  - 즉 파티션이 발생한 순간에는 C와 A 중 하나만 선택할 수밖에 없기 때문에, 실질적으로는 CP와 AP 중 하나의 트레이드오프를 선택하는 문제로 귀결된다.
- CP(Consistency + Partition Tolerance) 시스템
  - 네트워크 파티션이 발생하면, 일관성이 깨질 위험이 있는 노드는 응답을 거부하여 가용성을 포기한다.
  - 데이터의 정합성이 중요한 은행, 결제 시스템 등에 적합하다.
  - 대표적으로 ZooKeeper, MongoDB(기본 설정), HBase 등이 있다.
- AP(Availability + Partition Tolerance) 시스템
  - 네트워크 파티션이 발생해도 모든 노드가 응답은 계속하되, 데이터의 일관성은 즉시 보장하지 못할 수 있다. 대신 시간이 지나면 데이터가 일치하게 되는 최종적 일관성(Eventual Consistency)을 지향한다.
  - 서비스가 일시적으로 죽는 것보다, 약간 오래된 데이터라도 응답하는 것이 중요한 SNS 피드, 쇼핑몰 상품 조회 등에 적합하다.
  - 대표적으로 Cassandra, DynamoDB, Couchbase 등이 있다.
- CA(Consistency + Availability) 조합은 왜 현실적으로 의미가 없는가?
  - 네트워크 파티션이 아예 발생하지 않는다는 전제 하에서만 성립하는데, 분산 시스템에서는 노드 간 네트워크 장애를 원천적으로 배제할 수 없으므로 CA는 사실상 파티션 자체가 불가능한 단일 노드 시스템에서만 성립하는 이론적인 조합에 가깝다.
  - 전통적인 단일 RDBMS(단일 노드로 운영될 때)가 CA에 해당한다고 볼 수 있다.

## 인과적 일관성과 램포트 타임스탬프
- 인과적 일관성(Causal Consistency)
  - 인과관계(원인과 결과, Causality)가 있는 이벤트들은 모든 노드에서 항상 같은 순서로 관찰되어야 한다는 일관성 모델이다. (앞서 정리한 `복제 지연과 일관성 보장`의 일관된 순서로 읽기와 같은 맥락이다.)
  - 반면 인과관계가 없는(서로 동시에, 독립적으로 발생한) 이벤트는 노드마다 다른 순서로 보여도 괜찮다. 이는 모든 이벤트에 전역적으로 하나의 순서를 강제하는 선형성(Linearizability)보다 약한 보장이지만, 그만큼 네트워크 지연/장애에 덜 민감해 성능과 가용성 면에서 유리하다.
  - 예를 들어 SNS에서 "질문" 게시물과 그에 대한 "답변" 댓글은 인과관계가 있으므로 항상 질문이 먼저 보여야 하지만, 서로 무관한 두 사용자의 게시물 순서는 노드마다 달라도 상관없다.
- 왜 순서를 추적해야 하는가
  - 분산 시스템에서는 일 기준 시계의 타임스탬프로 "무엇이 먼저 발생했는가"를 판단할 수 없으므로(앞서 정리한 `신뢰할 수 없는 시계` 참고), 물리적 시간이 아닌 논리적인 방법으로 이벤트의 인과 순서를 추적해야 한다.
- 램포트 타임스탬프(Lamport Timestamp)
  - 각 노드가 (카운터, 노드ID) 형태의 값을 유지하며, 다음 규칙으로 갱신한다. 이벤트가 발생할 때마다 카운터를 1 증가시키고, 다른 노드로부터 메시지를 받으면 자신의 카운터를 메시지에 담긴 카운터와 자신의 카운터 중 더 큰 값+1로 갱신한다.
  - 두 타임스탬프를 비교할 때는 먼저 카운터 값을 비교하고, 카운터가 같으면 노드 ID로 동점을 깬다. 이렇게 하면 모든 이벤트에 대해 전역적으로 비교 가능한 하나의 전체 순서(Total Order)를 부여할 수 있다.
  - 중요한 성질은, A가 B보다 인과적으로 먼저 일어났다면(B가 A를 알고 발생) A의 램포트 타임스탬프는 항상 B보다 작다는 것이다. 다만 역은 성립하지 않는다. 즉 타임스탬프가 작다고 해서 반드시 인과적으로 먼저라는 뜻은 아니며, 서로 무관한(동시 발생) 이벤트 사이에서도 임의로 순서가 매겨진다.
- 한계와 전체 순서 브로드캐스트와의 관계
  - 램포트 타임스탬프는 모든 이벤트에 전체 순서를 부여할 수 있지만, "지금 이 순서가 최종 확정됐다"는 것을 그 시점에 바로 알 수는 없다. 예를 들어 유일한 사용자명을 선점하는 상황에서는, 더 작은 타임스탬프를 가진 요청이 나중에 도착할 수도 있다는 점에서 즉시 결정을 내릴 수 없다.
  - 이 "지금 당장 알 수 있는 확정된 순서"가 필요한 경우에는 전체 순서 브로드캐스트(Total Order Broadcast, 다음 항목 참고)와 같은 더 강력한 메커니즘이 필요하다.

## 전체 순서 브로드캐스트와 상태 기계 복제
- 전체 순서 브로드캐스트(Total Order Broadcast)란?
  - 여러 노드에게 메시지를 전달할 때, 모든 노드가 정확히 같은 순서로, 정확히 한 번씩 그 메시지들을 받도록 보장하는 프로토콜이다.
  - 신뢰성(Reliable Delivery) : 메시지가 유실되지 않고 모든 노드에 전달된다.
  - 전체 순서(Totally Ordered Delivery) : 어떤 노드도 다른 노드와 다른 순서로 메시지를 받지 않는다. 즉 메시지 A가 어떤 노드에서 B보다 먼저 전달됐다면, 다른 모든 노드에서도 A가 B보다 먼저 전달되어야 한다.
  - 앞서 정리한 램포트 타임스탬프(`인과적 일관성과 램포트 타임스탬프` 참고)는 모든 이벤트에 전체 순서를 부여할 수는 있지만 그 순서가 "지금 확정됐다"는 것을 즉시 알 수 없는 반면, 전체 순서 브로드캐스트는 메시지가 전달되는 그 순간 순서가 고정(확정)된다는 차이가 있다.
- 상태 기계 복제(State Machine Replication)와의 관계
  - 모든 노드가 동일한 초기 상태에서 시작해, 정확히 같은 순서로 동일한 연산(쓰기)을 적용하면 결정적으로 모든 노드가 항상 같은 최종 상태에 도달하게 된다는 아이디어이다.
  - 전체 순서 브로드캐스트는 바로 이 "모든 노드가 같은 순서로 연산을 받는다"는 조건을 만족시켜주므로, 전체 순서 브로드캐스트를 구현할 수 있다면 그 위에 선형성 있는 저장소나 상태 기계 복제 기반의 데이터베이스를 구축할 수 있다.
  - 단일 리더 복제(앞서 정리한 `복제 방식: 단일 리더, 다중 리더, 리더 없는 복제` 참고)도 본질적으로는 상태 기계 복제의 한 형태로 볼 수 있다. 리더가 받는 쓰기 순서가 그대로 복제 로그의 순서가 되고, 모든 팔로워가 그 순서대로 로그를 적용하기 때문이다.
- 전체 순서 브로드캐스트로 할 수 있는 것들
  - 선형성 있는 쓰기 구현, 분산 락/리더 선출, 고유성 제약(유일한 사용자명 등) 보장, 분산 트랜잭션에서의 원자적 커밋 순서 결정 등 다양한 분산 시스템 문제를 전체 순서 브로드캐스트 위에서 풀 수 있다.
  - 전체 순서 브로드캐스트를 안전하게 구현하는 것 자체는 합의(Consensus) 문제와 동치로 알려져 있어, 실제로는 Raft, Paxos와 같은 합의 알고리즘(다음 항목 참고)을 통해 구현된다.

## 합의 알고리즘(Raft, Paxos)과 ZooKeeper, etcd
- 합의(Consensus) 문제란?
  - 여러 노드가 각자 어떤 값을 제안했을 때, 그중 단 하나의 값에 대해 모든 (정상 동작하는) 노드가 동일하게 동의하도록 만드는 문제이다. 한 번 결정된 값은 절대 번복되지 않아야 한다(불변성).
  - 리더 선출(여러 노드 중 하나만 리더가 되어야 함)이나 원자적 커밋(여러 참여자가 모두 커밋할지 모두 중단할지 하나로 결정해야 함)과 같은 문제들이 모두 합의 문제의 한 형태로 환원될 수 있다.
- 왜 2PC로는 부족한가
  - 앞서 정리한 2단계 커밋(2PC)은 코디네이터가 단일 장애점이 되어, 코디네이터가 죽으면 참여자들이 무기한 블로킹된다는 근본적인 한계가 있었다.
  - Raft, Paxos와 같은 합의 알고리즘은 코디네이터(리더) 역할을 하는 노드가 죽더라도 남은 노드들의 정족수(Quorum, 과반수)만으로 새로운 리더를 선출하고 계속 진행할 수 있어, 단일 장애점 문제를 해결한다.
- 합의 알고리즘의 공통된 동작 방식
  - 대부분의 합의 알고리즘은 리더 기반(Leader-Based)으로 동작한다. 먼저 과반수 투표로 리더를 선출하고, 이후 모든 쓰기(제안)는 리더를 거치며, 리더는 그 쓰기를 과반수의 팔로워가 승인(정족수 확보)해야 비로소 확정(커밋)한다.
  - 리더가 죽으면 남은 노드들이 새로운 리더 선출(에포크 번호/임기 번호를 증가시켜 가며)을 진행하는데, 이 과정에서 과반수 투표를 통해 스플릿 브레인(둘 이상의 리더가 동시에 존재하는 상황)을 방지한다.
- Raft와 Paxos
  - Paxos는 가장 먼저 등장한 이론적 기반의 합의 알고리즘으로, 이해하고 올바르게 구현하기가 매우 어렵다고 알려져 있다.
  - Raft는 Paxos보다 이해하고 구현하기 쉽도록 설계된 알고리즘으로, 리더 선출과 로그 복제 과정을 명확하게 분리해 설명한다. etcd, Consul 등이 Raft를 사용한다.
  - 두 알고리즘 모두 전체 순서 브로드캐스트(앞서 정리한 항목 참고)를 구현하기 위한 수단으로 볼 수 있다.
- ZooKeeper와 etcd
  - ZooKeeper(합의 알고리즘으로 ZAB 사용)와 etcd(Raft 사용)는 합의 알고리즘을 내부적으로 구현해 제공하는 코디네이션 서비스(Coordination Service)이다. 애플리케이션이 직접 합의 알고리즘을 구현하는 대신, 이들을 이용해 분산 락, 리더 선출, 설정 정보 공유, 서비스 디스커버리(앞서 정리한 `리밸런싱 전략과 요청 라우팅` 참고) 등의 기능을 구현할 수 있다.
  - 소수의 노드(보통 3~5대)로 운영되며, 많은 양의 데이터를 저장하는 용도가 아니라 소량의 중요한 메타데이터(누가 리더인지, 어떤 파티션이 어디에 있는지 등)를 신뢰성 있게 관리하는 데 사용된다.

## 원천 데이터와 파생 데이터
- 원천 데이터(Source of Truth / System of Record)
  - 데이터가 처음 발생하는 지점이자, 그 데이터에 대한 "진짜" 값으로 신뢰되는 원본 데이터이다. 보통 사용자의 입력이나 비즈니스 이벤트를 직접 기록하는 OLTP 데이터베이스가 이에 해당한다.
  - 원천 데이터는 다른 어떤 데이터로부터도 유도되지 않으며, 정규화(Normalization)되어 중복이 최소화된 형태로 저장되는 경우가 많다.
- 파생 데이터(Derived Data)
  - 원천 데이터를 가공/변환/집계하여 만들어낸 데이터이다. 캐시, 검색 색인, 데이터 웨어하우스의 집계 테이블, 추천 시스템의 모델 등이 대표적인 예이다.
  - 파생 데이터는 원천 데이터로부터 언제든 다시 계산(재생성)할 수 있다는 특징이 있다. 즉 파생 데이터가 손상되거나 유실되어도, 원천 데이터가 살아있다면 다시 만들어낼 수 있다.
- 왜 이 구분이 중요한가
  - 원천 데이터는 절대 유실되면 안 되는 것이므로 백업/정합성 관리에 가장 엄격한 기준을 적용해야 하지만, 파생 데이터는 다시 만들 수 있으므로 상대적으로 가용성/성능 쪽에 더 유연하게 접근할 수 있다.
  - 파생 데이터를 만드는 과정(원천 데이터 → 파생 데이터로의 변환)은 CDC(앞서 정리한 `이중 쓰기(Dual Write) 문제와 CDC` 참고), 배치 처리(다음 항목 `일괄 처리와 맵리듀스` 참고), 스트림 처리 등 다양한 방식으로 이루어질 수 있으며, 이 변환 로직이 결정적(Deterministic)이어야 같은 원천 데이터로부터 항상 같은 파생 데이터를 재생성할 수 있다.
  - 실제 대규모 시스템은 하나의 원천 데이터로부터 여러 개의 파생 데이터(캐시, 검색 색인, 분석용 웨어하우스 등)를 서로 다른 형태로 유지하는 경우가 많으며, 이들 사이의 정합성을 어떻게 유지할지(동기 vs 비동기, 지연 허용 범위)가 시스템 설계의 핵심 고민이 된다.

## 일괄 처리와 맵리듀스, 데이터플로 엔진(Spark, Flink)
- 일괄 처리(Batch Processing)란?
  - 이미 모아져 있는 유한한(bounded) 크기의 데이터셋을 입력으로 받아, 한 번에 처리해 결과를 출력하는 방식이다. 스트림 처리(앞서 정리한 `스트림 처리: 이벤트 시간, 윈도우, 스트림 조인` 참고)가 끝없이 들어오는 데이터를 즉시 처리하는 것과 달리, 배치 처리는 처리 시작 시점에 입력 데이터의 전체 범위가 고정되어 있다.
  - 실시간성보다는 대량의 데이터를 정확하고 안정적으로 처리하는 것이 목적이며, 보통 일/시간 단위로 주기적으로 실행된다. (예: 하루치 로그 집계, 전체 데이터 재색인)
- 맵리듀스(MapReduce)
  - 대용량 데이터를 여러 노드에 분산해서 처리하기 위한 프로그래밍 모델이자 분산 처리 프레임워크로, Map 단계와 Reduce 단계로 구성된다.
  - Map : 입력 데이터를 여러 개의 조각(파티션)으로 나누어 각 노드에서 독립적으로 처리하며, 각 레코드에 대해 키-값(Key-Value) 쌍을 출력한다.
  - Shuffle & Sort : Map의 출력을 같은 키를 가진 값들이 한곳에 모이도록 네트워크를 통해 재분배(셔플)하고 정렬한다.
  - Reduce : 같은 키로 모인 값들을 집계/병합하여 최종 결과를 만든다.
  - 각 단계의 중간 결과를 디스크에 기록(내결함성을 위해)하기 때문에, 실패한 작업을 처음부터 다시 돌리지 않고 특정 단계부터 재시도할 수 있다는 장점이 있지만, 그만큼 디스크 I/O가 많아 반복적인 연산(예: 머신러닝의 반복 알고리즘)에는 비효율적이다.
- 데이터플로 엔진(Spark, Flink)
  - 맵리듀스의 "매 단계마다 디스크에 기록"하는 방식의 비효율을 개선하기 위해 등장한 차세대 분산 처리 프레임워크이다.
  - 연산 전체를 방향성 비순환 그래프(DAG, Directed Acyclic Graph)로 표현해, 가능한 한 중간 결과를 메모리에 유지하면서 여러 연산을 하나의 파이프라인으로 이어 처리한다. 이로 인해 디스크 I/O가 크게 줄어 맵리듀스보다 훨씬 빠른 처리 속도를 보인다.
  - Spark는 배치 처리에 특화되어 있으며 메모리 기반의 RDD(Resilient Distributed Dataset) 추상화를 사용하고, Flink는 스트림 처리를 기본 모델로 삼으면서 배치 처리를 "유한한 스트림"으로 취급해 두 모델을 통합적으로 다룬다는 차이가 있다.
  - 두 프레임워크 모두 일부 노드의 장애가 발생해도 처리를 재시작할 수 있는 내결함성(Fault Tolerance) 메커니즘(체크포인트, 데이터 계보 추적 등)을 갖추고 있어, 대규모 클러스터에서도 안정적으로 분산 처리를 수행할 수 있다.

## 로그 기반 메시지 브로커와 전통적 메시지 브로커
- 전통적 메시지 브로커 (AMQP/JMS 스타일, 예: RabbitMQ)
  - 메시지를 큐(Queue)에 쌓아두고, 컨슈머가 메시지를 가져가면 보통 그 메시지는 큐에서 제거(소비, Consume)되는 방식으로 동작한다.
  - 여러 컨슈머가 하나의 큐를 구독하면 메시지들이 나뉘어 분배(Round-Robin 등)되어 각 메시지는 보통 그중 하나의 컨슈머에게만 전달된다. 이는 작업(Task)을 여러 워커에게 나누어 처리시키는 작업 큐(Work Queue) 용도에 적합하다.
  - 메시지가 한 번 소비되면 사라지기 때문에, 같은 메시지를 나중에 다시 읽거나 여러 다른 소비자 그룹이 각자 독립적으로 전체 메시지를 다시 처리하는 것이 기본적으로는 어렵다.
- 로그 기반 메시지 브로커 (예: Kafka)
  - 메시지(이벤트)를 소비 여부와 무관하게 추가 전용(Append-Only) 로그에 순서대로 기록해두고, 일정 기간(또는 용량) 동안 보존한다. 컨슈머는 로그를 읽어도 메시지가 삭제되지 않으며, 각자 자신이 어디까지 읽었는지(오프셋, Offset)를 기억한다.
  - 하나의 토픽(Topic)을 여러 개의 파티션(Partition)으로 나누어 저장하며, 각 파티션 내에서는 메시지 순서가 보장된다. 컨슈머 그룹(Consumer Group) 단위로 파티션을 나누어 가져가 병렬로 처리할 수 있어 처리량을 확장할 수 있다.
  - 같은 메시지를 서로 다른 여러 컨슈머 그룹이 독립적으로 각자의 오프셋을 유지하며 재생(Replay)할 수 있어, 하나의 이벤트 스트림으로부터 여러 개의 파생 데이터(캐시 갱신, 검색 색인, 분석 집계 등)를 동시에 만들어낼 수 있다. 이는 앞서 정리한 CDC, 트랜잭셔널 아웃박스 패턴, 스트림 처리의 기반이 된다.
  - 메시지를 명시적으로 지우는 대신 오프셋만 커밋하면 되므로 처리 실패 시 같은 오프셋부터 재처리할 수 있어, 멱등한 처리 로직과 함께 사용하면 At-Least-Once 전달을 안전하게 다룰 수 있다.
- 선택 기준
  - 작업을 나누어 한 번만 처리하면 되는 단순한 작업 큐 용도라면 전통적 메시지 브로커가 적합하고, 이벤트를 여러 소비자가 독립적으로 재생/재처리해야 하거나 높은 처리량과 순서 보장이 중요한 이벤트 스트리밍 용도라면 로그 기반 메시지 브로커가 적합하다.
