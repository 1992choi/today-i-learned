## 교착상태(Deadlock)
- 교착상태란?
  - 일련의 프로세스들이 서로가 가진 자원을 기다리며 block되어, 더 이상 진행이 될 수 없는 상태를 의미한다.
  - 즉, 둘 이상의 프로세스가 다른 프로세스가 점유하고 있는 자원을 서로 기다릴 때 무한 대기에 빠지는 상황을 일컫는다.
- 교착상태 발생조건
  - 다음의 4가지 조건을 모두 성립해야 데드락이 발생한다.
    - 상호 배제
      - 매 순간 하나의 프로세스만이 자원을 사용할 수 있다.
    - 점유 대기
      - 자원을 가진 프로세스가 다른 자원을 기다릴 때, 보유하고 있는 자원을 놓지 않고 계속 가지고 있다.
    - 비선점
      - 프로세스는 OS에 의해 강제로 자원을 빼앗기지 않는다.
      - 즉, 자원을 강제로 빼앗는게 아니라, 자원을 점유하고 있는 프로세스가 해당 자원을 해제해야 한다는 것이다.
    - 순환 대기
      - 자원을 기다리는 프로세스 간에 사이클이 형성어되야 한다.
- 교착상태 해결법
  - 데드락 예방(Prevention)
    - 자원의 상호 배제 조건 방지
      - 한 번에 여러 프로세스가 공유 자원을 사용할 수 있게한다. (단, 동기화 관련 문제가 발생할 수 있다.)
    - 점유 대기 조건 방지
      - 프로세스 실행에 필요한 모든 자원을 한꺼번에 요구하고 허용할 때까지 작업을 보류해서, 나중에 또다른 자원을 점유하기 위한 대기 조건을 성립하지 않도록 한다.
    - 비선점 조건 방지
      - 자원을 보유한 프로세스가 다른 자원을 요청했을 때 즉시 할당받을 수 없다면, 보유하고 있던 자원을 모두 반납하도록 한다. 이후 반납했던 자원과 새로 요청한 자원을 모두 확보할 수 있을 때 다시 실행되도록 한다.
    - 순환 대기 조건 방지
      - 자원을 순환 형태로 대기하지 않도록 일정한 한 쪽 방향으로만 자원을 요구할 수 있도록 한다.
  - 데드락 회피(Avoidance)
    - 데드락 회피법에서는 Safe sequence, Safe state 등이 키워드이다.
    - 시스템의 프로세스들이 요청하는 모든 자원을, 데드락을 발생시키지 않으면서도 차례로 모두에게 할당해 줄 수 있다면 안정 상태(safe state)에 있다고 말한다.
    - 그리고 이처럼 특정한 순서로 프로세스들에게 자원을 할당, 실행 및 종료 등의 작업을 할 때 데드락이 발생하지 않는 순서를 찾을 수 있다면, 그것을 안전 순서(safe sequence)라고 부른다.
    - 회피 알고리즘(Ex. 은행원 알고리즘)을 통해 자원을 할당한 후에도 시스템이 항상 Safe state에 있을 수 있도록 할당을 허용하자는 것이 기본 특징이다.
  - 데드락 탐지(Detection) 및 회복(Recovery)
    - 시스템이 데드락 예방이나 회피법을 사용하지 않았을 때, 데드락이 발생할 수 있으니 여기에서 회복하기 위해 데드락을 탐지하고, 회복하는 알고리즘을 사용한다.
    - 탐지 기법
      - Allocation, Request, Available 등으로 시스템에 데드락이 발생했는지 여부를 탐색한다.
      - 즉, 은행원 알고리즘에서 했던 방식과 유사하게 현재 시스템의 자원 할당 상태를 가지고 파악한다.
      - 이 외에도 자원 할당 그래프를 통해 탐지하는 방법도 있다.
    - 회복 기법
      - 데드락을 탐지 기법을 통해 발견했다면, 순환 대기에서 벗어나 데드락으로부터 회복하기 위한 방법을 사용한다.
        - 단순히 프로세스를 1개 이상 중단시키기
          - 교착 상태에 빠진 모든 프로세스를 중단시키는 방법
            - 계속 연산중이던 프로세스들도 모두 일시에 중단되어 부분 결과가 폐기될 수 있는 부작용이 발생할 수 있다.
          - 프로세스를 하나씩 중단 시킬 때마다 탐지 알고리즘으로 데드락을 탐지하면서 회복시키는 방법
            - 매번 탐지 알고리즘을 호출 및 수행해야 하므로 부담이 되는 작업일 수 있다.
        - 자원 선점하기
          - 프로세스에 할당된 자원을 선점해서, 교착 상태를 해결할 때까지 그 자원을 다른 프로세스에 할당해준다.

## 뮤텍스와 세마포어
- 임계 영역(Critical Section)이란?
  - 여러 프로세스가 데이터를 공유하며 수행될 때, 각 프로세스에서 공유 데이터를 접근하는 프로그램 코드 블록을 뜻한다.
  - 즉, 여러 프로세스가 동일 자원을 동시에 참조하여 값(공유하는 변수명, 파일 등)이 오염될 위험 가능성이 있는 영역이다.
- 뮤텍스(Mutex)와 세마포어(Semaphore)란?
  - 프로세스 간 메시지를 전송하거나, 공유메모리를 통해 공유된 자원에 여러 개의 프로세스가 동시에 접근하면 Critical Section 문제가 발생할 수 있다.
  - 이를 해결하기 위해 데이터를 한 번에 하나의 프로세스만 접근할 수 있도록 제한을 두는 동기화 방식을 취해야 하는데, 대표적인 동기화 도구에는 뮤텍스와 세마포어가 있다.
- 뮤텍스(Mutex)
  - 동시 프로그래밍에서 공유 불가능한 자원의 동시 사용을 피하기 위해 사용하는 알고리즘이다.
  - 임계구역(Critical Section)을 가진 스레드들의 실행시간(Running Time)이 서로 겹치지 않고 각각 단독으로 실행되도록 하는 기술이다.
  - 한 프로세스에 의해 소유될 수 있는 Key를 기반으로 한 상호배제 기법이다.
  - 다중 프로세스들의 공유 리소스에 대한 접근을 조율하기 위해 동기화(Synchronization) 또는 락(Lock)을 사용한다.
  - 뮤텍스 객체를 두 스레드가 동시에 사용할 수 없다.
- 세마포어(Semaphore)
  - 멀티 프로그래밍 환경에서 공유된 자원에 대한 접근을 제한하는 방법이다.
  - 사용하고 있는 스레드/프로세스의 수를 공통으로 관리하는 하나의 값을 이용해 상호배제를 달성한다.
  - 공유 자원에 접근할 수 있는 프로세스의 최대 허용치만큼 동시에 사용자가 접근할 수 있다.
  - 각 프로세스는 세마포어의 값을 확인하고 변경할 수 있다.
  - 자원을 사용하지 않는 상태가 될 때, 대기하던 프로세스가 즉시 자원을 사용한다.
  - 이미 다른 프로세스에 의해 사용중이라는 사실을 알게 되면, 재시도 전에 일정시간 대기해야 한다.
  - 세마포어를 사용하는 프로세스는 그 값을 확인하고, 자원을 사용하는 동안에는 그 값을 변경함으로써 다른 세마포어 사용자들이 대기하도록 해야 한다.
  - 세마포어는 이진수를 사용하거나 추가적인 값을 가질 수 있다.
- 뮤텍스(Mutex)와 세마포어(Semaphore)의 차이점
  - 가장 큰 차이점은 동기화 대상의 갯수이다. 뮤텍스는 동기화 대상이 오직 1개일 때 사용하고, 세마포어는 동기화 대상이 1개 이상일 때 사용한다.
  - 세마포어는 뮤텍스가 될 수 있지만, 뮤텍스는 세마포어가 될 수 없다.
  - 뮤텍스는 자원 소유가 가능한 반면에 세마포어는 자원 소유가 불가능하다.
  - 뮤텍스는 소유하고 있는 스레드만이 이 뮤텍스를 해제할 수 있지만 세마포어는 세마포어를 소유하지 않은 스레드가 세마포어를 해제할 수 있다.
  - 세마포어는 시스템 범위에 걸쳐있고, 파일 시스템상에 파일로 존재하는 반면에 뮤텍스는 프로세스의 범위를 가지며 프로세스가 종료될 때 자동으로 Clean up된다.

## 프로세스 vs 스레드
- 프로세스(Process)란?
  - 운영체제로부터 자원을 할당받는 작업의 단위이며, 실행 중인 프로그램을 의미한다.
  - 각 프로세스는 독립된 메모리 공간(Code, Data, Stack, Heap)을 할당받아 실행되며, 다른 프로세스의 메모리 영역에 접근할 수 없다.
  - 최소 1개의 메인 스레드를 가지고 있으며, 프로세스 내에는 스레드가 여러 개 존재할 수 있다.
  - New(생성) → Ready(준비) → Running(실행) → Waiting/Blocked(대기) → Terminated(종료) 상태를 가지며, CPU 스케줄러에 의해 Ready와 Running 사이를 오간다.
- 프로세스 간 통신(IPC)
  - 프로세스끼리는 자원을 공유하지 않기 때문에, 통신을 하려면 파이프(Pipe), 소켓(Socket), 공유 메모리(Shared Memory), 메시지 큐(Message Queue), 시그널(Signal) 등 별도의 커널 지원이 필요하고 비용이 크다.
  - 공유 메모리가 가장 빠르지만 동기화를 직접 처리해야 하고, 소켓/파이프는 상대적으로 느리지만 구현이 단순하고 네트워크를 넘어서도 사용할 수 있다.
- 스레드(Thread)란?
  - 프로세스 내에서 실행되는 흐름의 단위로, 프로세스가 할당받은 자원을 이용하는 실제 작업 단위이다.
  - 한 프로세스 내의 스레드들은 Code, Data, Heap 영역을 공유하고, Stack 영역만 각자 독립적으로 할당받는다.
  - 스레드는 프로세스 내 자원을 공유하기 때문에 통신 비용이 적고, Context Switching 비용도 프로세스보다 적다.
  - 스택만 독립적으로 할당하는 이유는, 스택에는 함수 호출 정보(지역 변수, 매개변수, 리턴 주소)가 쌓이는데 각 스레드가 독립적인 실행 흐름(함수 호출 순서)을 가지려면 자신만의 호출 스택이 필요하기 때문이다. 스택을 공유하면 서로 다른 실행 흐름의 함수 호출 정보가 뒤섞여 프로그램이 정상적으로 동작할 수 없다.
- 멀티 프로세스 vs 멀티 스레드
  - 멀티 프로세스
    - 여러 개의 프로세스를 이용해 동시에 여러 작업을 처리하는 방식이다.
    - 하나의 프로세스에서 문제가 발생해도 다른 프로세스에 영향을 주지 않아 안정성이 높다.
    - 각 프로세스가 독립된 메모리 공간을 사용하므로 Context Switching 비용이 크고, 프로세스 간 통신(IPC) 비용도 크다.
  - 멀티 스레드
    - 하나의 프로세스 내에서 여러 스레드가 자원을 공유하며 동시에 여러 작업을 처리하는 방식이다.
    - 자원을 공유하기 때문에 통신 비용과 Context Switching 비용이 적어 효율적이다.
    - 자원을 공유하기 때문에 여러 스레드가 동시에 같은 데이터에 접근·수정하면서 값이 꼬이는 Race Condition이 발생할 수 있고, 뮤텍스·세마포어·락 등으로 임계 영역에 한 번에 하나의 스레드만 접근하도록 제한해 해결한다. 하나의 스레드에 문제가 생기면 프로세스 전체에 영향을 줄 수 있어 안정성은 낮다.
    - 스레드가 많다고 무조건 빠른 것은 아니다. CPU 코어 수를 초과하는 스레드는 Context Switching 오버헤드를 늘리고, 공유 자원에 대한 락 경합(Lock Contention)이 심해지면 오히려 성능이 떨어질 수 있다.
  - 안정성이 중요하고 작업 간 격리가 필요하다면(예: 웹 브라우저의 탭별 프로세스) 멀티 프로세스를, 자원 공유가 잦고 빠른 통신이 필요한 경우(예: 서버의 요청 처리)라면 멀티 스레드를 선택한다.

## 컨텍스트 스위칭
- 컨텍스트 스위칭(Context Switching)이란?
  - CPU가 하나의 프로세스(또는 스레드)를 실행하다가 다른 프로세스(또는 스레드)로 전환할 때, 기존 프로세스의 실행 상태(Context)를 저장하고 다음 프로세스의 상태를 불러오는 과정을 말한다.
  - 멀티태스킹 OS에서 여러 프로세스가 하나의 CPU를 시분할하여 사용할 수 있게 해주는 핵심 매커니즘이다.
  - 타이머 인터럽트로 인한 Time Quantum 만료, I/O 요청으로 인한 Blocked 상태 전환, 더 높은 우선순위 프로세스의 등장, 시스템 콜 처리 등의 상황에서 발생한다. 인터럽트는 하드웨어(타이머, I/O 장치)가 CPU에 비동기적으로 알리는 신호이고, 시스템 콜은 사용자 프로그램이 커널 기능을 사용하기 위해 명시적으로 호출하는 소프트웨어 인터럽트라는 차이가 있지만, 둘 다 CPU 제어권이 커널로 넘어가는 계기가 된다는 점은 같다.
- PCB(Process Control Block)란?
  - 프로세스의 상태 정보를 저장하는 커널 내부의 자료구조로, Context Switching 시 저장/복원되는 대상이다.
  - PC(Program Counter, 다음 실행할 명령어 주소), CPU 레지스터 값, 프로세스 상태(Ready/Running/Waiting 등), 메모리 관리 정보(페이지 테이블 등), 스케줄링 정보(우선순위 등), 입출력 상태 정보를 포함한다.
- 동작 과정
  - 1. 인터럽트(타이머 인터럽트, I/O 요청 등)가 발생하면 CPU는 현재 실행 중인 프로세스를 멈춘다.
  - 2. 현재 프로세스의 레지스터 값 등 실행 상태를 해당 프로세스의 PCB에 저장한다.
  - 3. 다음에 실행할 프로세스의 PCB에서 상태를 읽어와 CPU 레지스터에 복원한다.
  - 4. 복원된 프로세스를 실행 재개한다.
- Context Switching은 왜 오버헤드인가?
  - 레지스터/메모리 상태를 저장하고 복원하는 시간 자체도 오버헤드지만, 캐시(Cache)와 TLB(Translation Lookaside Buffer, 가상 주소 → 물리 주소 변환을 캐싱해두는 하드웨어 캐시)가 새 프로세스에 맞게 갱신되어야 하므로 캐시 미스가 늘어나는 간접 비용이 더 크다. 프로세스가 전환되면 주소 공간이 바뀌므로 기존 TLB 엔트리가 무효화(Flush)되고, 이후 메모리 접근 시 TLB Miss로 이어져 성능이 저하된다.
  - Time Quantum을 적절히 크게 설정해 전환 빈도를 줄이거나, 멀티스레드를 활용해 전환 비용 자체를 낮추거나, CPU affinity를 설정해 캐시 지역성을 유지하는 방식으로 비용을 줄일 수 있다.
- 스레드 전환이 프로세스 전환보다 비용이 적은 이유
  - 같은 프로세스 내의 스레드는 Code/Data/Heap 및 페이지 테이블(주소 공간)을 공유하기 때문에, 스레드 전환 시에는 메모리 매핑 정보를 교체할 필요가 없다.
  - 반면 프로세스 전환은 주소 공간 자체가 다르므로 페이지 테이블 교체, TLB Flush 등 추가 작업이 필요해 비용이 더 크다.

## 메모리 구조
- 프로세스의 메모리 구조는 크게 Code, Data, Stack, Heap 4가지 영역으로 나뉜다.
- Code(Text) 영역
  - 작성한 소스 코드가 컴파일되어 기계어(바이너리) 형태로 저장되는 영역이다.
  - 실행 중에 코드가 변경되면 안 되므로 읽기 전용(Read-only)으로 관리된다.
- Data 영역
  - 전역 변수, static 변수가 저장되는 영역이다.
  - 프로그램 시작과 함께 할당되고, 프로그램이 종료되어야 소멸된다.
  - 초기화된 데이터는 Data 영역에, 초기화되지 않은 데이터는 BSS(Block Started by Symbol) 영역에 저장되는 것이 일반적이다.
- Stack 영역
  - 함수 호출 시 생성되는 지역 변수, 매개변수, 리턴 주소 등이 저장되는 영역이다.
  - 함수가 호출될 때 스택 프레임이 push되고, 함수가 종료되면 자동으로 pop되어 해제된다.
  - 컴파일 타임에 크기가 결정되며, 후입선출(LIFO) 구조로 관리된다. 포인터 하나만 이동시키면 되는 단순한 push/pop 구조이고 접근 지역성이 좋아 캐시 효율이 높기 때문에 Heap보다 빠르다.
  - 재귀 함수가 종료 조건 없이 계속 호출되거나 지역 변수로 매우 큰 배열을 선언하는 등 스택 영역의 한계를 초과하면 Stack Overflow가 발생한다.
- Heap 영역
  - 개발자가 명시적으로 할당(예: Java의 `new`, C의 `malloc`)하는 동적 메모리 영역이다.
  - 크기가 가변적이며, 런타임에 할당/해제가 이루어진다. 할당 가능한 빈 공간을 탐색해야 하고 단편화(Fragmentation) 관리 등 추가 작업이 필요해 Stack보다 접근이 느리다.
  - 할당/해제가 반복되면서 사용 가능한 메모리가 작은 조각들로 흩어지는 단편화가 발생할 수 있는데, 전체 여유 공간은 충분해도 연속된 큰 블록이 없어 할당에 실패할 수 있다(외부 단편화, 내부 단편화).
  - Java, Python 등은 GC(Garbage Collector)가 더 이상 참조되지 않는(도달 불가능한) 객체를 자동으로 수거하고, C/C++은 개발자가 직접 해제(`free`, `delete`)해야 하며 해제하지 않으면 메모리 누수(Memory Leak)가 발생한다. GC가 있는 언어도 사용이 끝난 객체를 정적 컬렉션이나 리스너 등에서 계속 참조하고 있으면 GC 대상이 되지 않아 논리적인 메모리 누수가 생길 수 있다.
  - Java의 Heap은 일반적으로 Young Generation(Eden, Survivor)과 Old Generation으로 나뉘는데, 대부분의 객체는 금방 소멸한다는 가정(Weak Generational Hypothesis) 하에 Young 영역을 자주 GC(Minor GC)하고, 오래 살아남은 객체만 Old 영역으로 승격시켜 상대적으로 드물게 GC(Major/Full GC)한다.
- Stack과 Heap의 메모리 성장 방향
  - 일반적으로 Stack은 높은 주소에서 낮은 주소로, Heap은 낮은 주소에서 높은 주소로 성장하도록 설계되어, 두 영역이 서로를 향해 자라며 가운데 빈 공간을 공유한다.

## CPU 스케줄링
- CPU 스케줄링이란?
  - 여러 프로세스가 CPU 자원을 효율적으로 사용할 수 있도록, 어떤 프로세스에게 CPU를 할당할지 결정하는 정책이다.
  - 스케줄링 목표는 CPU 이용률 극대화, 처리량(Throughput) 증가, 대기 시간/응답 시간 최소화, 공평성 보장 등이다.
- 비선점(Non-preemptive) vs 선점(Preemptive) 스케줄링
  - 비선점: 프로세스가 CPU를 할당받으면 스스로 종료하거나 I/O를 요청하기 전까지는 다른 프로세스가 CPU를 빼앗을 수 없다. Context Switching 비용은 적지만 응답성이 떨어져, 응답성보다 처리량이 중요한 배치 처리 환경에 적합하다.
  - 선점: 우선순위가 높은 프로세스가 새로 들어오거나 Time Quantum이 만료되면 실행 중인 프로세스로부터 CPU를 강제로 회수할 수 있다. 응답성은 좋지만 Context Switching 비용이 늘어난다.
- FCFS(First Come First Served)
  - 도착한 순서대로 CPU를 할당하는 비선점 방식이다.
  - 구현이 단순하지만, 실행 시간이 긴 프로세스가 먼저 CPU를 차지하면 뒤따르는 짧은 프로세스들이 모두 대기해야 하는 Convoy Effect(호위 효과)가 발생할 수 있다. SJF나 Round Robin처럼 짧은 작업에 우선권을 주거나 Time Quantum으로 실행 시간을 제한하는 방식으로 완화할 수 있다.
- SJF(Shortest Job First)
  - 실행 시간(버스트 타임)이 가장 짧은 프로세스를 우선 실행하는 방식이다.
  - 평균 대기 시간을 최소화할 수 있지만, 실행 시간이 긴 프로세스는 계속 뒤로 밀려 자원을 할당받지 못하는 Starvation(기아 현상)이 발생할 수 있다.
  - 실행 전에 버스트 타임을 정확히 알기 어렵다는 현실적인 한계도 있다.
- Round Robin
  - 모든 프로세스에게 동일한 Time Quantum(시간 할당량)을 부여하고, 시간이 지나면 다음 프로세스로 순환하며 CPU를 할당하는 선점형 방식이다.
  - 시분할 시스템에 적합하며 응답 시간이 짧아지지만, Time Quantum이 너무 작으면 Context Switching 오버헤드가 커져 처리량이 떨어지고, 너무 크면 FCFS와 비슷해져 응답성이 떨어진다. 일반적으로 대부분의 CPU burst보다 약간 크게 설정하는 것이 권장된다.
- Priority Scheduling
  - 프로세스마다 우선순위를 부여하고, 우선순위가 높은 프로세스부터 CPU를 할당하는 방식이다.
  - 우선순위가 낮은 프로세스는 계속 뒤로 밀려 Starvation이 발생할 수 있는데, 대기 시간이 길어질수록 우선순위를 점진적으로 높여주는 Aging 기법으로 결국 실행될 수 있도록 보장해 해결한다.
- 그 외 알고리즘
  - Multilevel Queue: 프로세스를 우선순위/유형별로 여러 큐로 나누어 각기 다른 스케줄링을 적용하는 방식이다.
  - Multilevel Feedback Queue: Multilevel Queue에서 한 단계 더 나아가, 프로세스가 큐 사이를 이동할 수 있도록 하여 유연성을 높인 방식이다.
  - 멀티코어 환경에서는 코어마다 별도의 Ready Queue를 두는 방식(부하 분산 필요)과 전체 코어가 하나의 큐를 공유하는 방식이 있으며, 코어 간 작업을 옮길 때 캐시 지역성이 깨지는 비용(migration cost)도 함께 고려해야 한다.

## 가상 메모리
- 가상 메모리(Virtual Memory)란?
  - 물리적인 메인 메모리(RAM)의 용량과 상관없이, 프로세스에게 실제보다 크고 연속된 것처럼 보이는 독립적인 주소 공간을 제공하는 메모리 관리 기법이다.
  - 각 프로세스는 독립된 가상 주소 공간을 가지므로 다른 프로세스의 메모리를 침범할 위험이 줄어들어 안정성/보안도 높아지지만, 페이지 테이블 관리 오버헤드나 페이지 폴트로 인한 컨텍스트 스위칭 비용이 발생하고 과도하게 사용하면 스래싱 위험이 있다.
- 페이징(Paging)
  - 가상 메모리와 물리 메모리를 동일한 크기의 블록(가상 메모리는 Page, 물리 메모리는 Frame)으로 나누어 관리하는 기법이다.
  - 프로세스의 논리적 주소를 물리적 주소로 변환하기 위해 페이지 테이블(Page Table)을 사용하며, 이 변환을 빠르게 하기 위해 TLB(Translation Lookaside Buffer)라는 캐시를 활용한다. TLB에 변환 정보가 없으면(TLB Miss) 페이지 테이블을 직접 참조(Page Table Walk)해야 해서 접근 속도가 느려지며, 찾은 결과는 다시 TLB에 캐싱된다.
  - 물리 메모리를 고정 크기로 나누기 때문에 페이지 크기에 딱 맞지 않는 자투리 공간으로 인한 내부 단편화는 발생할 수 있지만 외부 단편화는 발생하지 않는다. 반면 의미 단위(코드, 데이터 등)로 가변 크기 블록을 나누는 세그멘테이션은 내부 단편화는 없지만 외부 단편화가 발생할 수 있다.
- 페이지 폴트(Page Fault)
  - CPU가 접근하려는 페이지가 물리 메모리(RAM)에 적재되어 있지 않을 때 발생하는 예외 상황이다.
  - 페이지 폴트가 발생하면 OS는 해당 페이지를 디스크(Swap 영역)에서 찾아 메모리로 적재(Swap-in)하고, 필요하다면 메모리가 가득 찼을 경우 기존 페이지를 디스크로 내보내는(Swap-out) 과정을 수행한다.
  - 어떤 페이지를 내보낼지 결정하는 페이지 교체 알고리즘에는 FIFO, LRU(Least Recently Used), LFU(Least Frequently Used), Optimal 등이 있다. LRU는 이론적으로는 각 페이지의 마지막 참조 시각을 기록해 가장 오래전에 사용된 페이지를 교체하지만, 오버헤드가 크기 때문에 실제 OS에서는 Reference Bit를 이용한 Clock(Second Chance) 알고리즘 등으로 근사하여 구현한다.
- 스와핑(Swapping)
  - 메모리에 있는 프로세스(또는 페이지)를 디스크의 Swap 영역으로 내보내고, 필요할 때 다시 불러오는 과정이다.
  - 물리 메모리보다 큰 작업을 실행 가능하게 해주지만, 디스크 I/O는 메모리 접근보다 훨씬 느리기 때문에 잦은 스와핑은 성능을 크게 저하시킨다.
- 스래싱(Thrashing)
  - 프로세스가 실제로 필요한 작업 시간보다 페이지 교체(Swapping)에 더 많은 시간을 소비하게 되어, CPU 이용률과 시스템 처리량이 급격히 떨어지는 현상이다.
  - 주로 동시에 실행되는 프로세스 수가 너무 많아 각 프로세스에 할당된 메모리(Working Set)가 부족할 때 발생하며, CPU 이용률은 떨어지는데 페이지 폴트율이 급증하는 패턴으로 감지할 수 있다.
  - 해결 방법으로는 프로세스 수(Multiprogramming Degree)를 줄이거나, 각 프로세스의 Working Set(작업 집합)을 파악해 필요한 만큼의 페이지를 미리 확보해주는 방법 등이 있다.

## 시스템 콜과 커널/사용자 모드
- 사용자 모드와 커널 모드란?
  - CPU가 명령어를 실행할 수 있는 권한 수준을 구분한 것으로, 하드웨어적으로 지원되는 보호 메커니즘이다.
  - 사용자 모드(User Mode): 일반 응용 프로그램이 실행되는 영역으로, 하드웨어에 직접 접근하거나 메모리 보호 영역을 침범하는 등의 제한된 연산은 수행할 수 없다.
  - 커널 모드(Kernel Mode): 운영체제 커널이 실행되는 영역으로, CPU, 메모리, 디스크 등 모든 하드웨어 자원에 직접 접근할 수 있는 특권 모드이다.
  - 사용자 프로세스가 잘못된 접근을 하더라도 커널 영역과 다른 프로세스에 영향을 주지 못하도록 격리함으로써 시스템의 안정성과 보안을 보장한다.
- 시스템 콜(System Call)이란?
  - 사용자 모드에서 실행 중인 프로그램이 커널 모드의 기능(파일 입출력, 프로세스 생성, 네트워크 통신 등)을 사용해야 할 때, 커널에게 요청하기 위해 제공되는 인터페이스이다.
  - 예를 들어 파일을 열기 위한 `open()`, 읽기 위한 `read()`, 프로세스를 생성하는 `fork()`, 네트워크 통신을 위한 `socket()` 등이 시스템 콜에 해당한다.
- 시스템 콜 동작 과정 (모드 전환)
  - 1. 사용자 프로세스가 시스템 콜을 호출하면, 소프트웨어 인터럽트(트랩)가 발생해 CPU 제어권이 커널로 넘어간다.
  - 2. CPU는 사용자 모드에서 커널 모드로 전환되고, 커널은 해당 시스템 콜에 대응하는 커널 함수를 실행한다.
  - 3. 요청된 작업이 끝나면 다시 사용자 모드로 전환되어, 시스템 콜을 호출했던 지점부터 프로세스가 실행을 재개한다.
  - 이 과정에서 레지스터 저장/복원 등 컨텍스트 스위칭과 유사한 오버헤드가 발생하기 때문에, 시스템 콜 호출 횟수가 지나치게 많으면 성능 저하로 이어질 수 있다. (예: 파일을 한 바이트씩 read()하는 대신 버퍼링을 통해 시스템 콜 호출 횟수를 줄이는 것이 일반적이다.)
- strace
  - 리눅스에서 특정 프로세스가 호출하는 시스템 콜을 실시간으로 추적할 수 있는 도구로, 프로세스가 실제로 어떤 시스템 콜을 어떤 순서로 호출하는지 관찰해 디버깅이나 성능 분석에 활용할 수 있다.

## 조건변수와 모니터
- 모니터(Monitor)란?
  - 공유 자원과 이를 다루는 함수(프로시저), 그리고 동기화 메커니즘을 하나의 모듈로 캡슐화한 고수준 동기화 도구이다.
  - 모니터 내부의 함수는 한 번에 하나의 스레드/프로세스만 실행할 수 있도록 자동으로 상호 배제(Mutual Exclusion)가 보장되기 때문에, 개발자가 직접 뮤텍스나 세마포어로 락을 걸고 해제하는 과정을 명시적으로 관리하지 않아도 된다.
  - 자바의 `synchronized` 키워드나 클래스 단위의 동기화도 모니터 개념을 기반으로 구현된 대표적인 예시이다.
- 조건변수(Condition Variable)란?
  - 모니터 내부에서, 특정 조건이 만족될 때까지 스레드를 대기시키고 조건이 만족되면 대기 중인 스레드를 깨우기 위해 사용하는 동기화 도구이다.
  - 단순히 락(상호 배제)만으로는 "자원이 특정 상태가 될 때까지 기다린다"는 요구사항을 표현할 수 없기 때문에, 조건변수와 함께 사용해 이를 해결한다.
- 조건변수의 주요 연산
  - wait(): 조건이 만족되지 않으면 현재 스레드를 대기 상태로 전환하고, 락을 반납한다.
  - signal()(또는 notify()): 해당 조건변수에서 대기 중인 스레드 중 하나를 깨운다.
  - broadcast()(또는 notifyAll()): 대기 중인 모든 스레드를 깨운다.
- 생산자-소비자 문제(Producer-Consumer Problem)
  - 생산자(Producer)는 공유 버퍼에 데이터를 채우고, 소비자(Consumer)는 그 버퍼에서 데이터를 꺼내 쓰는 대표적인 동기화 문제이다.
  - 버퍼가 가득 찼는데 생산자가 계속 데이터를 채우려 하거나, 버퍼가 비어있는데 소비자가 계속 꺼내려고 하면 문제가 발생하므로, 뮤텍스(상호 배제)와 조건변수(버퍼가 가득 참/비어 있음을 알리는 조건)를 함께 사용해 두 조건을 모두 만족시키며 안전하게 동기화한다.

## Copy-on-Write (COW)
- Copy-on-Write란?
  - 여러 프로세스(또는 객체)가 동일한 자원을 공유하다가, 실제로 쓰기(수정) 작업이 발생하는 시점에만 데이터를 복사하는 메모리 최적화 기법이다.
  - 읽기만 하는 동안에는 원본 데이터를 공유해서 불필요한 복사 비용을 줄이고, 쓰기가 필요한 순간에만 실제 복사를 수행해 메모리와 시간을 절약한다.
- fork()와 Copy-on-Write
  - 리눅스에서 `fork()`로 자식 프로세스를 생성할 때, 전통적인 방식이라면 부모 프로세스의 메모리(Code, Data, Heap, Stack)를 통째로 복사해야 하므로 비용이 크다.
  - 현대 운영체제는 `fork()` 시점에는 실제 메모리를 복사하지 않고, 부모와 자식이 동일한 물리 메모리 페이지를 공유하며 페이지 테이블만 별도로 구성해 읽기 전용(Read-only)으로 매핑한다.
  - 이후 부모 또는 자식 중 하나가 해당 페이지에 쓰기 작업을 시도하면, 그 시점에 페이지 폴트가 발생해 해당 페이지만 실제로 복사(Copy)한 뒤 쓰기 작업을 수행한다.
  - 이를 통해 `fork()` 이후 곧바로 `exec()`로 새로운 프로그램을 실행하는 경우처럼, 실제로는 메모리 복사가 필요 없는 상황에서 불필요한 복사 비용을 크게 줄일 수 있다.
- 다른 활용 사례
  - 프로그래밍 언어/런타임에서도 문자열이나 컬렉션 등을 복사할 때, 실제 값이 변경되기 전까지는 참조만 공유하다가 변경 시점에 실제 복사를 수행하는 방식으로 COW를 활용하는 경우가 있다.

## 파일 디스크립터와 파일 시스템
- 파일 디스크립터(File Descriptor)란?
  - 프로세스가 파일이나 소켓 등 입출력 자원에 접근할 때 사용하는, 커널이 관리하는 작은 정수(정수 인덱스)이다.
  - 프로세스가 파일을 열면(`open()`), 커널은 해당 파일에 대한 정보(파일 오프셋, 접근 모드 등)를 담은 파일 테이블 엔트리를 만들고, 프로세스에게는 이를 가리키는 파일 디스크립터 번호를 돌려준다.
  - 리눅스에서는 프로세스가 시작될 때 기본적으로 0(표준 입력, stdin), 1(표준 출력, stdout), 2(표준 에러, stderr)가 미리 할당되어 있다.
  - "리눅스에서는 모든 것이 파일이다(Everything is a file)"라는 철학에 따라, 일반 파일뿐 아니라 디렉터리, 소켓, 파이프, 디바이스 등도 모두 파일 디스크립터로 다뤄진다.
- 하드 링크와 심볼릭 링크
  - 하드 링크(Hard Link): 하나의 실제 데이터(아이노드, inode)를 여러 개의 파일 이름이 함께 가리키는 방식이다. 원본 파일을 삭제해도 다른 하드 링크가 남아있다면 데이터는 유지된다.
  - 심볼릭 링크(Symbolic Link, 소프트 링크): 실제 데이터가 아니라 다른 파일의 경로(Path)를 가리키는 별도의 파일이다. 원본 파일이 삭제되면 심볼릭 링크는 깨진 링크(dangling link)가 된다.
- 파일 시스템이란?
  - 디스크와 같은 저장 장치에 파일과 디렉터리를 어떤 구조로 저장하고 관리할지를 정의하는 운영체제의 하위 시스템이다.
  - 파일의 이름, 위치(데이터 블록), 크기, 권한, 생성/수정 시각 등의 메타데이터를 아이노드(inode)와 같은 자료구조로 관리하며, 디렉터리는 파일 이름과 아이노드 번호를 매핑해주는 특수한 파일로 구현된다.
- 대표적인 파일 시스템 종류
  - ext4: 리눅스에서 널리 사용되는 저널링(Journaling) 파일 시스템으로, 저널을 통해 시스템 장애 시에도 파일 시스템의 일관성을 빠르게 복구할 수 있다.
  - NTFS: 윈도우에서 사용하는 파일 시스템으로, 권한 관리와 저널링을 지원한다.
  - FAT32/exFAT: 구조가 단순해 USB 등 이동식 저장장치에서 널리 사용되지만, 파일 크기나 권한 관리 등에 제약이 있다.

## 프로세스 간 통신(IPC) - 파이프, 공유메모리, 시그널
- IPC(Inter-Process Communication)란?
  - 서로 독립된 메모리 공간을 가지는 프로세스들이 데이터를 주고받거나 동기화하기 위해 사용하는 통신 메커니즘이다.
  - 프로세스는 스레드와 달리 메모리를 공유하지 않기 때문에, 통신을 위해서는 커널의 지원을 받는 별도의 방법이 필요하다.
- 파이프(Pipe)
  - 하나의 프로세스의 출력을 다른 프로세스의 입력으로 연결해주는, 단방향(익명 파이프 기준) 통신 방식이다.
  - 익명 파이프(Anonymous Pipe)는 부모-자식처럼 관련 있는 프로세스 간에만 사용할 수 있고, 이름 있는 파이프(Named Pipe, FIFO)는 파일 시스템에 이름을 가진 형태로 존재해 관련 없는 프로세스 간에도 사용할 수 있다.
  - 구현이 단순하고 사용하기 쉽지만, 기본적으로 단방향 통신이며(양방향이 필요하면 파이프를 두 개 사용) 전송 가능한 데이터 크기에 제한이 있다.
- 공유 메모리(Shared Memory)
  - 커널이 여러 프로세스가 동일한 물리 메모리 영역을 각자의 가상 주소 공간에 매핑해주는 방식으로, IPC 방식 중 가장 빠르다.
  - 커널을 거치지 않고 메모리에 직접 접근하기 때문에 속도는 빠르지만, 여러 프로세스가 동시에 접근할 수 있어 동기화(뮤텍스, 세마포어 등)를 개발자가 직접 처리해야 한다.
- 메시지 큐(Message Queue)
  - 커널이 관리하는 큐에 메시지 형태로 데이터를 주고받는 방식으로, 파이프와 달리 비순차적으로 특정 타입의 메시지만 골라서 읽을 수 있다.
- 소켓(Socket)
  - TCP/IP 기반의 통신 방식으로, 같은 컴퓨터의 프로세스뿐 아니라 네트워크로 연결된 다른 컴퓨터의 프로세스와도 통신할 수 있다.
- 시그널(Signal)
  - 특정 이벤트(예: `Ctrl+C` 입력, 예외 발생, 다른 프로세스의 종료 요청)가 발생했음을 비동기적으로 알리기 위해 커널이 프로세스에게 전달하는 소프트웨어 인터럽트이다.
  - 프로세스는 특정 시그널에 대해 기본 동작을 그대로 따르거나, 시그널 핸들러(Signal Handler)를 등록해 직접 처리 방식을 정의할 수 있다. (단, `SIGKILL`처럼 무시하거나 가로챌 수 없는 시그널도 있다.)
  - 전달할 수 있는 정보가 시그널 번호 정도로 제한적이기 때문에, 대량의 데이터를 주고받기보다는 이벤트 발생을 알리는 용도로 주로 사용된다.

## 컨테이너와 가상화
- 가상화(Virtualization)란?
  - 하나의 물리적인 하드웨어 자원을 논리적으로 분할해, 여러 개의 독립된 실행 환경처럼 사용할 수 있도록 하는 기술이다.
- 하이퍼바이저 기반 가상화(VM, Virtual Machine)
  - 하이퍼바이저(Hypervisor)가 물리 하드웨어 위에서 여러 개의 가상 머신을 실행하며, 각 가상 머신은 독립된 커널을 포함한 전체 운영체제를 가진다.
  - 완전히 독립된 커널을 사용하기 때문에 격리성이 매우 높지만, OS 전체를 부팅하고 자원(디스크, 메모리)을 할당해야 하므로 무겁고 시작 속도가 느리다.
- 컨테이너(Container)란?
  - 호스트 OS의 커널을 여러 컨테이너가 공유하면서, 프로세스/네트워크/파일 시스템 등을 논리적으로 격리해 마치 독립된 서버처럼 보이게 하는 경량 가상화 기술이다.
  - 별도의 커널을 부팅할 필요가 없어 VM보다 훨씬 가볍고 시작 속도가 빠르며, 이미지 크기도 작다.
- 컨테이너 격리를 가능하게 하는 리눅스 커널 기능
  - Namespace: 프로세스가 볼 수 있는 자원(PID, 네트워크, 마운트, 호스트명 등)의 시야를 컨테이너별로 분리해, 컨테이너 안에서는 자신만의 독립된 환경처럼 보이게 한다.
  - cgroups(Control Groups): 컨테이너가 사용할 수 있는 CPU, 메모리, 디스크 I/O 등의 자원 사용량을 제한하고 격리한다.
- VM과 컨테이너 비교
  - VM은 하드웨어 수준까지 가상화하여 커널을 포함한 완전한 OS를 실행하는 반면, 컨테이너는 호스트의 커널을 공유하며 프로세스 수준에서 격리한다.
  - 이 차이 때문에 컨테이너는 VM보다 훨씬 가볍고 빠르게 뜰 수 있지만, 격리 수준은 VM보다 상대적으로 낮다(같은 커널을 공유하므로 커널 취약점에는 함께 영향을 받을 수 있다).
- Docker와 컨테이너
  - Docker는 이러한 컨테이너 기술(Namespace, cgroups)을 활용해, 애플리케이션과 그 실행에 필요한 모든 의존성(라이브러리, 런타임 등)을 하나의 이미지로 패키징하고 실행할 수 있게 해주는 대표적인 컨테이너 플랫폼이다.
  - "내 컴퓨터에서는 잘 되는데" 문제를 해결해, 개발/테스트/운영 환경 간의 일관성을 보장하는 데 널리 활용된다.
