## DDL, DML, DCL, TCL
- DDL (Data Definition Language)
  - 데이터베이스의 구조를 정의할 때 사용하는 언어이다.
  - DDL은 명령어를 입력하는 순간 작업이 즉시 반영(Auto Commit)되기 때문에 사용할 때 주의해야 한다.
  - 종류
    - CREATE : 테이블, 뷰 또는 인덱스와 같은 새 데이터베이스 개체를 생성
    - ALTER : 기존 데이터베이스 개체를 수정
    - DROP : 테이블, 뷰 또는 인덱스와 같은 데이터베이스 개체 삭제
    - TRUNCATE : 테이블의 모든 행을 삭제(DROP과 달리 테이블의 구조와 인덱스는 그대로 유지)
    - RENAME : 기존 데이터베이스 개체의 이름을 변경
- DML (Data Manipulation Language)
  - 데이터베이스 내의 데이터를 조작하는 데 사용하는 언어이다.
  - 종류
    - SELECT : 데이터를 조회하는 명령어
    - INSERT : 데이터를 생성하는 명령어
    - UPDATE : 데이터를 수정하는 명령어
    - DELETE : 데이터를 삭제하는 명령어
- DCL (Data Control Language)
  - 데이터베이스에 접근하고 객체들을 사용하도록 권한을 주고 회수하는 데 사용되는 언어이다.
  - 종류
    - GRANT : 권한 부여
    - REVOKE : 권한을 제한하거나 회수
- TCL (Transaction Control Language)
  - 트랜잭션을 제어하는 명령인 COMMIT, ROLLBACK, SAVEPOINT를 따로 분리해서 TCL이라고 표현하고 있다.
  - 종류
    - COMMIT : 논리적인 작업의 단위를 묶어서 DML에 의해 조작된 결과를 영구적으로 반영
    - ROLLBACK : 논리적인 작업의 단위를 묶어서 DML에 의해 조작된 결과를 작업 이전의 상태로 복구
    - SAVEPOINT : 저장점을 정의하면 롤백할 때 트랜잭션에 포함된 전체 작업을 롤백하는 것이 아니라 현시점에서 SAVEPOINT까지 트랜잭션의 일부만 롤백

## Key의 종류와 특징
- Key란?
  - 데이터베이스에서 조건에 만족하는 튜플을 찾거나 순서대로 정렬할 때 다른 튜플들과 구별할 수 있는 유일한 기준이 되는 속성이다.
- Key의 종류
  - Candidate Key (후보키)
    - 튜플을 유일하게 식별할 수 있는 속성들의 부분 집합
    - 모든 릴레이션은 반드시 하나 이상의 후보키를 가져야 한다.
    - 유일성과 최소성을 만족해야 한다.
      - `유일성 : 하나의 키값으로 튜플을 유일하게 식별할 수 있는 성질` 
      - `최소성 : 키를 구성하는 속성들 중 꼭 필요한 최소한의 속성들로만 키를 구성하는 성질`
  - Primary Key (기본키)
    - 후보키 중에서 선택한 메인이 되는 키
    - Null 값을 가질 수 없다.
    - 동일한 값이 중복될 수 없다.
  - Alternate Key (대체키)
    - 후보키 중 기본키를 제외한 나머지 키
  - Super Key (슈퍼키)
    - 유일성은 만족하지만, 최소성은 만족하지 못하는 키
    - 릴레이션을 구성하는 모든 튜플에 대해 유일성은 만족하지만, 최소성은 만족시키지 못한다.
  - Foreign Key (외래키)
    - 다른 릴레이션의 기본키 또는 유니크(UNIQUE) 제약이 걸린 속성을 참조하는 속성의 집합
    - 외래키는 참조되는 릴레이션의 기본키(또는 유니크 키)와 대응되어 릴레이션 간에 참조 관계를 표현하는데 중요한 도구로 사용된다.
    - 외래키로 지정되면 참조 테이블의 기본키에 없는 값은 입력할 수 없다. (참조 무결성 조건)

## 자연키와 인조키
- 자연키
  - 비즈니스 모델에서 자연스럽게 나오는 속성
  - Ex) 회원 테이블의 사용자ID
- 인조키
  - 비즈니스 모델과 상관없이 오로지 키 역할을 하기 위해 인조적으로 만든 속성
  - Ex) UUID, Auto Increment의 값
- 자연키와 인조키의 특징
  - 자연키는 변할 위험이 존재한다.
    - Ex) 가령 회원 테이블의 자연키를 주민번호로 지정했는데 정책에 따라 주민번호를 저장하지 못하게 된다면 다른 속성으로 변경이 필요하다.
  - 인조키를 사용하면 성능을 향상시킬 수 있다.
    - 자연키를 PK로 사용하는 경우 일반적으로 문자열로 사용할 가능성이 높은데, 문자열을 사용하는 것은 숫자를 사용하는 것보다 느리다.
    - PK의 크기는 작을수록, 원시 타입일수록 성능상 유리하다.

## 이상(Anomaly)
- 이상(Anomaly)이란?
  - 릴레이션에서 일부 속성들의 종속이나 데이터의 중복으로 인해 데이터 조작시 불일치가 발생하는 것을 의미한다.
  - 이상 현상은 정규화(Normalization)를 통해 방지할 수 있다.
- 이상의 종류
  - 삽입 이상(Insertion Anomaly)
    - 불필요한 정보를 함께 저장하지 않고서는 어떤 정보를 저장하는 것이 불가능한 현상.
  - 갱신 이상(Update Anomaly)
    - 데이터 일부만 변경되어, 데이터가 불일치하는 현상.
  - 삭제 이상(Deletion Anomaly)
    - 튜플 삭제로 인하여 꼭 필요한 데이터까지 함께 삭제되는 현상.

## 정규화
- 정규화란?
  - 관계형 데이터베이스의 설계에서 중복을 최소화하기 위하여 데이터를 구조화하는 프로세스를 뜻한다.
  - 삽입, 삭제, 갱신 이상이 있는 관계를 재구성함으로써 바람직한 스키마를 만들 수 있다.
- 정규화의 종류
  - 1NF
    - 모든 도메인이 원자값으로만 구성된다.
    - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/505be8f8-f9ed-4f8c-9e02-2a20d42e7547)
  - 2NF
    - 기본키가 아닌 모든 속성이 기본키에 대하여 완전 함수적 종속을 만족한다.
    - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/8f19a508-0b6e-4746-a161-9036157582de)
  - 3NF
    - 후보키를 제외한 속성들 간에 이행 종속성이 없다.
    - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/5d66af2e-fd92-41b9-831c-95b319523b41)
  - BCNF
    - 모든 결정자가 후보키일 때, 결정자이면서 후보키가 아닌 것을 제거한다.
    - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/5953a132-4eac-48a4-b951-a19a50091c73)
  - 4NF
    - 다치 종속을 제거한다.
  - 5NF
    - 모든 조인 종속이 후보키를 통해서만 성립한다.

## 반정규화(Denormalization)
- 반정규화란?
  - 정규화된 데이터베이스는 데이터 중복을 최소화하고 무결성을 보장하지만, 그만큼 여러 테이블을 JOIN해야 하는 경우가 많아져 조회 성능이 저하될 수 있다.
  - 반정규화는 이러한 조회 성능을 향상시키기 위해, 의도적으로 데이터의 중복을 허용하거나 테이블을 통합/분리하는 것을 뜻한다.
- 정규화와 반정규화의 관계
  - 정규화는 데이터 무결성과 중복 최소화(쓰기 최적화)를, 반정규화는 조회 성능과 개발 편의성(읽기 최적화)을 목적으로 하는 서로 반대되는 방향의 작업이다.
  - 무조건 반정규화가 좋은 것은 아니며, 조회 성능과 데이터 정합성 사이의 트레이드오프를 고려하여 신중하게 적용해야 한다.
- 반정규화 방법
  - 테이블 병합 : 자주 함께 조회되는 테이블을 하나로 합쳐 JOIN을 줄인다.
  - 중복 컬럼 추가 : 자주 JOIN해서 가져오는 컬럼을 참조 테이블에도 중복 저장한다.
  - 파생(계산) 컬럼 추가 : 매번 집계 연산을 하는 대신, 계산된 결과값을 컬럼으로 저장해둔다. (Ex. 게시글의 댓글 수, 주문의 총 금액)
  - 요약 테이블 추가 : 통계성 데이터를 미리 집계해서 별도의 테이블로 관리한다.
- 장점
  - JOIN 횟수와 연산량이 줄어들어 조회 성능이 향상된다.
  - 조회 쿼리가 단순해져 개발 및 유지보수가 쉬워지는 경우가 있다.
- 단점
  - 데이터가 여러 곳에 중복 저장되므로, 값을 변경할 때 모든 곳을 함께 갱신해야 하는 갱신 이상(Update Anomaly)이 발생할 수 있다.
  - 중복 데이터로 인해 저장 공간을 더 많이 차지한다.
  - 데이터 정합성을 유지하기 위한 추가적인 로직(트랜잭션, 배치 등)이 필요해 복잡도가 올라간다.

## JOIN
- JOIN이란?
  - 두 개 이상의 테이블이나 데이터베이스를 연결하여 데이터를 검색하는 행위를 뜻한다.
  - 일반적으로 Primary key 혹은 Foreign key로 두 테이블을 연결한다.
  - 연결하려면 적어도 하나의 칼럼은 서로 공유되고 있어야 한다.
- JOIN의 종류
  - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/13aba6a1-b866-4772-a747-82c49d5e1b07)
  - INNER JOIN
    - 조인 조건이 일치하는 행(교집합)만 반환한다.
    - Ex) `SELECT * FROM A INNER JOIN B ON A.id = B.a_id`
  - LEFT / RIGHT OUTER JOIN
    - 기준이 되는 한쪽 테이블의 모든 행 + 교집합을 반환하며, 매칭되지 않는 반대편 테이블의 컬럼은 NULL로 채워진다.
    - Ex) `SELECT * FROM A LEFT JOIN B ON A.id = B.a_id`
  - FULL OUTER JOIN
    - 합집합
  - CROSS JOIN
    - 모든 경우의 수 (N * M)
  - SELF JOIN
    - 하나의 테이블을 여러번 복사해서 조인

## Transaction
- 트랜잭션이란?
  - 데이터베이스의 상태를 변화시키기 위해서 수행하는 작업의 단위를 뜻한다.
- 트랜잭션 특징
  - 원자성(Atomicity)
    - 트랜잭션이 데이터베이스에 모두 반영되던가, 아니면 전혀 반영되지 않아야 한다.
  - 일관성(Consistency)
    - 트랜잭션의 작업 처리 결과가 항상 일관성이 있어야 한다.
  - 독립성(Isolation)
    - 각각의 트랜잭션은 서로 간섭없이 독립적으로 수행되어야 한다.
  - 지속성(Durability)
    - 트랜잭션이 성공적으로 완료되었을 경우, 결과는 영구적으로 반영되어야 한다.
- 격리수준
  - 레벨 0 (Read Uncommitted)
    - 트랜잭션에서 처리 중인, 아직 커밋 되지 않은 데이터를 다른 트랜잭션에서 읽는 것을 허용한다.
    - Dirty Read, Non-Repeatable Read, Phantom Read 현상이 발생할 수 있다.
      - Dirty Read
        - 다른 트랜잭션에서 커밋되지 않은 변화를 읽음.
        - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/414b1cd4-13ca-4e39-bcff-e091933c00bf)
      - Non-Repeatable Read
        - 같은 데이터를 한 Transaction 에서 읽었음에도 불구하고 값이 달라지는 현상.
        - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/1b7d12af-ef64-4cb8-ac43-17bf55dfcfad)
      - Phantom Read
        - 한 개의 Transaction 에서 같은 조건으로 2번 읽었는데 2 번의 결과가 다른 현상.
        - 없던 데이터가 생기는 현상.
        - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/6bea3fb4-5c29-4335-a542-6f64434f3e55)
  - 레벨 1 (Read Committed)
    - 트랜잭션이 커밋되어 확정된 데이터를 읽는 것을 허용한다.
    - 대부분의 DBMS가 기본 모드로 채택하고 있는 격리수준이다. (단, MySQL(InnoDB)은 REPEATABLE READ를 기본 격리수준으로 채택하고 있다.)
    - Non-Repeatable Read, Phantom Read 현상이 발생할 수 있다.
  - 레벨 2 (Repeatable Read)
    - 선행 트랜잭션이 읽은 데이터는 트랜잭션이 종료될 때까지 후행 트랜잭션이 갱신하거나 삭제하는 것은 불허함으로써 같은 데이터를 두 번 쿼리했을 때 일관성 있는 결과를 리턴한다.
    - Phantom Read 현상이 발생할 수 있다. (단, MySQL InnoDB는 MVCC와 Next-Key Lock을 통해 대부분의 경우 Phantom Read를 방지한다.)
  - 레벨 3 (Serializable Read)
    - 선행 트랜잭션이 읽은 데이터를 후행 트랜잭션이 갱신하거나 삭제하지 못할 뿐만 아니라 중간에 새로운 레코드를 삽입하는 것도 막아준다.
    - 완벽하게 읽기 일관성 모드를 제공한다.
    - 일관성이 높아지지만 데이터를 처리하는 속도가 느려지게 된다.

## MVCC (Multi-Version Concurrency Control)
- MVCC란?
  - 데이터를 변경할 때 기존 데이터를 바로 덮어쓰지 않고, 변경 시점의 버전을 새로 남겨 여러 버전의 데이터를 동시에 관리하는 방식이다.
  - 읽기 작업이 쓰기 작업 때문에 락을 기다리지 않고, 쓰기 작업도 읽기 작업 때문에 락을 기다리지 않도록 하여 동시성을 높이면서도, 각 트랜잭션에게는 일관된 시점의 데이터를 보여줄 수 있다.
- 동작 원리 (MySQL InnoDB 기준)
  - 각 Row는 실제 데이터 외에도 트랜잭션 정보(트랜잭션 ID 등)를 함께 저장하며, Row가 변경될 때마다 이전 버전의 데이터는 Undo Log에 기록된다.
  - 트랜잭션이 데이터를 조회할 때는 현재 최신 데이터를 그대로 읽는 것이 아니라, 자신의 트랜잭션이 시작된 시점(또는 격리 수준에 따른 시점)을 기준으로 스냅샷을 구성하여, 그 시점에 커밋되어 있던 버전의 데이터를 Undo Log를 통해 재구성해서 읽는다.
  - 즉 다른 트랜잭션이 동시에 데이터를 변경(커밋)하고 있더라도, 읽기 작업은 그 변경 작업을 기다리지 않고 자신이 봐야 할 버전의 데이터를 곧바로 읽을 수 있다.
- MVCC와 격리 수준(Isolation Level)
  - Read Committed는 매 조회(SELECT)마다 그 시점의 최신 커밋된 버전으로 스냅샷을 새로 뜨기 때문에, 같은 트랜잭션 내에서도 조회할 때마다 다른 값을 볼 수 있다(Non-Repeatable Read 발생 가능).
  - Repeatable Read는 트랜잭션이 처음 조회를 시작한 시점에 스냅샷을 한 번 고정해두고, 트랜잭션이 끝날 때까지 그 스냅샷을 계속 사용하기 때문에 같은 데이터를 여러 번 조회해도 일관된 결과를 얻을 수 있다.
  - MySQL InnoDB는 Repeatable Read 격리 수준에서 MVCC와 갭 락을 포함한 Next-Key Lock을 함께 사용하여, 표준 SQL 스펙상 발생 가능한 Phantom Read까지도 대부분의 경우 방지한다.
- MVCC의 장점
  - 읽기 작업에 공유 락(Shared Lock)을 걸지 않아도 되므로, 읽기와 쓰기가 서로를 블로킹하지 않아 동시성이 크게 향상된다.
  - 트랜잭션마다 일관된 스냅샷을 볼 수 있어, 락 기반 방식보다 적은 락 경합으로도 읽기 일관성을 보장할 수 있다.
- MVCC의 단점
  - 데이터의 여러 버전을 관리해야 하므로, 변경이 잦은 테이블에서는 Undo Log(버전 정보)가 계속 쌓여 저장 공간을 더 사용하게 된다.
  - 오래된 트랜잭션이 오랫동안 종료되지 않으면, 그 트랜잭션이 참조할 수도 있는 옛 버전의 데이터를 계속 보관해야 하므로 Undo Log가 정리(purge)되지 못하고 계속 쌓이는 문제가 발생할 수 있다.

## Index
- Index란?
  - 테이블에 대한 동작의 속도를 높여주는 자료 구조를 일컫는다.
  - 테이블 내의 1개의 컬럼 혹은 여러 개의 컬럼을 이용하여 생성될 수 있다.
- Index의 장단점
  - 장점
    - 테이블을 조회하는 속도와 그에 따른 성능을 향상시킬 수 있다.
    - 전반적인 시스템의 부하를 줄일 수 있다.
  - 단점
    - 인덱스를 관리하기 위해 DB의 약 10%에 해당하는 저장공간이 필요하다.
    - 인덱스를 관리하기 위해 추가 작업이 필요하다.
    - 인덱스를 잘못 사용하는 경우, 오히려 성능이 저하될 수 있다.
- Index의 자료구조
  - 인덱스를 구현하기 위해서는 다양한 자료구조를 사용할 수 있는데, 가장 대표적으로는 해시 테이블, B-Tree, B+Tree가 존재한다.
    - 해시 테이블(Hash table)
      - 해시 테이블은 키(Key)와 해시 값(Hash Value) 쌍으로 이루어진 자료구조이다.
      - O(1)의 시간복잡도를 가지고 있어 상당히 빠른 검색을 할 수 있는 것이 특징이다.
      - 해시 테이블은 검색 속도가 매우 빠르지만, 데이터의 분포에 따라 충돌이 발생할 수 있다.
      - 해시는 등호(=) 연산에만 특화되어 있어 부등호 연산(>, <)이 자주 사용되는 데이터베이스 검색을 위해서는 해시 테이블이 적합하지 않다.
    - B-Tree
      - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/031b6ec4-396b-4948-8443-84e19cfe5c64)
      - B-Tree는 데이터베이스에서 가장 널리 사용되는 인덱스 자료구조 중 하나이다.
      - O(logN)의 시간 복잡도를 가지고 있다.
      - 이진 트리와는 다르게 하나의 노드에 많은 정보를 가지거나, 두 개 이상의 자식을 가질 수도 있다.
      - B-Tree의 각 노드 내 데이터들은 항상 정렬된 상태인 것이 특징이며, 데이터와 데이터 사이의 범위를 이용하여 자식 노드를 가진다.
      - B-Tree의 경우, 키 값과 데이터 값이 노드 안에 함께 저장되기 때문에 노드 크기가 크고, 디스크 I/O 작업이 많아지는 문제가 있기 때문에 B+Tree 구조를 더 많이 사용한다.
    - B+Tree
      - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/2b18df86-d42c-4e07-a83b-b493d301557c)
      - B+Tree는 B-Tree의 변형된 구조이다.
      - B-Tree는 내부 노드와 리프 노드가 모두 데이터를 가지는 반면에 B+Tree는 리프 노드만 데이터를 가지기 때문에 더 적은 I/O 작업을 필요로 한다.
      - B-Tree와 B+Tree 모두 O(log n)의 시간복잡도를 가지지만, B+Tree가 더 작은 크기의 노드들을 읽어나가기 때문에 리프 노드에 더 빨리 도착할 수 있다.
      - B-Tree는 탐색을 위해서 노드를 찾아서 이동해야 한다는 단점을 가지고 있는데, B+Tree는 이러한 단점을 해소하고자 같은 레벨의 모든 키값들이 정렬되어 있고, 같은 레벨의 Sibling node는 연결 리스트 형태로 이어져 있다. 또한 이 자료들은 연결 리스트로 연결되어 있으므로 탐색에 유리하다.

## 클러스터형 인덱스와 넌클러스터형 인덱스
- 클러스터형 인덱스(Clustered Index)
  - 인덱스의 키 값에 따라 테이블의 데이터 자체가 물리적으로 정렬되어 저장되는 인덱스이다.
  - 인덱스의 리프 노드(Leaf Node)에 데이터 페이지 자체가 저장되어 있어, 인덱스를 찾으면 곧바로 데이터에 도달할 수 있다.
  - 데이터가 물리적으로 하나의 순서로만 정렬될 수 있으므로, 테이블당 1개만 생성할 수 있다.
  - MySQL InnoDB 기준으로 기본키(Primary Key)에 자동으로 생성되며, 기본키가 없으면 UNIQUE 컬럼, 그마저도 없으면 내부적으로 숨겨진 자동 증가 키를 기준으로 클러스터형 인덱스가 생성된다.
- 넌클러스터형 인덱스(Non-Clustered Index)
  - 인덱스와 실제 데이터의 물리적인 저장 순서가 무관한 인덱스이다.
  - 리프 노드에 데이터 자체가 아니라, 데이터의 위치를 가리키는 포인터(또는 클러스터형 인덱스의 키 값)가 저장된다.
  - 한 테이블에 여러 개 생성할 수 있다.
- MySQL InnoDB에서의 동작 방식
  - InnoDB는 PK를 기준으로 한 클러스터형 인덱스(=IOT, Index-Organized Table) 구조를 사용한다.
  - 세컨더리(넌클러스터형) 인덱스의 리프 노드에는 데이터 위치 대신 PK 값이 저장되기 때문에, 세컨더리 인덱스로 조회할 경우 먼저 세컨더리 인덱스에서 PK를 찾은 뒤, 그 PK로 클러스터형 인덱스를 다시 조회하는 과정(2번의 탐색)이 필요할 수 있다. 이를 흔히 '북마크 룩업(Bookmark Lookup)'이라 부른다.
- 장단점 비교
  - 클러스터형 인덱스
    - 장점 : 데이터 접근 시 추가적인 조회 과정 없이 곧바로 데이터에 도달할 수 있어 조회 성능이 좋다. 특히 범위(Range) 검색에 유리하다.
    - 단점 : 데이터 삽입/수정 시 정렬 순서를 유지해야 하므로 페이지 분할(Page Split) 등의 추가 비용이 발생할 수 있으며, 테이블당 1개만 생성 가능하다.
  - 넌클러스터형 인덱스
    - 장점 : 여러 개를 자유롭게 생성할 수 있어 다양한 조회 조건에 대응하기 유리하다.
    - 단점 : 리프 노드에서 실제 데이터로 한 번 더 접근해야 하므로(북마크 룩업), 클러스터형 인덱스보다 조회 성능이 상대적으로 낮을 수 있다.

## 커버링 인덱스(Covering Index)
- 커버링 인덱스란?
  - 쿼리를 처리하는 데 필요한 모든 컬럼(SELECT, WHERE, ORDER BY, GROUP BY 절에서 사용되는 컬럼)이 인덱스 자체에 포함되어 있어서, 실제 데이터 페이지에 접근하지 않고 인덱스만으로 쿼리 결과를 반환할 수 있는 경우를 뜻한다.
  - 인덱스만으로 처리가 끝나기 때문에, 앞서 설명한 넌클러스터형 인덱스의 북마크 룩업(추가 데이터 조회) 과정을 생략할 수 있다.
- 예시
  - `user` 테이블에 `(name, age)` 복합 인덱스가 있다고 가정할 때, 다음 쿼리는 인덱스에 포함된 컬럼만으로 결과를 만들 수 있어 커버링 인덱스로 동작한다.
    - `SELECT name, age FROM user WHERE name = 'choi'`
  - 반면 `SELECT name, age, email FROM user WHERE name = 'choi'`처럼 인덱스에 없는 `email` 컬럼을 조회하면, 커버링 인덱스가 아니게 되어 실제 데이터 페이지 조회가 추가로 발생한다.
- 장점
  - 데이터 페이지에 접근하는 디스크 I/O가 줄어들어 쿼리 성능이 향상된다.
  - 인덱스는 일반적으로 전체 데이터보다 크기가 작기 때문에, 메모리(버퍼 풀)에 캐싱되어 있을 가능성이 높아 성능상 이점이 크다.
- 단점
  - 커버링 인덱스를 만들기 위해 인덱스에 포함하는 컬럼 수가 늘어나면, 인덱스 자체의 크기가 커지고 저장 공간을 더 많이 차지한다.
  - 인덱스 컬럼이 많아질수록 데이터 삽입/수정/삭제 시 인덱스를 갱신하는 비용(쓰기 성능 저하)도 함께 증가한다.

## 페이지네이션(Pagination) - Offset 기반 vs Cursor 기반
- 페이지네이션이란?
  - 대량의 데이터를 한 번에 모두 조회하지 않고, 일정한 단위(페이지)로 나누어 조회하는 방식이다.
  - 데이터베이스와 애플리케이션 서버의 부하를 줄이고, 클라이언트가 필요한 만큼만 데이터를 받아 응답 속도를 높이기 위해 사용한다.
- Offset 기반 페이지네이션
  - `LIMIT`과 `OFFSET`을 사용하여, 몇 번째 데이터부터 몇 개를 가져올지 지정하는 방식이다. (예: `SELECT * FROM posts ORDER BY id DESC LIMIT 10 OFFSET 100`)
  - 특정 페이지 번호로 바로 이동하기 쉽고 구현이 단순하다는 장점이 있다.
  - 단점
    - `OFFSET`이 커질수록 데이터베이스는 건너뛸 행까지 모두 읽은 뒤에 버려야 하므로, 뒷 페이지로 갈수록 조회 성능이 선형적으로 느려진다.
    - 조회하는 도중 데이터가 추가되거나 삭제되면, 페이지 사이에 순서가 밀리면서 동일한 데이터가 중복으로 조회되거나 특정 데이터가 누락되는 정합성 문제가 발생할 수 있다.
- Cursor 기반 페이지네이션
  - 이전 페이지의 마지막 데이터를 기준(커서, 주로 정렬 기준이 되는 컬럼의 값)으로 삼아, 그 다음 데이터부터 조회하는 방식이다. (예: `SELECT * FROM posts WHERE id < 100 ORDER BY id DESC LIMIT 10`)
  - `OFFSET`처럼 앞의 데이터를 건너뛸 필요 없이, 인덱스를 통해 커서 위치를 바로 찾아 그 다음 데이터를 조회하므로 페이지가 뒤로 갈수록 성능이 저하되는 문제가 없다.
  - 데이터가 중간에 추가/삭제되더라도, 커서 값을 기준으로 다음 데이터를 조회하기 때문에 Offset 방식에서 발생하는 데이터 중복/누락 문제에서 비교적 자유롭다.
  - 단점
    - 특정 페이지 번호로 바로 이동(예: "10페이지로 이동")하는 것이 불가능하거나 까다로우며, 순차적으로 다음 페이지를 조회하는 방식(무한 스크롤 등)에 적합하다.
    - 커서로 사용하는 컬럼에 반드시 인덱스가 설정되어 있어야 하며, 정렬 기준이 여러 컬럼일 경우(예: 동점 데이터 처리) 커서 로직이 복잡해질 수 있다.
- 언제 어떤 방식을 선택하는가?
  - 관리자 페이지처럼 특정 페이지 번호로 바로 이동해야 하거나 전체 페이지 수를 보여줘야 하는 경우에는 Offset 기반이 적합하다.
  - SNS 피드나 무한 스크롤처럼 순차적으로 다음 데이터만 불러오면 되고, 데이터 양이 많아 뒷 페이지 성능 저하가 문제가 될 수 있는 경우에는 Cursor 기반이 적합하다.

## SQL vs NoSQL

  - 관계형 데이터베이스.

  - 비관계형 데이터베이스.
  - 반정형화, 비정형화된 데이터에 적합하다.
  - 대용량의 데이터 저장에 유리하다.

## 파티셔닝(Partitioning)
- 파티셔닝(Partitioning)이란?
  - 테이블 또는 인덱스 데이터를 파티션(Partition) 단위로 나누어 저장하는 것을 말한다.
  - '파티셔닝(Partitioning)' 기법을 통해 소프트웨어적으로 데이터베이스를 분산 처리하여 성능이 저하되는 것을 방지하고 관리를 보다 수월하게 할 수 있게 되었다.
- 파티셔닝의 목적
  - 성능(Performance)
    - 특정 DML과 Query의 성능을 향상시킨다.
    - 주로 대용량 Data WRITE 환경에서 효율적이다.
    - 특히, Full Scan에서 데이터 Access의 범위를 줄여 성능 향상을 가져온다.
  - 가용성(Availability)
    - 물리적인 파티셔닝으로 인해 전체 데이터의 훼손 가능성이 줄어들고 데이터 가용성이 향상된다.
    - 각 분할 영역(partition)별로 독립적으로 백업하고 복구할 수 있다.
    - table의 partition 단위로 Disk I/O을 분산하여 경합을 줄이기 때문에 UPDATE 성능을 향상시킨다.
  - 관리용이성(Manageability)
    - 큰 table들을 제거하여 관리를 쉽게 해준다.
- 장단점
  - 장점
    - 전체 데이터를 손실할 가능성이 줄어들어 데이터 가용성이 향상된다.
    - partition별로 백업 및 복구가 가능하다.
    - partition 단위로 I/O 분산이 가능하여 UPDATE 성능을 향상시킨다.
    - 데이터 전체 검색 시 필요한 부분만 탐색해 성능이 증가한다. 즉, Full Scan에서 데이터 Access의 범위를 줄여 성능 향상을 가져온다.
    - 필요한 데이터만 빠르게 조회할 수 있기 때문에 쿼리 자체가 가볍다.
  - 단점
    - table간 JOIN에 대한 비용이 증가한다.
    - table과 index를 별도로 파티셔닝할 수 없다.
- 파티셔닝의 종류
  - 수평 파티셔닝
    - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/264c805b-cf30-4914-8c25-1e96e67a66de)
    - 하나의 테이블의 각 행을 다른 테이블에 분산시키는 것이다.
    - 퍼포먼스, 가용성을 위해 KEY 기반으로 여러 곳에 분산 저장한다.
    - 일반적으로 분산 저장 기술에서 파티셔닝은 수평 분할을 의미한다.
    - 보통 수평 분할을 한다고 했을 때는 하나의 데이터베이스 안에서 이루어지는 경우를 지칭한다.
    - 장단점
      - 장점
        - 데이터의 개수가 작아지고 따라서 인덱스의 개수도 작아지게 된다. 자연스럽게 성능은 향상된다.
      - 단점
        - 서버간의 연결과정이 많아진다.
        - 데이터를 찾는 과정이 기존보다 복잡하기 때문에 latency가 증가하게 된다.
        - 하나의 서버가 고장나게 되면 데이터의 무결성이 깨질 수 있다.
  - 수직 파티셔닝
    - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/ce48933f-b0a3-4776-994f-5ae747420c2b)
    - 테이블의 일부 열을 빼내는 형태로 분할한다. 정규화도 수직 파티셔닝과 관련된 과정이라고 할 수 있다.
    - 수직 파티셔닝은 이미 정규화된 데이터를 분리하는 과정이라고 생각해야 한다.
    - 관계형 DB에서 3정규화와 같은 개념으로 접근하면 이해하기 쉽다.
    - 장단점
      - 장점
        - 자주 사용하는 컬럼 등을 분리시켜 성능을 향상시킬 수 있다.
        - 한 테이블을 SELECT하면 결국 모든 컬럼을 메모리에 올리게 되므로 필요없는 컬럼까지 올라가서 한 번에 읽을 수 있는 ROW가 줄어든다. 이는 I/O 측면에서 봤을 때 필요한 컬럼만 올리면 훨씬 많은 수의 ROW를 메모리에 올릴 수 있으니 성능상의 이점이 있다.
        - 같은 타입의 데이터가 저장되기 때문에 저장 시 데이터 압축률을 높일 수 있다.
      - 단점
        - 데이터를 찾는 과정이 기존보다 복잡하므로 Latency가 증가한다.

## Sharding
- Sharding이란?
  - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/e39102a1-6262-489c-bc22-5cd31cf8e3d0)
  - 샤딩은 각 DB 서버에서 데이터를 분할하여 저장하는 방식이다.
  - 샤딩(Sharding)은 DB 트래픽을 분산할 수 있는 중요한 수단이다.
- 파티셔닝과 샤딩의 관계
  - 샤딩은 수평 파티셔닝의 일종으로 볼 수 있다.
  - 그러나 수평적 파티셔닝은 동일한 DB 서버 내에서 테이블을 분할하는 것이고 샤딩은 DB 서버를 분할한다는 것이다.
- 장단점
  - 장점
    - Scale-Out이 가능하다.
    - 스캔 범위를 줄여서 쿼리 속도를 높일 수 있다.
    - 장애가 샤드 단위로 발생한다.
  - 단점
    - 프로그래밍 복잡도가 증가한다.
    - 데이터가 한쪽 샤드로 몰릴 경우, 샤딩이 무의미 해진다.
- 샤딩의 종류
  - 모듈러 샤딩(Modular Sharding)
    - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/de822d3c-6a63-4b7e-a397-feaf8d6100bf)
    - 모듈러 샤딩(Modular Sharding)은 PK를 모듈러 연산한 결과로 DB를 라우팅하는 방식이다.
  - 레인지 샤딩(Range Sharding)
    - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/8145d02a-f5ad-431a-bf37-4f9e47184c4d)
    - 레인지 샤딩(Range Sharding)은 PK의 범위를 기준으로 DB를 특정하는 방식이다.
  - 디렉토리 샤딩(Directory Sharding)
    - ![image](https://github.com/1992choi/today-i-learned/assets/27760576/b95d1c1a-80fd-403d-9fb8-ef4e616f9ba9)
    - 디렉토리 샤딩(Directory Based Sharding)은 별도의 조회 테이블을 사용해서 샤딩을 하는 방식이다.

## Replication (복제)
- Replication이란?
  - 하나의 데이터베이스(Master/Primary)에 저장된 데이터를 하나 이상의 다른 데이터베이스(Slave/Replica)에 복제하여 동일한 데이터를 유지하는 기술이다.
  - 데이터의 가용성을 높이고, 읽기 트래픽을 분산시켜 성능을 향상시키기 위한 목적으로 주로 사용된다.
- Master-Slave 구조
  - Master(Primary)는 모든 쓰기(INSERT/UPDATE/DELETE) 요청을 처리하고, 변경 사항을 Slave(Replica)에게 전파한다.
  - Slave는 Master로부터 전달받은 변경 사항을 반영하며, 일반적으로 읽기(SELECT) 요청만 처리한다.
  - 애플리케이션(또는 프록시, 로드밸런서 등)에서 쓰기는 Master로, 읽기는 Slave로 트래픽을 분리하는 것을 Read/Write Splitting(읽기/쓰기 분리)이라고 한다.
  - Master 장애 시 Slave 중 하나를 새로운 Master로 승격시키는 Failover를 통해 가용성을 확보할 수 있다.
- 복제 방식
  - 동기 복제(Synchronous Replication) : Master는 Slave가 변경 사항을 모두 반영했다는 응답을 받은 후에야 트랜잭션 커밋을 완료로 처리한다. 데이터 정합성은 보장되지만, Slave의 응답을 기다려야 하므로 쓰기 성능이 저하된다.
  - 비동기 복제(Asynchronous Replication) : Master는 Slave의 반영 여부와 상관없이 자체적으로 트랜잭션을 커밋하고, 변경 사항은 이후 별도로 Slave에 전파된다. 쓰기 성능은 좋지만, Master에 장애가 발생하면 아직 Slave에 전파되지 않은 데이터가 유실될 수 있다.
  - 대부분의 RDBMS(MySQL 등)는 기본적으로 비동기 복제를 사용하며, 정합성이 중요한 경우 준동기(Semi-Synchronous) 복제 등을 절충안으로 사용하기도 한다.
- Replication Lag(복제 지연)
  - 비동기 복제 환경에서는 Master에 반영된 변경 사항이 Slave에 전파되기까지 시간차가 발생할 수 있는데, 이를 복제 지연(Replication Lag)이라고 한다.
  - 데이터를 쓴 직후 바로 같은 데이터를 Slave에서 조회하면, 아직 복제가 반영되지 않아 이전 데이터를 읽게 되는 문제가 발생할 수 있다. (예: 회원가입 직후 바로 마이페이지를 조회했는데 정보가 안 보이는 경우)
  - 이런 문제를 완화하기 위해 쓰기 직후의 조회는 Master에서 처리하도록 라우팅하거나, 복제 지연 정도를 모니터링하여 지연이 심한 Slave는 트래픽에서 제외하는 방법 등을 사용한다.
- Replication과 Sharding/Partitioning의 차이
  - Replication은 동일한 데이터의 복사본을 여러 서버에 두어 가용성과 읽기 성능을 높이는 것이 목적이고, Sharding/Partitioning은 서로 다른 데이터를 여러 서버(또는 물리적 단위)로 나누어 저장해 쓰기 처리량과 저장 용량을 확장하는 것이 목적이다.
  - 실제 대규모 시스템에서는 Sharding으로 데이터를 나눈 뒤, 각 샤드마다 다시 Replication을 적용해 가용성까지 함께 확보하는 방식이 흔히 사용된다.

## DB Lock
- DB Lock
  - Database에 동시 접근이 일어난다면 데이터가 오염될 가능성이 있기 때문에, 데이터의 일관성과 무결성을 유지하기 위해 Lock을 사용한다.
- Lock의 종류
  - Shared Lock(공유락, Read Lock)
    - 공유락은 데이터를 읽을 때 사용하는 Lock이다.
    - Read Lock 끼리는 데이터의 일관성과 무결성을 해치지 않기 때문에 동시에 접근이 가능하다.
    - 만약 특정 데이터에 Shared Lock 이 걸려있다면, 아래 Exclusive Lock을 걸 수 없고, 여러 Shared Lock은 동시에 적용될 수 있다.
  - Exclusive Lock(배타락, Write Lock)
    - 배타락은 데이터를 변경할 때 사용하는 Lock이다.
    - 하나의 트랜잭션이 완료될 때까지 유지되며, 배타락이 끝날 때까지 어떠한 접근도 허용되지 않는다.
    - Exclusive Lock이 걸리면 Shared Lock을 걸 수 없다.
    - Exclusive 상태의 데이터에 대해 다른 트랜잭션이 Exclusive Lock을 걸 수 없다.
- Lock 단위
  - Row Level
    - Row에만 락을 설정한다.
    - 가장 많이 사용되는 Lock이다.
  - Page Level
    - Row가 담긴 Page 에만 락을 설정한다.
    - 같은 페이지에 존재하는 모든 Row는 모두 잠긴다.
  - Table Level
    - Table 과 Index 모두에 락을 설정한다.
    - 전체 테이블에 대한 데이터 변경이 있을 경우 사용한다.
    - 테이블을 제어하는 DDL 구문을 사용할 때 Lock이 걸린다고 하여, DDL Lock 이라고도 한다.
  - Database Level
    - Database의 복구나 스키마 변경 시 락을 설정한다.
    - 1개의 세션이 하나의 Database의 데이터에 접근할 수 있다.
    - DB 전체에 영향이 있는 DB 업데이트와 같은 작업에만 사용한다.
  - Column Level
    - 컬럼 기준으로 Lock이 걸린다.
    - Lock 설정 및 해제에 리소스가 많이 들어 잘 사용하지 않는다.
- 블로킹(Blocking)
  - Lock 간의 경합(Race Condition)이 발생하여 특정 Transaction이 작업을 진행하지 못하고 멈춰선 상태를 말한다.
  - 공유락끼리는 블로킹이 발생하지 않지만, 배타락은 블로킹을 발생시킨다.
  - (Shared Lock + Exclusive Lock) 또는 (Exclusive Lock + Exclusive Lock) 끼리 블로킹이 발생할 수 있다.
  - 해결방안
    - SQL문이 빠르게 수행될 수 있도록 리팩토링한다.
    - 트랜잭션을 가능한 짧게 정의하여 경합을 줄인다.
    - 동일한 데이터를 동시에 변경하지 않도록 설계한다.
    - LOCK_TIMEOUT을 설정하여 해당 Lock의 최대시간을 조정한다.
- 교착상태(DeadLock)
  - 교착상태는 두 트랜잭션이 각각 Lock을 설정하고 서로의 Lock에 접근하여 값을 얻어오려고 할 때, 이미 각각의 트랜잭션에 의해 Lock이 설정되어 있기 때문에 양쪽 트랜잭션 모두 영원히 처리가 되지 않게 되는 상태를 뜻한다.
  - 발생상황
    - Shared Lock + Exclusive Lock
      - 트랜잭션 A가 Shared Lock을 설정하고 sleep 되었을 때, 트랜잭션 B가 해당 데이터에 Exclusive Lock을 걸려고 하면 무기한 기다려야 하는 교착상태에 빠진다.
    - Exclusive Lock + Exclusive Lock
      - 트랜잭션 A에서 Exclusive Lock을 걸었을 때 트랜잭션 B에서도 다른 데이터에 Exclusive Lock을 걸었을 경우 서로의 Lock된 데이터에 접근하려고 할 때 기존의 Lock이 해제될 때까지 기다리게 된다.
  - 해결방안
    - Dead Lock이 감지되면 둘 중 하나의 트랜잭션을 강제 종료한다.
    - Dead Lock 방지를 위해 접근 순서를 동일하게 하는 것이 중요하다.

## 뷰(View)
- 뷰(View)란?
  - 하나 이상의 테이블에서 원하는 데이터를 조회하는 SELECT 쿼리를 저장해두고, 마치 하나의 가상 테이블처럼 사용할 수 있도록 만든 데이터베이스 객체이다.
  - 실제 데이터를 저장하지 않고, 조회할 때마다 정의된 SELECT 문이 실행되어 결과를 보여준다.
- 뷰의 특징
  - 실제 테이블처럼 SELECT 문에서 사용할 수 있지만, 물리적으로 데이터를 저장하지 않으므로 저장 공간을 거의 차지하지 않는다.
  - 자주 사용하는 복잡한 JOIN이나 서브쿼리를 뷰로 만들어두면, 이후에는 단순한 `SELECT * FROM view_name` 형태로 조회할 수 있어 쿼리가 단순해지고 재사용성이 높아진다.
  - 특정 컬럼이나 행만 노출시켜, 민감한 컬럼(급여, 주민번호 등)을 감추고 필요한 정보만 제공하는 보안 목적으로도 활용할 수 있다.
- 뷰의 장단점
  - 장점
    - 복잡한 쿼리를 단순화하여 재사용할 수 있다.
    - 특정 사용자에게 필요한 컬럼/행만 노출시켜 보안성을 높일 수 있다.
    - 원본 테이블 구조가 일부 변경되어도 뷰의 정의만 수정하면 되므로, 뷰를 참조하는 애플리케이션 코드는 영향을 덜 받는 논리적 독립성을 제공한다.
  - 단점
    - 뷰 자체에는 인덱스를 생성할 수 없어(MySQL 기준), 뷰 내부에서 참조하는 원본 테이블과 쿼리의 성능에 그대로 의존한다.
    - 뷰를 여러 겹 중첩해서 사용하면 실행 계획이 복잡해지고, 성능 저하나 디버깅 어려움으로 이어질 수 있다.
    - 뷰를 통한 데이터 변경(INSERT/UPDATE/DELETE)은 제약이 많다. 단일 테이블 기반의 단순한 뷰는 가능하지만, JOIN이나 집계 함수가 포함된 뷰는 대부분 변경이 불가능하다.
- 구체화된 뷰(Materialized View)와의 차이
  - 일반 뷰는 조회할 때마다 SELECT 쿼리를 다시 실행하는 반면, 구체화된 뷰는 쿼리 결과를 실제로 디스크에 저장해두고 주기적으로 갱신한다.
  - 조회 성능은 구체화된 뷰가 훨씬 빠르지만, 데이터가 실시간으로 반영되지 않고(갱신 주기에 의존) 저장 공간을 추가로 사용한다는 단점이 있다. (MySQL은 기본적으로 Materialized View를 지원하지 않아, 트리거나 배치로 유사하게 구현하기도 한다.)

## Redis
- Redis란?
  - Remote Dictionary Server의 약자로, 데이터를 메모리(RAM)에 저장하는 인메모리 Key-Value 저장소이다.
  - 디스크가 아닌 메모리에 데이터를 저장하기 때문에 매우 빠른 응답 속도를 제공하며, 캐시, 세션 저장소, 메시지 브로커, 분산 락 등 다양한 용도로 사용된다.
- Redis의 주요 특징
  - 인메모리 기반: 디스크 I/O 없이 메모리에서 데이터를 읽고 쓰기 때문에, 디스크 기반의 RDBMS보다 훨씬 빠른 응답 속도를 제공한다.
  - 싱글 스레드: 명령어 처리를 기본적으로 싱글 스레드로 수행하기 때문에, 별도의 락 없이도 각 명령어가 원자적(Atomic)으로 실행되는 것을 보장할 수 있고 Context Switching 오버헤드도 없다. (Redis 6.0부터 네트워크 I/O 등 일부 작업에는 멀티스레드를 활용하지만, 실제 명령어 실행 자체는 여전히 싱글 스레드다.)
  - 다양한 자료구조 지원: String, List, Set, Sorted Set(ZSet), Hash 등 여러 자료구조를 기본으로 지원해, 단순 캐시 외에도 랭킹 시스템(Sorted Set), 중복 제거(Set) 등 다양한 용도로 활용할 수 있다.
  - 영속성(Persistence): 기본적으로는 인메모리라 서버가 꺼지면 데이터가 사라지지만, RDB(특정 시점 스냅샷 방식)와 AOF(Append Only File, 명령어 로그 방식) 두 가지 방식으로 데이터를 디스크에 저장해 장애 복구가 가능하다.
- 활용 사례
  - 캐시(Cache): DB 조회 결과를 캐싱해 반복적인 쿼리 부하를 줄인다.
  - 세션 저장소(Session Store): 여러 WAS(Web Application Server)가 세션을 공유해야 할 때, 특정 서버 메모리 대신 Redis에 세션을 저장해 서버 간 세션 불일치 문제를 해결한다.
  - 분산 락(Distributed Lock): 여러 서버(프로세스)가 동시에 같은 자원에 접근하는 것을 막기 위해 `SETNX` 등을 활용해 락을 구현한다.
  - 실시간 랭킹/순위: Sorted Set의 정렬된 특성을 이용해 실시간 랭킹 보드를 구현한다.
  - Pub/Sub 메시징: 간단한 메시지 발행/구독 기반의 실시간 통신에 사용한다.
- Redis와 Memcached 비교
  - Memcached는 단순 문자열 Key-Value만 지원하는 반면, Redis는 다양한 자료구조와 영속성, 복제(Replication) 등 더 풍부한 기능을 제공한다.
  - Memcached는 멀티스레드로 동작해 여러 CPU 코어를 활용할 수 있지만, Redis는 싱글 스레드로 동작해 단일 명령어의 원자성 보장이 쉽다는 차이가 있다.

## MongoDB
- MongoDB란?
  - 대표적인 문서 지향(Document-Oriented) NoSQL 데이터베이스로, 데이터를 BSON(Binary JSON) 형태의 문서(Document)로 저장한다.
  - RDBMS의 테이블(Table)은 컬렉션(Collection), 행(Row)은 문서(Document)에 대응된다고 볼 수 있다.
- MongoDB의 특징
  - 스키마리스(Schemaless): 고정된 스키마 없이, 같은 컬렉션 안에서도 문서마다 서로 다른 필드 구조를 가질 수 있어 유연하다. 다만 유연한 만큼 데이터 일관성 관리는 애플리케이션 레벨에서 신경써야 한다.
  - 중첩 문서(Embedded Document): 관계형 DB처럼 JOIN으로 여러 테이블을 연결하는 대신, 연관된 데이터를 하나의 문서 안에 중첩해서 저장할 수 있어 조회 시 JOIN 없이 한 번에 데이터를 가져올 수 있다.
  - 수평 확장(Scale-Out): 샤딩(Sharding)을 기본적으로 지원해, 데이터를 여러 서버에 분산 저장하며 대용량 데이터 처리에 유리하다.
  - Replica Set: 여러 개의 MongoDB 인스턴스가 Primary-Secondary 구조로 데이터를 복제해 가용성을 높이며, Primary 장애 시 Secondary 중 하나가 자동으로 Primary로 승격(Failover)된다.
- 언제 MongoDB(NoSQL)를 선택하는가?
  - 스키마가 자주 변경되거나, 데이터 구조가 명확히 정형화되어 있지 않은 경우.
  - 데이터 간 관계(JOIN)보다 문서 하나로 완결된 조회가 잦은 경우. (예: 상품 상세 정보, 로그 데이터)
  - 트랜잭션의 엄격한 일관성보다는, 대용량 데이터에 대한 확장성과 쓰기 처리량이 더 중요한 경우.
  - 반대로 데이터 간의 관계가 복잡하고 강한 일관성(트랜잭션)이 중요한 경우(예: 금융 거래)에는 RDBMS가 더 적합하다.
- MongoDB의 트랜잭션 지원
  - 과거에는 단일 문서에 대해서만 원자성을 보장했지만, MongoDB 4.0 이후부터는 여러 문서/컬렉션에 걸친 멀티 도큐먼트 트랜잭션도 지원한다. 다만 RDBMS만큼 널리 사용되는 방식은 아니며, 성능 오버헤드를 고려해 꼭 필요한 경우에만 사용하는 것이 권장된다.

## 실행 계획(Execution Plan)과 옵티마이저
- 옵티마이저(Optimizer)란?
  - SQL이 실행되기 전, 동일한 결과를 만들어낼 수 있는 여러 실행 방법(어떤 인덱스를 사용할지, 테이블을 어떤 순서로 조인할지 등) 중에서 통계 정보를 바탕으로 가장 비용이 적게 드는 방법을 선택하는 DBMS의 구성 요소이다.
  - 대부분의 DBMS는 비용 기반 옵티마이저(CBO, Cost-Based Optimizer)를 사용하며, 테이블의 행 수, 인덱스의 카디널리티(Cardinality) 등의 통계 정보를 기반으로 예상 비용을 계산한다.
- 실행 계획(Execution Plan)이란?
  - 옵티마이저가 선택한, SQL을 실제로 처리하는 절차를 보여주는 정보이다. `EXPLAIN` 명령어를 통해 쿼리를 실제로 실행하지 않고도 확인할 수 있다.
  - 어떤 테이블에 접근하는 순서인지, 인덱스를 사용하는지(사용한다면 어떤 인덱스인지), 예상되는 조회 행 수는 얼마인지 등을 파악할 수 있어 쿼리 튜닝의 출발점이 된다.
- 주요 확인 항목 (MySQL 기준)
  - `type` : 테이블에 접근하는 방식을 나타내며, `const`/`eq_ref`/`ref`/`range`/`index`/`ALL` 순으로 성능이 좋다. `ALL`은 인덱스를 전혀 사용하지 못하고 전체 테이블을 스캔(Full Table Scan)한다는 의미이다.
  - `key` : 실제로 사용된 인덱스를 나타낸다. 의도한 인덱스가 사용되지 않았다면 쿼리나 인덱스 설계를 재검토해야 한다.
  - `rows` : 옵티마이저가 예상한, 쿼리를 처리하기 위해 조사해야 할 행 수이다. 이 값이 실제 테이블 크기에 비해 과도하게 크다면 비효율적인 실행 계획일 가능성이 높다.
  - `Extra` : `Using filesort`(인덱스를 사용하지 못해 별도의 정렬 작업이 필요함), `Using temporary`(임시 테이블을 생성해야 함) 등 추가적인 처리 정보가 표시되며, 성능에 부정적인 신호인 경우가 많다.

## 인덱스를 타지 못하는 경우와 복합 인덱스 설계
- 인덱스를 타지 못하는 대표적인 경우
  - 인덱스가 설정된 컬럼에 가공(함수, 연산)을 가한 경우 : `WHERE YEAR(created_at) = 2024`처럼 컬럼에 함수를 적용하면, 인덱스에 저장된 원본 값과 비교할 수 없어 인덱스를 타지 못한다. (`WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'`처럼 컬럼은 그대로 두고 비교하는 방식으로 바꿔야 한다.)
  - 타입이 암묵적으로 변환되는 경우 : 문자열 타입 컬럼에 숫자 리터럴로 조건을 걸면(`WHERE phone = 01012345678`) 타입 변환이 발생해 인덱스를 타지 못할 수 있다.
  - LIKE 검색에서 와일드카드(%)가 앞에 오는 경우 : `LIKE '%keyword'`는 인덱스를 활용할 수 없지만, `LIKE 'keyword%'`처럼 뒤에만 오는 경우에는 인덱스 범위 탐색이 가능하다.
  - OR 조건으로 연결된 컬럼 중 일부에만 인덱스가 있는 경우 : 모든 컬럼에 인덱스가 걸려 있지 않다면 OR 조건 전체가 풀스캔으로 처리될 수 있다.
  - 옵티마이저가 판단하기에 조회 대상 데이터가 테이블 전체의 상당 비율을 차지하는 경우 : 인덱스를 통한 접근보다 풀 테이블 스캔이 더 빠르다고 판단되면 인덱스가 존재해도 사용하지 않을 수 있다.
- 복합 인덱스(Composite Index) 설계 원칙
  - 여러 컬럼을 묶어 하나의 인덱스로 구성하는 것을 복합 인덱스라고 하며, 컬럼의 순서가 매우 중요하다.
  - 등호(`=`) 조건으로 자주 사용되고, 카디널리티(값의 분포가 다양한 정도)가 높은 컬럼을 앞쪽에 배치하는 것이 일반적이다. 범위(`>`, `<`, `BETWEEN`) 조건으로 사용되는 컬럼은 뒤쪽에 배치하는데, 범위 조건 컬럼 이후의 컬럼들은 인덱스를 온전히 활용하지 못하기 때문이다.
  - 최좌측 접두 원칙(Leftmost Prefix) : `(A, B, C)` 복합 인덱스는 `(A)`, `(A, B)`, `(A, B, C)` 조합의 조건에서는 인덱스를 사용할 수 있지만, `(B)`나 `(B, C)`처럼 맨 앞 컬럼(A)이 조건에 없는 경우에는 해당 인덱스를 사용할 수 없다.
  - 정렬(ORDER BY)에도 사용될 컬럼이라면 인덱스 컬럼 순서를 정렬 순서와 일치시켜, 인덱스를 이용해 별도의 정렬 작업(Using filesort) 없이 바로 정렬된 결과를 얻을 수 있도록 설계하는 것이 좋다.

## 슬로우 쿼리 튜닝
- 슬로우 쿼리(Slow Query)란?
  - 설정된 임계 시간(예: 1초)보다 오래 걸린 쿼리를 의미하며, MySQL의 경우 `slow_query_log`를 활성화하고 `long_query_time`을 설정하면 슬로우 쿼리를 로그 파일에 기록해준다.
- 슬로우 쿼리 튜닝 절차
  - 1. 슬로우 쿼리 로그나 모니터링 도구(APM 등)를 통해 느린 쿼리를 식별한다.
  - 2. `EXPLAIN`으로 실행 계획을 분석하여, 인덱스를 타지 못하거나(`type = ALL`) 예상 조회 행 수(`rows`)가 비정상적으로 많은 구간을 찾는다.
  - 3. 원인에 따라 인덱스를 추가/수정하거나, 쿼리 자체를 재작성(불필요한 SELECT * 제거, 서브쿼리를 JOIN으로 변경 등)한다.
  - 4. 변경 후 다시 실행 계획과 실제 실행 시간을 비교하여 개선 효과를 검증한다.
- 대표적인 튜닝 사례
  - 필요한 컬럼만 SELECT하기 : `SELECT *`는 불필요한 컬럼까지 가져와 네트워크/메모리 비용을 늘리고, 커버링 인덱스를 활용할 기회도 놓치게 된다.
  - 페이지네이션 최적화 : 오프셋이 커질수록 성능이 저하되는 OFFSET 기반 페이징 대신, 커서 기반 페이징으로 전환한다.
  - 서브쿼리를 JOIN으로 변경 : 상관 서브쿼리(Correlated Subquery)는 외부 쿼리의 각 행마다 반복 실행되어 느려질 수 있어, 가능하다면 JOIN으로 바꿔 한 번에 처리하는 것이 유리할 수 있다.
  - N+1 문제 해결 : 반복문 안에서 개별 쿼리를 실행하는 대신, Fetch Join이나 IN 절을 활용해 한 번의 쿼리로 묶어서 조회한다.
  - 적절한 인덱스 추가 : WHERE, JOIN, ORDER BY에 자주 사용되는 컬럼에 인덱스를 추가하되, 인덱스가 너무 많아지면 쓰기(INSERT/UPDATE/DELETE) 성능이 저하되므로 꼭 필요한 인덱스만 유지하는 것이 중요하다.

## Redo Log, Undo Log와 WAL
- WAL(Write-Ahead Logging)이란?
  - 데이터 페이지를 직접 디스크에 반영하기 전에, 먼저 로그를 디스크에 기록해두는 방식이다. 데이터 파일을 매번 즉시 디스크에 쓰는 것보다, 순차 기록(append)이 가능한 로그 파일에 먼저 기록하는 편이 훨씬 빠르기 때문에 성능과 안정성을 동시에 확보할 수 있다.
  - 장애(서버 다운 등)가 발생해도, 디스크에 안전하게 기록된 로그를 이용해 데이터를 복구할 수 있다는 것이 핵심 아이디어이다.
- Redo Log란?
  - 커밋된 트랜잭션의 변경 내용을 기록해두는 로그로, 장애 발생 시 아직 데이터 파일에 반영되지 않은 변경 사항을 재적용(Redo)하여 데이터를 복구하는 데 사용된다.
  - MySQL InnoDB는 변경된 데이터 페이지를 매번 즉시 디스크에 쓰지 않고, 먼저 Redo Log에 기록한 뒤 트랜잭션을 커밋 처리한다. 실제 데이터 페이지는 이후 적절한 시점에 모아서 디스크에 반영(Flush)되는데, 이 사이에 장애가 발생해도 Redo Log를 이용해 복구할 수 있다.
- Undo Log란?
  - 트랜잭션이 데이터를 변경하기 전의 이전 값을 기록해두는 로그로, 트랜잭션이 롤백될 때 변경 이전 상태로 되돌리는 데 사용된다.
  - MVCC(다중 버전 동시성 제어)를 구현하는 데에도 활용되는데, 다른 트랜잭션이 특정 시점 기준의 이전 버전 데이터를 읽어야 할 때 Undo Log를 통해 해당 시점의 데이터를 재구성해서 보여준다.
- Redo Log vs Undo Log
  - Redo Log는 "커밋된 변경 사항이 유실되지 않도록" 보장하기 위한 것(지속성, Durability)이고, Undo Log는 "커밋되지 않은 변경 사항을 되돌리기" 위한 것(원자성, Atomicity)과 "다른 트랜잭션에게 일관된 과거 시점 데이터를 보여주기" 위한 것(MVCC)이라는 차이가 있다.

## 캐시 전략 (Look-aside, Write-through, Write-back)
- Look-aside 캐시 (Cache-Aside, Lazy Loading)
  - 애플리케이션이 데이터를 조회할 때, 먼저 캐시를 확인하고 캐시에 데이터가 없으면(Cache Miss) DB에서 조회한 뒤 그 결과를 캐시에 저장하는 방식이다.
  - 실제로 조회된 데이터만 캐시에 저장되므로 캐시 공간을 효율적으로 사용할 수 있지만, 데이터를 변경할 때는 캐시와 DB를 각각 어떻게 갱신할지(쓰기 전략)를 별도로 결정해야 한다.
  - 가장 널리 사용되는 캐싱 패턴으로, 주로 아래 설명할 Write-around 방식과 함께 사용된다.
- Write-through (쓰기 통과)
  - 데이터를 쓸 때 캐시와 DB에 동시에(또는 캐시를 거쳐) 값을 반영하는 방식이다.
  - 캐시와 DB의 데이터가 항상 동기화되어 일관성이 높다는 장점이 있지만, 매 쓰기 연산마다 캐시와 DB에 모두 써야 하므로 쓰기 지연 시간이 늘어난다.
- Write-back (Write-behind, 쓰기 지연)
  - 데이터를 캐시에만 먼저 쓰고, DB에는 나중에 비동기적으로(배치 처리, 일정 주기 등) 반영하는 방식이다.
  - 쓰기 성능이 뛰어나지만, DB에 반영되기 전에 캐시 서버가 장애로 다운되면 아직 반영되지 않은 데이터가 유실될 위험이 있다.
- Write-around
  - 데이터를 쓸 때는 DB에만 반영하고 캐시는 갱신하지 않다가, 이후 해당 데이터가 조회될 때(Cache Miss) 캐시에 적재하는 방식이다.
  - 한 번 쓰고 자주 읽지 않는 데이터에 적합하며, Look-aside 읽기 전략과 함께 사용하면 캐시에는 실제로 자주 조회되는 데이터만 유지될 수 있다.
- 선택 기준
  - 읽기가 훨씬 빈번한 경우에는 Look-aside + Write-around 조합이 일반적이며, 쓰기 직후 곧바로 일관된 데이터를 읽어야 하는 요구사항이 강하다면 Write-through를, 쓰기 성능이 매우 중요하고 약간의 데이터 유실 위험을 감수할 수 있다면 Write-back을 고려한다.

## 저장 프로시저, 함수, 트리거
- 저장 프로시저(Stored Procedure)란?
  - 자주 사용되는 일련의 SQL 로직(여러 쿼리, 조건문, 반복문 등)을 데이터베이스 내부에 이름을 붙여 저장해두고, 필요할 때 호출해서 실행할 수 있도록 만든 객체이다.
  - 애플리케이션에서 여러 번의 쿼리를 주고받는 대신, 한 번의 호출로 DB 내부에서 여러 로직을 한꺼번에 처리할 수 있어 네트워크 왕복(Round-trip) 횟수를 줄일 수 있다.
- 저장 함수(Stored Function)란?
  - 저장 프로시저와 유사하지만, 반드시 하나의 값을 반환해야 하며 SQL 문(SELECT 등) 내부에서 함수처럼 호출해서 사용할 수 있다는 차이가 있다.
- 트리거(Trigger)란?
  - 특정 테이블에 INSERT, UPDATE, DELETE 같은 이벤트가 발생했을 때, 자동으로 실행되도록 등록해둔 로직이다.
  - 예를 들어 특정 테이블에 데이터가 삽입될 때마다 별도의 이력(audit log) 테이블에 자동으로 기록을 남기는 데 활용할 수 있다.
- 장점과 단점
  - 장점 : 반복적인 로직을 DB에 모아두어 중복을 줄일 수 있고, 애플리케이션과 DB 사이의 네트워크 비용을 줄여 성능상 이점을 얻을 수 있는 경우가 있다.
  - 단점 : 비즈니스 로직이 애플리케이션 코드가 아닌 DB에 흩어져 있어 버전 관리, 테스트, 디버깅이 어려워지고, 특정 DBMS 문법에 종속되어 다른 DBMS로 전환하기 어려워진다. 또한 트리거처럼 암묵적으로 실행되는 로직은 코드만 봐서는 동작을 파악하기 어려워 유지보수를 어렵게 만들 수 있다.
  - 이런 이유로 최근에는 비즈니스 로직을 가능한 애플리케이션 레벨에서 관리하고, 저장 프로시저/트리거는 제한적인 용도로만 사용하는 것이 일반적인 추세이다.

## 데이터 타입 선택과 스키마 설계
- 적절한 데이터 타입 선택이 중요한 이유
  - 데이터 타입에 따라 저장 공간, 연산 속도, 인덱스 효율이 달라지기 때문에, 저장할 값의 범위와 특성에 맞는 최소한의 타입을 선택하는 것이 성능과 저장 공간 모두에 유리하다.
- 숫자 타입
  - 저장할 값의 범위에 맞는 가장 작은 정수 타입(TINYINT, SMALLINT, INT, BIGINT 등)을 사용하는 것이 저장 공간과 인덱스 크기 측면에서 유리하다.
  - 금액처럼 정밀한 소수 계산이 필요한 경우에는 부동소수점 타입(FLOAT, DOUBLE) 대신, 정확한 값을 저장할 수 있는 고정 소수점 타입(DECIMAL)을 사용해야 반올림 오차로 인한 금전적 문제를 방지할 수 있다.
- 문자열 타입
  - 길이가 고정적인 값(예: 전화번호, 코드값)은 CHAR를, 길이가 가변적인 값은 VARCHAR를 사용한다. CHAR는 고정 길이이기 때문에 짧은 값이 많은 경우 디스크 I/O 측면에서 유리할 수 있고, VARCHAR는 실제 데이터 길이만큼만 저장해 공간을 절약할 수 있다.
  - TEXT/BLOB처럼 큰 데이터를 저장하는 타입은 인덱스 생성이 제한적이고 조회 성능에도 영향을 줄 수 있어, 꼭 필요한 경우에만 사용하는 것이 좋다.
- 날짜/시간 타입
  - 날짜/시간 정보는 문자열(VARCHAR)로 저장하기보다 DATETIME, TIMESTAMP 등 전용 타입으로 저장해야 날짜 연산, 정렬, 범위 검색에 인덱스를 효율적으로 활용할 수 있다.
  - TIMESTAMP는 내부적으로 UTC로 저장되고 조회 시 세션 타임존에 맞춰 변환되는 반면, DATETIME은 입력한 값 그대로 저장되어 타임존 정보를 고려하지 않는다는 차이가 있다.
- NULL 허용 여부
  - 꼭 필요한 경우가 아니라면 컬럼을 NOT NULL로 설계하는 것이 좋은데, NULL을 허용하는 컬럼은 인덱스 처리와 옵티마이저의 통계 계산을 더 복잡하게 만들 수 있고, 값이 없는 것(NULL)과 빈 값('')을 구분해야 하는 등 애플리케이션 로직도 복잡해질 수 있다.
- 정규화와 반정규화 사이의 균형
  - 스키마를 설계할 때는 데이터 중복과 이상 현상을 줄이기 위한 정규화를 기본으로 하되, 조회 성능이 중요한 부분에서는 의도적인 반정규화(중복 컬럼 추가, 통계 테이블 분리 등)를 함께 고려해 균형을 맞추는 것이 실무에서 널리 쓰이는 접근이다.

## 쓰기 스키마와 읽기 스키마 (Schema-on-write vs Schema-on-read)
- Schema-on-write (쓰기 스키마)
  - 데이터를 쓰기 전에 스키마가 명확히 정의되어 있고, DB가 저장 시점에 그 스키마를 강제하는 방식이다. 전통적인 RDBMS가 대표적이다.
  - 모든 데이터가 동일한 구조를 따른다는 것이 보장되므로 데이터 정합성과 문서화 측면에서 유리하지만, 스키마를 변경하려면 `ALTER TABLE`과 같은 마이그레이션 작업이 필요하고 대용량 테이블에서는 이 작업이 오래 걸리거나 서비스에 영향을 줄 수 있다.
- Schema-on-read (읽기 스키마)
  - 데이터를 쓸 때는 구조를 강제하지 않고, 읽는 쪽 애플리케이션이 데이터의 구조를 해석하는 방식이다. 문서 지향 NoSQL(MongoDB 등)이 대표적이며 "schemaless"라고도 불린다.
  - 정확히는 스키마가 없는 것이 아니라, DB가 스키마를 강제하지 않고 암묵적인 스키마를 애플리케이션 코드가 책임지는 것에 가깝다.
  - 같은 컬렉션 안에서도 레코드마다 필드 구조가 달라도 되므로, 데이터 구조가 자주 바뀌거나 레코드 간 구조가 다양한 경우 유리하다.
- 스키마 변경 시의 차이
  - Schema-on-write 방식에서 필드를 추가/제거하려면 테이블 전체에 대한 마이그레이션이 필요하다.
  - Schema-on-read 방식에서는 새로운 필드를 가진 데이터부터 그냥 쓰면 되고, 기존 레코드는 그대로 둔 채 애플리케이션이 "필드가 없으면 기본값으로 처리" 하는 방식으로 점진적인 변경(마이그레이션 없는 변경)을 할 수 있다.
  - 다만 이 유연함은 데이터 일관성 검증 책임을 DB에서 애플리케이션으로 옮기는 것일 뿐이므로, 구조가 자주 바뀌지 않고 강한 정합성이 중요한 도메인에서는 여전히 Schema-on-write가 더 적합하다.

## 롤링 배포 중 스키마 변경 (Expand-Contract)
- 문제 상황
  - 무중단 배포를 위해 롤링 배포(Rolling Deployment)를 하면, 배포가 진행되는 동안 구버전 코드와 신버전 코드가 동시에 같은 DB에 접근하는 구간이 반드시 발생한다.
  - 이때 스키마를 한 번에 바꿔버리면, 아직 구버전으로 떠있는 서버가 변경된 스키마를 이해하지 못해 장애가 발생할 수 있다. 따라서 스키마 변경은 신버전/구버전 코드 양쪽에서 모두 호환되는 방식으로 단계적으로 이루어져야 한다.
- Expand-Contract 패턴
  - Expand(확장) : 기존 컬럼/필드는 그대로 둔 채, 새로운 컬럼/필드를 추가한다. 이 시점에는 구버전 코드는 새 필드를 몰라도 되고(무시), 신버전 코드는 기존 필드와 새 필드에 동시에 쓰기(Dual Write)를 하여 두 버전이 공존해도 데이터가 깨지지 않도록 한다.
  - Migrate(이행) : 기존 데이터를 새 필드에 맞게 백필(backfill)하고, 모든 서버 인스턴스가 신버전 코드로 완전히 교체될 때까지 기다린다.
  - Contract(축소) : 모든 서버가 신버전으로 전환되어 더 이상 기존 필드를 참조하지 않는 것이 확인되면, 기존 컬럼/필드를 제거하여 스키마를 정리한다.
- 적용 시 고려사항
  - 각 단계 사이에는 충분한 시간(배포 전파 시간 + 모니터링 기간)을 두어야 하며, 되돌림(Rollback)이 필요한 경우를 대비해 Contract 단계는 가장 마지막에, 충분히 안전하다고 확신될 때 수행해야 한다.
  - 이 패턴은 DDIA에서 다루는 전방/후방 호환성(상위/하위 호환성)과 직접적으로 연결된다. 신버전 코드가 구버전이 쓴 데이터를 읽을 수 있어야 하고(하위 호환), 구버전 코드가 신버전이 쓴 데이터를 받아도 깨지지 않아야 한다(상위 호환).

## 저장소 엔진: 로그 구조(LSM 트리)와 B-트리
- 저장소 엔진의 두 계열
  - OLTP 데이터베이스의 저장소 엔진은 크게 로그 구조(Log-Structured, 대표적으로 LSM 트리)와 페이지 지향(Page-Oriented, 대표적으로 B-트리) 두 계열로 나눌 수 있다.
- B-트리 (기존에 정리한 `Index`의 B-Tree/B+Tree 참고)
  - 고정 크기의 페이지(블록) 단위로 데이터를 관리하며, 값을 변경할 때 해당 페이지를 디스크에서 찾아 그 자리에서 덮어쓴다(in-place update).
  - 덮어쓰기 중 장애가 나면 페이지가 손상될 수 있어, 변경 전에 WAL(Write-Ahead Log)에 먼저 기록해두고 복구 시 사용한다.
  - 데이터가 항상 정렬된 상태로 유지되어 범위 검색(Range Scan)에 유리하며, MySQL InnoDB 등 전통적인 RDBMS에서 널리 사용된다.
- LSM 트리 (Log-Structured Merge-Tree)
  - 쓰기가 들어오면 즉시 디스크의 정해진 위치를 찾아 덮어쓰는 대신, 먼저 메모리 내의 정렬된 자료구조(Memtable, 보통 균형 트리)에 추가한다.
  - Memtable이 일정 크기 이상 커지면, 그 내용을 정렬된 상태로 디스크에 통째로 순차 기록(append-only)하여 불변(Immutable) 파일인 SSTable(Sorted String Table)로 만든다.
  - 시간이 지나며 여러 개의 SSTable이 쌓이게 되는데, 백그라운드에서 이들을 주기적으로 병합/정리하는 컴팩션(Compaction) 과정을 거쳐 중복되거나 삭제된 키를 제거하고 파일 개수를 관리한다.
  - 쓰기가 항상 순차 디스크 I/O(append)로 처리되기 때문에 랜덤 쓰기가 많은 B-트리보다 쓰기 처리량이 뛰어나며, Cassandra, RocksDB, LevelDB, HBase 등에서 사용된다.
- 장단점 비교
  - LSM 트리 : 쓰기 성능이 뛰어나고 데이터 압축률이 높지만, 읽기 시 여러 SSTable을 확인해야 할 수 있어(Bloom Filter 등으로 보완) 읽기 성능이 B-트리보다 불리할 수 있고, 컴팩션 과정이 디스크/CPU 자원을 추가로 소모한다.
  - B-트리 : 데이터가 항상 하나의 정렬된 구조로 유지되어 읽기/범위 검색 성능이 안정적이지만, 랜덤 위치에 대한 in-place 쓰기가 많아 쓰기 집약적인 워크로드에서는 상대적으로 불리하다.

## SS테이블, 멤테이블, 컴팩션
- 멤테이블(Memtable)
  - LSM 트리에서 쓰기 요청이 들어오면 가장 먼저 기록되는 메모리 내의 정렬된 자료구조(보통 균형 이진 탐색 트리)이다.
  - 쓰기 직후 바로 메모리에서 조회할 수 있어 최근 쓰기에 대한 읽기 성능이 빠르며, 메모리에만 있으므로 장애 시 유실을 막기 위해 디스크에 순차적으로 기록되는 별도의 쓰기 전용 로그(WAL과 유사한 역할)를 함께 남겨 복구에 사용한다.
- SS테이블(SSTable, Sorted String Table)
  - Memtable이 임계 크기 이상으로 커지면, 그 내용을 키 기준으로 정렬된 상태 그대로 디스크에 순차 기록(append)하여 만드는 불변(Immutable) 파일이다.
  - 파일 내에서 키가 정렬되어 있고 각 키가 단 한 번만 등장하기 때문에, 파일 전체를 메모리에 올리지 않고도 희소 색인(Sparse Index, 일부 키의 오프셋만 메모리에 저장)만으로 원하는 키의 위치를 빠르게 찾을 수 있다.
  - 정렬되어 있다는 특징 덕분에 여러 SSTable을 병합할 때도 각 파일을 순차적으로 읽어가며 합치는 병합 정렬(Merge Sort)과 같은 방식으로 효율적으로 처리할 수 있다.
- 컴팩션(Compaction)
  - 쓰기가 반복될수록 디스크에 SSTable 파일이 계속 늘어나는데, 읽기 시 여러 SSTable을 다 뒤져야 하는 비효율을 줄이기 위해 백그라운드에서 여러 SSTable을 병합하여 더 적은 수의 SSTable로 합치는 과정이다.
  - 병합 과정에서 같은 키에 대해 여러 버전이 존재하면 가장 최신 값만 남기고, 삭제 마커(Tombstone)가 찍힌 키는 완전히 제거하여 공간을 회수한다.
  - 컴팩션 전략으로는 크기 기준으로 비슷한 크기의 SSTable들을 합치는 Size-Tiered Compaction(Cassandra)과, 레벨별로 데이터 범위를 나누어 관리하는 Leveled Compaction(RocksDB, LevelDB)이 대표적이며, 전략에 따라 쓰기 증폭(Write Amplification)과 읽기 성능 사이의 트레이드오프가 달라진다.

## OLTP와 OLAP, 데이터 웨어하우스
- OLTP (Online Transaction Processing)
  - 사용자의 요청에 실시간으로 응답하는 트랜잭션성 업무 처리를 위한 워크로드이다. (예: 주문 생성, 재고 차감)
  - 한 번에 적은 수의 레코드를 다루는 짧은 트랜잭션이 많고, 주로 기본키(Primary Key)를 기준으로 특정 레코드를 빠르게 조회/수정하는 패턴이 대부분이다.
  - 애플리케이션 서비스의 실제 비즈니스 상태를 저장하는 것이 목적이라 최신 데이터, 높은 동시성, 짧은 응답 시간이 중요하다.
- OLAP (Online Analytical Processing)
  - 데이터를 집계/분석하여 비즈니스 인사이트를 얻기 위한 워크로드이다. (예: 지난 달 지역별 매출 합계)
  - 한 번의 쿼리가 수백만~수십억 건의 레코드를 스캔하며, 전체 컬럼이 아닌 일부 컬럼만 집계 연산(SUM, AVG 등)에 사용하는 경우가 많다.
  - 실시간성보다는 처리량(대량의 데이터를 얼마나 빠르게 집계하는지)이 중요하며, 데이터는 보통 배치로 적재된 후 분석된다.
- 데이터 웨어하우스(Data Warehouse)
  - OLTP 데이터베이스는 분석 쿼리(대량 스캔, 복잡한 집계)를 수행하면 트랜잭션 처리 성능에 영향을 줄 수 있기 때문에, 여러 OLTP 시스템의 데이터를 추출(Extract)-변환(Transform)-적재(Load, ETL)하여 분석 전용으로 모아두는 별도의 데이터베이스가 데이터 웨어하우스이다.
  - OLTP와 분리되어 있어 무거운 분석 쿼리가 실제 서비스(OLTP)에 영향을 주지 않으며, 분석에 최적화된 스키마(스타 스키마 등)와 저장 방식(컬럼 지향 저장소 등)을 별도로 사용할 수 있다.
  - 스타 스키마(Star Schema) : 분석 대상이 되는 이벤트를 기록하는 하나의 큰 사실 테이블(Fact Table, 예: 주문 내역)과, 그 이벤트를 설명하는 속성들을 담은 여러 차원 테이블(Dimension Table, 예: 고객, 상품, 날짜)로 구성하는 대표적인 데이터 웨어하우스 모델링 방식이다.

## 컬럼 지향 저장소(Column-oriented Storage)
- 등장 배경
  - 전통적인 행 지향(Row-oriented) 저장소는 한 레코드(행)의 모든 컬럼 값을 디스크상에 연속해서 저장하는데, OLAP처럼 전체 레코드 중 일부 컬럼만 집계하는 쿼리에서는 필요 없는 컬럼까지 함께 디스크에서 읽어오는 비효율이 발생한다.
  - 컬럼 지향 저장소는 행이 아니라 각 컬럼의 값들을 모아서 연속된 공간에 저장하는 방식으로, 특정 컬럼만 필요한 분석 쿼리에서 그 컬럼의 데이터만 읽으면 되므로 디스크 I/O를 크게 줄일 수 있다.
- 압축(Compression)에 유리한 이유
  - 같은 컬럼 안에는 비슷하거나 반복되는 값이 많기 때문에(예: 상태값, 카테고리), 비트맵 인코딩(Bitmap Encoding), 실행 길이 인코딩(Run-Length Encoding) 등의 압축 기법을 적용하기 좋고, 압축률이 높아지면 디스크 사용량뿐 아니라 메모리/캐시에 더 많은 데이터를 올릴 수 있어 성능도 함께 향상된다.
- 벡터화 처리(Vectorized Processing)
  - 압축된 컬럼 데이터를 CPU 캐시에 올려 한 번에 여러 값을 묶어서 연산(SIMD)하는 벡터화 처리를 통해 집계 연산의 속도를 추가로 높일 수 있다.
- 단점과 쓰기 트레이드오프
  - 하나의 레코드(행)를 통째로 쓰거나 수정하려면, 그 레코드가 속한 모든 컬럼 파일을 각각 찾아가 갱신해야 하므로 OLTP처럼 레코드 단위의 쓰기가 빈번한 워크로드에는 적합하지 않다.
  - 이런 이유로 보통 메모리상의 쓰기 버퍼(행 지향에 가까운 구조)에 먼저 쓰기를 모았다가, 일정량이 쌓이면 컬럼 지향 형태로 정렬/병합해 디스크에 반영하는 LSM 트리와 유사한 방식을 함께 사용하는 경우가 많다.
- 대표적인 사례
  - Amazon Redshift, Google BigQuery와 같은 분석용 데이터 웨어하우스, Parquet/ORC와 같은 컬럼 지향 파일 포맷이 대표적으로 이 방식을 사용한다.

## 복제 방식: 단일 리더, 다중 리더, 리더 없는 복제
- 단일 리더 복제(Single-Leader Replication)
  - 하나의 노드(리더/마스터)만 쓰기를 받고, 나머지 노드(팔로워/슬레이브)는 리더의 변경 사항을 전달받아 복제하는 방식이다. (기존에 정리한 `Replication (복제)`의 Master-Slave 구조와 동일한 개념이다.)
  - 모든 쓰기가 한 곳(리더)을 거치기 때문에 쓰기 순서를 정하기 쉽고 구현이 비교적 단순하며, MySQL/PostgreSQL/MongoDB 등 대부분의 DBMS가 기본적으로 채택하는 방식이다.
  - 단점은 리더가 단일 장애점(SPOF)이 될 수 있고, 리더 장애 시 새로운 리더로 승격(Failover)하는 과정이 필요하다는 것, 그리고 쓰기 처리량이 리더 한 대의 성능에 묶인다는 것이다.
- 다중 리더 복제(Multi-Leader Replication)
  - 여러 노드가 각각 쓰기를 받아들이고, 받은 변경 사항을 서로에게 복제하는 방식이다. 주로 데이터센터(리전)별로 하나씩 리더를 두어, 각 리전의 쓰기를 해당 리전의 리더가 처리하도록 구성한다.
  - 리전 간 네트워크 지연이 있어도 각 리전에서 로컬 리더에 바로 쓸 수 있어 쓰기 가용성과 지연 측면에서 유리하지만, 서로 다른 리더에서 같은 데이터가 동시에 수정되면 쓰기 충돌(Write Conflict)이 발생할 수 있어 별도의 충돌 해소 로직이 필요하다.
- 리더 없는 복제(Leaderless Replication)
  - 리더 개념 없이, 클라이언트(또는 코디네이터)가 여러 복제 노드에 직접 쓰기/읽기를 요청하는 방식이다. Dynamo 스타일로 알려져 있으며 Cassandra, Riak, DynamoDB 등이 대표적이다.
  - 쓰기는 여러 노드에 동시에 보내고 그중 일정 수 이상이 성공하면 성공으로 간주하며(정족수, Quorum), 읽기도 여러 노드에서 값을 가져와 가장 최신 버전을 선택한다.
  - 일부 노드가 쓰기를 놓쳤을 경우를 보완하기 위해, 읽을 때 오래된 값을 발견하면 바로 고쳐주는 읽기 보정(Read Repair)과, 백그라운드에서 노드 간 데이터를 주기적으로 비교/동기화하는 안티 엔트로피(Anti-Entropy) 프로세스를 함께 사용한다.
  - 특정 노드 장애에도 가용성을 잃지 않는다는 장점이 있지만, 그만큼 즉각적인 강한 일관성 보장은 약해지고 일관성 수준 자체를 정족수 설정으로 애플리케이션이 조정해야 한다.
- 선택 기준
  - 단일 리더는 구현이 단순하고 강한 일관성을 비교적 쉽게 보장할 수 있어 대부분의 서비스에 기본으로 적합하다.
  - 다중 리더는 여러 지역에 쓰기를 분산해야 하거나 오프라인 클라이언트(로컬 우선 앱 등)를 지원해야 할 때 고려하며, 리더 없는 복제는 가용성이 일관성보다 중요한 대규모 분산 환경(SNS, IoT 등)에 적합하다.

## 복제 로그 구현 방식 (구문 기반, WAL 전달, 논리적 로그)
- 구문 기반 복제(Statement-Based Replication)
  - 리더가 실행한 SQL 구문(INSERT, UPDATE, DELETE 등)을 그대로 팔로워에게 전달해 각 팔로워가 같은 구문을 다시 실행하는 방식이다.
  - 전달해야 할 데이터량이 적다는 장점이 있지만, 비결정적(Nondeterministic) 함수가 포함되면 노드마다 결과가 달라질 수 있다는 치명적인 문제가 있다. (예: `NOW()`, `RAND()`, `UUID()`)
  - 또한 자동 증가 컬럼(AUTO_INCREMENT)이나 기존 데이터에 의존하는 구문은 반드시 리더와 동일한 순서로 실행되어야 하며, 트리거/저장 프로시저처럼 부수 효과가 있는 로직도 노드마다 다른 결과를 낼 수 있다.
  - 이런 문제 때문에 MySQL도 5.1 이후로는 기본값을 구문 기반에서 행 기반으로 전환했다.
- WAL 전달(Write-Ahead Log Shipping)
  - 저장소 엔진이 데이터를 디스크에 반영하기 위해 기록하는 WAL(앞서 정리한 `Redo Log, Undo Log와 WAL` 참고)을 그대로 팔로워에게 전송해, 팔로워가 리더와 바이트 수준으로 동일한 데이터 구조를 만들도록 하는 방식이다.
  - PostgreSQL의 스트리밍 복제가 대표적이며, 복제 결과가 리더와 완전히 일치한다는 장점이 있다.
  - 단점은 로그가 디스크 페이지의 어느 바이트를 바꿨는지와 같은 저장소 엔진 내부 수준의 정보를 담고 있어 특정 버전/엔진에 강하게 결합된다는 점이다. 이로 인해 리더와 팔로워의 DB 버전이 다르면 복제가 동작하지 않을 수 있어, 무중단 버전 업그레이드(롤링 업그레이드)가 어려워진다.
- 논리적 로그 복제(Logical / Row-Based Replication)
  - 저장소 엔진 내부 구조와 분리된, 행(Row) 단위의 변경 내용을 논리적인 형태로 기록해 전달하는 방식이다. MySQL의 binlog(ROW 포맷)가 대표적이다.
  - 삽입된 행은 모든 컬럼의 새 값을, 삭제된 행은 그 행을 식별할 수 있는 정보를, 수정된 행은 식별 정보와 변경된 컬럼의 새 값을 기록한다.
  - 저장소 엔진과 분리되어 있어 리더와 팔로워가 서로 다른 DB 버전(또는 다른 저장소 엔진)을 사용할 수 있고, 이 덕분에 무중단 버전 업그레이드가 가능하다.
  - 또한 로그 형식이 외부에서 파싱하기 쉬워, DB 변경 사항을 캐시/검색 엔진/데이터 웨어하우스 등 외부 시스템으로 흘려보내는 CDC(Change Data Capture)의 기반으로 활용된다.
- 트리거 기반 복제(Trigger-Based Replication)
  - DB가 제공하는 복제 기능이 아니라, 트리거와 저장 프로시저를 이용해 변경 사항을 별도 테이블에 기록하고 애플리케이션이 이를 읽어 복제하는 방식이다.
  - 복제 대상을 세밀하게 고르거나 서로 다른 종류의 DB로 복제해야 하는 등 유연성이 필요할 때 사용하지만, 오버헤드가 크고 DB 내장 복제보다 버그와 제약이 많아 일반적으로 권장되지 않는다.

## 리더 장애 복구(Failover)와 스플릿 브레인
- Failover란?
  - 단일 리더 복제 구조에서 리더 노드에 장애가 발생했을 때, 팔로워 중 하나를 새로운 리더로 승격시키고 클라이언트의 쓰기 요청을 그쪽으로 라우팅하도록 전환하는 과정이다.
- Failover의 진행 과정
  - 리더 장애 판단 : 대부분의 시스템은 노드 간 하트비트를 주고받다가, 일정 시간(타임아웃) 동안 응답이 없으면 리더가 죽었다고 간주한다. 죽었는지 단순히 느린지를 확실히 구분할 방법은 없기 때문에 타임아웃에 의존할 수밖에 없다.
  - 새로운 리더 선출 : 남은 노드 중 하나를 새 리더로 선출한다. 데이터 유실을 최소화하기 위해 기존 리더의 변경 사항을 가장 많이 반영한(가장 최신 상태인) 노드를 고르는 것이 일반적이며, 선출 과정 자체는 합의 알고리즘(Raft 등)을 사용하거나 별도의 컨트롤러 노드가 지정하는 방식으로 이루어진다.
  - 시스템 재구성 : 클라이언트의 쓰기 요청이 새 리더로 전달되도록 라우팅을 변경하고, 기존 리더가 복구되어 돌아왔을 때는 자신이 더 이상 리더가 아님을 인식하고 새 리더의 팔로워가 되도록 해야 한다.
- Failover 과정에서 발생할 수 있는 문제
  - 데이터 유실 : 비동기 복제를 사용하는 경우, 기존 리더가 커밋했지만 아직 팔로워에 전파되지 않은 쓰기가 존재할 수 있다. 새 리더로 승격된 뒤 기존 리더가 복구되어 돌아오면, 그 사이 새 리더에는 다른 쓰기가 반영되어 있어 충돌하게 되는데, 보통 기존 리더의 미전파 쓰기를 폐기(버림)하는 방식으로 처리하므로 커밋된 데이터가 유실될 수 있다.
  - 외부 시스템과의 불일치 : DB 외부 시스템(캐시, 검색 엔진 등)이 기존 리더의 데이터를 기준으로 동작하고 있었다면, 유실된 쓰기로 인해 DB와 외부 시스템 간 데이터가 어긋날 수 있다. (예: 자동 증가 ID가 재사용되어 이미 다른 데이터에 쓰인 ID와 충돌)
  - 스플릿 브레인(Split Brain) : 두 노드가 동시에 자신이 리더라고 믿는 상태를 말한다. 네트워크 단절로 기존 리더가 죽은 것으로 오판되어 새 리더가 선출되었지만, 실제로 기존 리더는 살아있어 양쪽 모두 쓰기를 받아버리는 경우가 대표적이다. 두 리더가 각각 쓰기를 처리하면 데이터가 서로 달라지며 유실/손상으로 이어진다.
  - 타임아웃 설정의 어려움 : 타임아웃이 너무 길면 장애 복구가 늦어져 그만큼 서비스 중단 시간이 길어지고, 너무 짧으면 일시적인 부하 증가나 네트워크 지연을 장애로 오판해 불필요한 Failover가 발생한다. 불필요한 Failover는 이미 부하가 높은 상황을 더 악화시킬 수 있다.
- 스플릿 브레인 방지 방법
  - 정족수(Quorum) 기반 선출 : 과반수 노드의 동의를 얻은 노드만 리더가 될 수 있도록 하여, 네트워크가 분리되어도 한쪽에서만 리더가 선출되도록 보장한다.
  - 펜싱(Fencing, STONITH) : 새 리더가 선출되면 기존 리더를 강제로 차단하거나 종료시켜, 되살아난 기존 리더가 쓰기를 수행하지 못하게 만든다. 펜싱 토큰(단조 증가하는 번호)을 함께 사용하면, 오래된 토큰을 가진 기존 리더의 쓰기 요청을 저장소 쪽에서 거부할 수 있다.
  - 이러한 어려움 때문에 일부 운영 팀은 자동 Failover를 끄고, 장애 상황을 사람이 직접 판단해 수동으로 전환하는 정책을 택하기도 한다.

## 복제 지연과 일관성 보장 (자신이 쓴 내용 읽기, 단조 읽기, 일관된 순서로 읽기)
- 최종적 일관성(Eventual Consistency)과 복제 지연
  - 비동기 복제 환경에서는 리더에 반영된 쓰기가 팔로워에 전파되기까지 시간차(복제 지연, Replication Lag)가 존재한다. 쓰기가 멈추면 결국 모든 팔로워가 리더와 같아지므로 이를 최종적 일관성이라 부르지만, "결국"이 언제인지에 대한 보장은 없다.
  - 평소에는 지연이 수밀리초 수준이어도, 부하가 몰리거나 네트워크에 문제가 생기면 수 초~수 분까지 벌어질 수 있어 사용자에게 드러나는 이상 현상이 발생한다. 이를 완화하기 위해 아래의 세 가지 보장을 선택적으로 제공한다.
- 자신이 쓴 내용 읽기(Read-after-Write / Read-your-writes Consistency)
  - 사용자가 자신이 방금 쓴 데이터는 반드시 반영된 상태로 볼 수 있어야 한다는 보장이다. 다른 사용자의 쓰기에 대해서는 아무것도 보장하지 않는다.
  - 이 보장이 없으면 사용자는 자신의 데이터가 유실된 것처럼 느낀다. (예: 댓글을 작성했는데 새로고침하니 댓글이 사라져 보이는 경우)
  - 구현 방법
    - 사용자가 수정할 수 있는 데이터는 리더에서 읽고, 그 외에는 팔로워에서 읽는다. (예: 내 프로필은 리더에서, 다른 사람 프로필은 팔로워에서 조회)
    - 마지막 쓰기 시각을 기억해두고, 쓰기 후 일정 시간(예: 1분) 이내의 읽기는 리더에서 처리한다.
    - 클라이언트가 가장 최근 쓰기의 타임스탬프(또는 로그 위치)를 기억하고, 읽기 요청 시 그 시점 이상으로 복제가 진행된 팔로워에서만 읽도록 한다.
  - 여러 디바이스에서 접근하는 경우(Cross-Device)에는 한 디바이스의 쓰기를 다른 디바이스에서도 읽을 수 있어야 하므로, 타임스탬프를 클라이언트가 아닌 서버 측에서 사용자별로 중앙 관리해야 하고, 디바이스들이 서로 다른 데이터센터로 라우팅될 수 있다는 점도 고려해야 한다.
- 단조 읽기(Monotonic Reads)
  - 사용자가 데이터를 여러 번 읽을 때, 시간을 거꾸로 거슬러 과거의 데이터를 보게 되는 일은 없어야 한다는 보장이다.
  - 복제 지연이 서로 다른 여러 팔로워에서 번갈아 읽으면, 첫 번째 읽기에서는 최신 데이터를 보고 두 번째 읽기에서는 더 오래된 데이터를 보는 역행 현상이 발생할 수 있다.
  - 각 사용자가 항상 동일한 복제 서버에서 읽도록(예: 사용자 ID의 해시값으로 복제 서버를 선택) 라우팅하면 보장할 수 있다. 다만 그 복제 서버에 장애가 발생하면 다른 서버로 재라우팅해야 한다.
  - 자신이 쓴 내용 읽기보다는 약하지만, 단조 읽기는 "한 번 본 데이터는 사라지지 않는다"는 수준의 보장을 제공한다.
- 일관된 순서로 읽기(Consistent Prefix Reads)
  - 쓰기가 특정 순서로 발생했다면, 그것을 읽는 사람도 같은 순서로 보게 된다는 보장이다. 인과관계가 뒤바뀌어 보이지 않도록 하는 것이 목적이다.
  - 파티션(샤드)마다 복제 지연이 다르면, 질문보다 답변이 먼저 보이는 것처럼 인과관계가 역전된 상태를 읽을 수 있다.
  - 인과적으로 연관된 쓰기들을 같은 파티션에 저장하여 순서를 보장하거나, 인과관계를 명시적으로 추적하는 알고리즘(인과적 일관성, 램포트 타임스탬프 등)을 사용해 해결한다.
- 애플리케이션 레벨 처리의 한계
  - 이러한 보장들을 애플리케이션 코드에서 직접 구현하는 것은 복잡하고 실수하기 쉬우므로, 가능하다면 트랜잭션처럼 DB가 더 강한 보장을 제공하도록 맡기는 것이 바람직하다는 것이 DDIA의 관점이다.

## 다중 리더 복제의 쓰기 충돌과 해소 방법
- 쓰기 충돌(Write Conflict)이란?
  - 다중 리더 복제에서는 여러 리더가 각각 쓰기를 받아들이기 때문에, 서로 다른 리더에서 같은 데이터를 동시에 수정하면 어느 값이 맞는지 알 수 없는 충돌이 발생한다.
  - 단일 리더 복제에서는 두 번째 쓰기가 첫 번째 쓰기를 기다리거나(블로킹) 실패하므로 사용자가 즉시 재시도할 수 있지만, 다중 리더에서는 양쪽 쓰기가 각자의 리더에서 모두 성공한 뒤 나중에 비동기로 복제되는 시점에야 충돌이 드러나기 때문에 사용자에게 재시도를 요구할 수 없다.
- 충돌 회피(Conflict Avoidance)
  - 가장 단순하고 권장되는 접근은 애초에 충돌이 생기지 않도록 설계하는 것이다. 특정 레코드에 대한 모든 쓰기가 항상 동일한 리더를 거치도록 라우팅하면 그 레코드에 대해서는 단일 리더처럼 동작한다. (예: 사용자별 데이터는 해당 사용자의 홈 데이터센터 리더에서만 처리)
  - 다만 데이터센터 장애나 사용자의 이동으로 라우팅 대상 리더가 바뀌면 다시 충돌 가능성이 생기므로 완벽한 해법은 아니다.
- 수렴(Convergent) 충돌 해소 방법
  - 모든 복제 서버가 최종적으로 동일한 값에 도달해야 하므로(수렴), 충돌이 발생했을 때 어떤 값을 남길지 결정하는 규칙이 필요하다.
  - LWW(Last Write Wins, 최종 쓰기 승리) : 각 쓰기에 타임스탬프나 고유 ID를 부여하고 가장 큰 값을 가진 쓰기를 채택한다. 구현이 간단해 널리 쓰이지만, 채택되지 않은 쓰기는 조용히 버려지므로 데이터 유실이 발생한다.
  - 복제 서버 우선순위 : 복제 서버마다 고유 번호를 부여하고 번호가 높은 서버의 쓰기를 채택한다. 이 역시 데이터 유실이 발생한다.
  - 값 병합(Merge) : 두 값을 어떤 방식으로든 합친다. (예: 문자열을 사전순으로 정렬해 연결)
  - 충돌 기록 보존 : 충돌한 모든 값을 명시적으로 보존해두고, 이후 애플리케이션 코드나 사용자에게 어느 값을 택할지 묻는 방식으로 해소한다.
- 사용자 정의 충돌 해소 로직
  - 대부분의 다중 리더 복제 도구는 애플리케이션 코드로 충돌 해소 로직을 작성할 수 있게 해주며, 실행 시점에 따라 두 가지로 나뉜다.
  - 쓰기 수행 중(On Write) : 복제된 변경 로그에서 충돌이 감지되면 즉시 충돌 핸들러를 호출한다. 백그라운드에서 빠르게 실행되므로 사용자에게 물어볼 수는 없다.
  - 읽기 수행 중(On Read) : 충돌한 값들을 모두 저장해두고, 다음에 그 데이터를 읽을 때 애플리케이션에 여러 버전을 함께 반환해 해소하도록 한다. (CouchDB 방식)
- 자동 충돌 해소 자료구조
  - CRDT(Conflict-free Replicated Data Type) : 집합, 카운터, 맵, 리스트 등에 대해 여러 복제 서버가 독립적으로 수정해도 자동으로 동일한 상태로 수렴하도록 설계된 자료구조이다.
  - 병합 가능한 영속 자료구조(Mergeable Persistent Data Structure) : Git처럼 변경 이력을 모두 추적하고 3-way 병합을 수행하는 방식이다.
  - 운영 변환(Operational Transformation) : 구글 독스와 같은 공동 편집 환경에서 텍스트의 순서 있는 삽입/삭제를 충돌 없이 반영하기 위해 사용되는 알고리즘이다.

## 정족수(Quorum) 읽기와 쓰기
- 정족수(Quorum)란?
  - 리더 없는 복제(앞서 정리한 `복제 방식: 단일 리더, 다중 리더, 리더 없는 복제` 참고)에서, 클라이언트가 모든 복제 노드가 아니라 일정 수 이상의 노드로부터만 응답을 받으면 쓰기/읽기가 성공한 것으로 간주하는 방식이다.
  - 복제 노드 수를 n, 쓰기 성공에 필요한 최소 노드 수를 w, 읽기 성공에 필요한 최소 노드 수를 r이라 할 때, `w + r > n`을 만족하도록 설정하면 읽기 정족수와 쓰기 정족수가 최소 한 노드에서는 겹치게 되어, 읽을 때 최신 쓰기가 반영된 노드를 적어도 하나는 포함한다고 기대할 수 있다.
- 일반적인 설정
  - 노드 수가 n개일 때 w와 r을 과반수(`(n/2)+1`)로 설정하는 것이 널리 쓰인다. 이렇게 하면 최대 `n/2`개의 노드가 죽거나 응답하지 않아도 읽기/쓰기를 계속 처리할 수 있다.
  - w나 r을 낮추면(예: w=1) 가용성과 쓰기/읽기 속도는 높아지지만, 최신 데이터를 보장받지 못할 가능성이 커진다.
- 정족수를 지켜도 완벽하지 않은 이유
  - 쓰기와 읽기가 동시에 일어나면, 쓰기가 일부 노드에만 반영된 상태에서 읽기가 수행되어 어떤 클라이언트는 새 값을, 어떤 클라이언트는 옛 값을 볼 수 있다.
  - 쓰기가 w개보다 적은 노드에만 반영된 상태에서 실패로 끝날 경우, 그 쓰기를 롤백하지 않고 그대로 두는 구현이 많아 이후 읽기에서 일부만 반영된 쓰기가 보일 수 있다.
  - 쓰기를 수행하던 노드가 중간에 장애가 나서 새 값과 이전 값이 섞인 노드로 복구되면, 그 다음 정족수 계산에 영향을 줄 수 있다.
  - 타이밍 문제(시계 이슈)로 인해 두 클라이언트가 동시에 같은 값을 쓸 때 어느 쓰기가 "승리"하는지가 모호해질 수 있다.
  - 이런 이유로 `w + r > n`이 보장하는 것은 "대부분의 경우 최신 값을 읽을 가능성이 높다"는 수준이며, 선형성(Linearizability)과 같은 강한 보장은 아니다.
- 느슨한 정족수(Sloppy Quorum)와 암시적 핸드오프(Hinted Handoff)
  - 네트워크 단절로 지정된 n개의 노드에 정족수를 채울 수 없을 때, 원래 담당 노드가 아닌 다른 가용한 노드에 임시로 쓰기를 기록해 가용성을 높이는 방식이다.
  - 네트워크가 복구되면 임시로 기록된 데이터를 원래 담당 노드로 옮겨주는데(Hinted Handoff), 이 방식을 사용하면 w개의 응답을 받았더라도 그중에 원래 담당 노드가 포함되지 않을 수 있어 최신 값을 읽는다는 보장이 더 약해진다.

## 파티셔닝 방식: 키 범위 vs 해시
- 파티셔닝의 목표
  - 대용량 데이터셋을 여러 노드에 나누어 저장할 때, 데이터와 쿼리 부하가 모든 노드에 고르게 분산되는 것이 이상적이다. 일부 노드가 다른 노드보다 훨씬 많은 데이터/부하를 담당하면 그 노드가 병목(Hot Spot)이 되어 전체 시스템 성능이 저하된다.
- 키 범위 기반 파티셔닝(Partitioning by Key Range)
  - 키의 정렬된 범위를 나누어 각 파티션에 할당한다. (예: A~D는 파티션1, E~H는 파티션2)
  - 키가 정렬되어 저장되므로 범위 조회(Range Query)가 매우 효율적이다. (예: 특정 날짜 범위의 로그 조회)
  - 단점은 특정 패턴의 키(예: 타임스탬프를 그대로 키로 사용)가 몰리면 특정 시점의 쓰기가 전부 하나의 파티션(그 시점을 담당하는)으로 쏠려 핫스팟이 발생하기 쉽다는 것이다. 이를 완화하려면 키 앞에 추가 식별자(예: 디바이스 ID)를 붙여 쓰기를 분산시키는 방법을 사용할 수 있지만, 그러면 범위 조회 시 여러 파티션을 함께 조회해야 하는 트레이드오프가 생긴다.
  - HBase, RethinkDB, 초기 MongoDB 등이 이 방식을 사용한다.
- 해시 기반 파티셔닝(Partitioning by Hash of Key)
  - 키에 해시 함수를 적용한 뒤, 그 해시값의 범위를 각 파티션에 할당한다.
  - 좋은 해시 함수는 비슷한 키라도 전혀 다른 해시값을 만들어내므로, 특정 키 범위로의 쏠림 없이 데이터를 비교적 균등하게 분산시킬 수 있다.
  - 단점은 해시로 흩어지는 특성 때문에 범위 조회를 할 수 없다는 것이다. 연속된 키 범위라도 해시값은 서로 무관한 파티션에 저장되어, 범위 조회를 하려면 모든 파티션을 뒤져야 한다.
  - Cassandra, MongoDB(해시 샤딩 모드) 등이 사용하며, Cassandra는 복합 키의 첫 번째 컬럼만 해싱해 파티셔닝에 쓰고 나머지 컬럼은 정렬 키로 사용하는 절충안(Compound Key)을 제공해, 같은 첫 컬럼 값 내에서는 범위 조회가 가능하도록 한다.
- 선택 기준
  - 범위 조회가 자주 필요한 워크로드(시계열 데이터 등)에는 키 범위 기반이, 쓰기 분산과 균등한 부하가 더 중요한 워크로드에는 해시 기반이 적합하다.

## 핫스팟과 핫 키 처리
- 핫스팟(Hot Spot)과 핫 키(Hot Key)란?
  - 파티셔닝을 적용했음에도 특정 파티션이 다른 파티션보다 훨씬 많은 읽기/쓰기 부하를 받는 상태를 핫스팟이라 하며, 그 원인이 되는 특정 키(또는 소수의 키)에 요청이 과도하게 몰리는 것을 핫 키라 부른다.
  - 해시 기반 파티셔닝이 평균적인 부하 분산에는 유리하지만, 극단적인 경우(예: 유명인의 SNS 계정, 특정 인기 상품)에는 하나의 키에 대한 요청이 집중되어 해시로도 분산시킬 수 없는 핫스팟이 생길 수 있다.
- 핫 키로 인한 문제
  - 해당 키를 담당하는 파티션(노드)에 읽기/쓰기가 집중되어 그 노드만 과부하 상태가 되고, 나머지 노드는 유휴 상태로 남아 전체 자원이 비효율적으로 사용된다.
  - 단일 리더 복제 환경에서는 그 키에 대한 모든 쓰기가 하나의 리더로 집중되므로, 파티션을 아무리 늘려도 해당 키의 쓰기 처리량 자체는 늘어나지 않는다는 근본적인 한계가 있다.
- 완화 방법
  - 키 분산(Salting) : 핫 키 앞뒤에 임의의 접두사/접미사를 붙여 여러 개의 하위 키로 쪼개고, 이를 서로 다른 파티션에 분산시킨다. (예: `user:123` → `user:123:0`, `user:123:1`, ...) 다만 이 경우 그 키로 조회할 때는 쪼개진 모든 하위 키를 조회해 합쳐야 하므로 애플리케이션 로직이 복잡해진다.
  - 핫 키를 식별해 별도 처리 : 모니터링을 통해 특정 키가 핫 키인지 감지하고, 그 키만 예외적으로 별도의 전용 노드나 캐시에서 처리하도록 분리한다.
  - 애플리케이션 레벨 캐싱 : 자주 읽히는(읽기 위주) 핫 키는 Redis와 같은 캐시 계층에서 흡수하여, DB 파티션까지 요청이 도달하지 않도록 한다.
  - 다만 애플리케이션이 핫 키를 완전히 자동으로 감지하고 분산시키는 것은 여전히 어려운 문제이며, 대부분은 일부 수동 작업(특정 키 패턴에 대한 분산 로직 추가)이 필요하다.

## 파티셔닝과 보조 색인 (로컬 색인 vs 전역 색인)
- 문제 상황
  - 기본키(Primary Key)로 파티셔닝된 데이터에, 기본키가 아닌 다른 컬럼(보조 색인, Secondary Index)으로 조회하려는 경우 색인을 어떻게 파티셔닝할지가 문제가 된다. 보조 색인은 기본키처럼 깔끔하게 하나의 파티션으로 나뉘지 않기 때문이다. (예: 중고차 사이트에서 색상, 제조사별 검색)
- 문서 기반 파티셔닝(Local Index, 로컬 색인)
  - 각 파티션이 자신이 가진 문서(레코드)에 대해서만 독립적으로 보조 색인을 유지한다. (예: 파티션1의 빨간 차 색인은 파티션1에만, 파티션2의 빨간 차 색인은 파티션2에만 존재)
  - 쓰기가 간단하다. 문서를 추가/수정/삭제할 때 해당 문서가 속한 파티션의 색인만 갱신하면 되므로 하나의 파티션에만 접근하면 된다.
  - 읽기는 비효율적일 수 있다. 특정 조건(예: 색상=빨강)으로 조회하려면 모든 파티션에 색인 조회 요청을 보내고 결과를 모아 합쳐야 한다(분산 조인, Scatter/Gather). 파티션 수가 많아질수록 느려지고, 일부 파티션이 느리면 전체 응답이 그 파티션에 좌우되는 꼬리 지연 증폭 문제도 발생한다.
  - MongoDB, Cassandra, Elasticsearch 등이 기본적으로 이 방식을 사용한다.
- 용어 기반 파티셔닝(Global Index, 전역 색인)
  - 보조 색인 자체를 색인 값(용어, Term) 기준으로 별도로 파티셔닝하여, 전체 데이터셋에 대해 하나의 전역적인 색인 구조를 만든다. (예: 색인 값 A~F는 색인 파티션1, G~M은 색인 파티션2)
  - 읽기가 효율적이다. 특정 조건으로 조회할 때 해당 조건의 값이 속한 색인 파티션 하나(또는 소수)만 조회하면 되므로 분산 조인 없이 바로 결과를 얻을 수 있다.
  - 쓰기가 비효율적일 수 있다. 하나의 문서를 쓸 때 그 문서가 가진 여러 속성 각각이 서로 다른 색인 파티션에 걸쳐 있을 수 있어, 하나의 쓰기가 여러 파티션에 걸친 갱신으로 이어진다. 이 여러 파티션에 걸친 갱신을 원자적으로 처리하는 것이 어려워, 보통 비동기(최종적 일관성)로 처리한다.
- 선택 기준
  - 쓰기가 빈번하고 읽기 지연에 다소 여유가 있다면 로컬 색인이, 반대로 읽기 성능과 일관된 다중 조건 검색이 중요하고 쓰기 지연을 감수할 수 있다면 전역 색인이 적합하다.

## 리밸런싱 전략과 요청 라우팅
- 리밸런싱(Rebalancing)이란?
  - 노드를 추가/제거하거나 하드웨어 장애로 노드가 바뀌었을 때, 데이터와 요청 부하가 다시 모든 노드에 고르게 분산되도록 파티션을 재배치하는 과정이다.
  - 좋은 리밸런싱은 리밸런싱 동안에도 읽기/쓰기 요청을 계속 처리할 수 있어야 하고(가용성), 필요한 데이터만 이동시켜 네트워크/디스크 부하를 최소화해야 하며, 자동으로 트리거되기보다는 사람이 승인하는 반자동 방식이 운영상 안전하다.
- 안티패턴: 해시 모듈로(mod N) 방식
  - 해시값을 파티션 수로 나눈 나머지(`hash(key) mod N`)로 파티션을 결정하는 방식은 노드 수(N)가 바뀌면 거의 모든 키의 소속 파티션이 바뀌어버려, 리밸런싱 시 대부분의 데이터를 재이동시켜야 하므로 비효율적이다.
- 고정 개수 파티션(Fixed Number of Partitions)
  - 노드 수와 무관하게 처음부터 노드 수보다 훨씬 많은 수의 파티션(예: 1000개)을 만들어두고, 각 노드가 여러 파티션을 담당하도록 한다.
  - 노드가 추가되면 기존 노드들이 담당하던 파티션 중 일부를 통째로(옮길 데이터만, 파티션을 다시 나누지 않고) 새 노드로 넘겨주면 되므로 이동량이 예측 가능하고 운영이 단순하다.
  - 단점은 파티션 수를 처음에 정해야 하는데, 데이터셋 전체 크기를 미리 가늠하기 어려운 경우 파티션 수를 잘못 잡으면 각 파티션이 너무 크거나 작아져 운영 오버헤드가 생긴다. Riak, Elasticsearch 등이 사용한다.
- 동적 파티셔닝(Dynamic Partitioning)
  - 파티션이 일정 크기를 초과하면 자동으로 둘로 분할(Split)하고, 데이터가 줄어 작아지면 인접 파티션과 병합(Merge)하는 방식이다.
  - 데이터 양에 따라 파티션 수가 자동으로 늘거나 줄기 때문에, 고정 개수 방식과 달리 데이터셋 크기를 미리 알 필요가 없다. 다만 처음 데이터가 거의 없을 때는 모든 쓰기가 하나의 파티션(노드)에만 집중되는 문제가 있어, 미리 어느 정도 분할된 상태로 시작(Pre-splitting)하는 경우가 많다. HBase, RethinkDB 등이 사용한다.
- 노드 비례 파티셔닝(Partitioning Proportional to Nodes)
  - 노드 수에 비례해 파티션 수를 고정(예: 노드당 파티션 수를 일정하게 유지)하는 방식으로, 노드가 추가될 때마다 무작위로 일부 기존 파티션을 선택해 분할하고 새 노드에 그 절반을 할당한다. Cassandra, Ketama 등이 사용한다.
- 요청 라우팅(Request Routing)
  - 클라이언트의 요청이 어떤 노드로 가야 하는지 결정하는 문제로, 서비스 디스커버리(Service Discovery)의 한 형태이다.
  - 라우팅 티어(Routing Tier) : 별도의 라우팅 전용 컴포넌트(로드밸런서 등)가 요청을 받아 올바른 노드로 전달한다. 클라이언트는 데이터 분산 구조를 알 필요가 없다.
  - 코디네이션 서비스(ZooKeeper 등) 활용 : 각 노드가 자신이 담당하는 파티션 정보를 ZooKeeper와 같은 코디네이터에 등록하고, 라우팅 티어나 클라이언트가 이를 구독해 최신 라우팅 정보를 유지한다. (HBase, Kafka 등이 이 방식에 가깝다.)
  - 가십 프로토콜(Gossip Protocol) 활용 : 별도의 코디네이터 없이, 노드들끼리 서로 상태 정보를 주고받아(가십) 클러스터 전체의 파티션 배치 정보를 전파한다. 클라이언트는 임의의 노드에 요청을 보내도 되고, 그 노드가 올바른 파티션으로 재전달해준다. (Cassandra, Riak 등)

## 갱신 손실(Lost Update)과 해결 방법
- 갱신 손실(Lost Update)이란?
  - 두 트랜잭션이 동시에 같은 레코드를 "읽고 → 값을 계산해서 → 다시 쓰는" 읽기-수정-쓰기(Read-Modify-Write) 패턴으로 갱신할 때, 한쪽의 변경 사항이 다른 쪽에 의해 덮어써져 사라지는 현상이다.
  - 예) 두 트랜잭션이 동시에 카운터 값 `5`를 읽고, 각각 `+1` 연산을 적용해 `6`으로 저장하면, 원래는 `7`이 되어야 하는데 둘 중 하나의 증가 연산이 반영되지 않아 최종 값이 `6`이 되어버린다.
  - Read Committed 격리 수준에서도 갱신 손실은 방지되지 않는다. 각 트랜잭션의 읽기/쓰기 자체는 커밋된 값만 보지만, 두 트랜잭션이 각각 읽은 이후 서로의 쓰기를 모르고 진행하기 때문이다.
- 해결 방법
  - 원자적 쓰기 연산(Atomic Write Operation) 사용 : 애플리케이션에서 "읽고 → 계산 → 쓰기"로 나누어 처리하지 않고, DB가 제공하는 원자적 연산을 그대로 사용한다. (예: `UPDATE counters SET value = value + 1`) 대부분의 DB는 이런 연산을 실행할 때 내부적으로 배타락을 걸어 안전하게 처리한다.
  - 명시적 락(Explicit Locking) : `SELECT ... FOR UPDATE`처럼 읽을 때 명시적으로 배타락을 걸어, 다른 트랜잭션이 같은 레코드를 동시에 수정하지 못하게 한다.
  - 자동 감지(Automatic Detection) : Snapshot Isolation(스냅샷 격리)에서 동시 갱신을 감지하면 트랜잭션을 중단(abort)시키고, 애플리케이션이 재시도하도록 하는 방식이다. PostgreSQL, MySQL(InnoDB) 등이 Repeatable Read 수준에서 이런 감지를 제공한다.
  - CAS(Compare-and-Set) : 읽은 시점의 값을 조건으로 걸어, 그 값이 변경되지 않았을 때만 쓰기가 성공하도록 한다. (예: `UPDATE ... WHERE value = <읽은 값>`) 쓰기가 실패하면 값을 다시 읽어 재시도한다.
  - 다중 리더/리더 없는 복제 환경에서는 동시 쓰기가 서로 다른 노드에서 일어날 수 있어 락이나 CAS가 통하지 않으므로, 여러 값을 모두 보존한 뒤 애플리케이션 레벨에서 병합하는 방식을 사용하기도 한다. (앞서 정리한 `다중 리더 복제의 쓰기 충돌과 해소 방법` 참고)

## 쓰기 스큐(Write Skew)와 팬텀(Phantom)
- 쓰기 스큐(Write Skew)란?
  - 두 트랜잭션이 같은 레코드를 갱신하는 것이 아니라, 서로 다른 레코드를 각각 갱신하지만 그 둘 사이에 존재하는 어떤 불변식(제약 조건)이 두 트랜잭션이 동시에 실행됐을 때 깨지는 현상이다. 갱신 손실과 달리 "같은 레코드를 동시에 쓰는" 전형적인 패턴이 아니라서 감지하기가 더 까다롭다.
  - 대표적인 예 : 병원 당직 시스템에서 "최소 1명은 당직을 서야 한다"는 제약이 있을 때, 두 명의 당직 의사가 동시에 "지금 당직자가 2명이니 나는 빠져도 되겠다"고 각자 판단해 동시에 당직을 취소하면, 결과적으로 당직자가 0명이 되어 제약이 깨진다. 각자는 자신이 조회한 시점(2명)을 기준으로 판단했으므로 개별 쓰기 자체는 정당해 보인다.
  - 다른 예로는 회의실 중복 예약 방지(같은 시간대 중복 예약 확인 후 예약), 계좌 잔액이 0 이상이어야 하는 제약을 두 개의 동시 이체로 위반하는 경우 등이 있다.
- 팬텀(Phantom)
  - 하나의 트랜잭션이 어떤 조건(WHERE 절)으로 조회했을 때는 없던 레코드가, 다른 트랜잭션의 쓰기로 인해 그 조건에 해당하는 새로운 레코드로 나타나는 현상이다. (기존에 정리한 `Transaction`의 Phantom Read 참고)
  - 쓰기 스큐는 대부분 "조회 → 그 결과를 바탕으로 판단 → 쓰기" 패턴에서 발생하는데, 이 조회가 존재하는 레코드의 값뿐 아니라 "조건을 만족하는 레코드가 몇 개인지"에 의존할 경우 팬텀에 취약해진다. 즉 쓰기 스큐는 팬텀이 원인이 되어 발생하는 대표적인 이상 현상 중 하나로 볼 수 있다.
- 해결 방법
  - 조건부 잠금(Materializing Conflicts) : 팬텀의 대상이 될 수 있는 행이 실제로 존재하지 않으면 잠글 수 없으므로, 미리 그 조건에 해당하는 행(또는 락을 걸 수 있는 더미 행)을 만들어두고 `SELECT ... FOR UPDATE`로 명시적으로 잠근 뒤 진행한다. 다만 구현이 부자연스럽고 누수되기 쉬워 최후의 수단으로 권장된다.
  - 직렬화 가능(Serializable) 격리 수준 사용 : 트랜잭션들이 순서대로(직렬로) 실행된 것과 동일한 결과를 보장하는 가장 강력한 격리 수준을 사용하면, 쓰기 스큐와 팬텀을 포함한 모든 동시성 이상 현상을 원천적으로 방지할 수 있다. (다음 항목 `직렬성 구현 방식` 참고)

## 직렬성 구현 방식 (순차 실행, 2PL, SSI)
- 직렬성(Serializable) 격리 수준이란?
  - 여러 트랜잭션을 동시에 실행하더라도, 그 결과가 트랜잭션들을 어떤 순서로든 하나씩 차례로(직렬로) 실행한 것과 동일하도록 보장하는 가장 강력한 격리 수준이다. 이를 보장하면 갱신 손실, 쓰기 스큐, 팬텀 등 모든 동시성 이상 현상이 원천적으로 방지된다.
- 1. 실제 순차 실행(Actual Serial Execution)
  - 트랜잭션을 여러 스레드로 동시에 처리하는 대신, 단일 스레드에서 트랜잭션을 하나씩 순서대로 실행하는 방식이다. 동시성 문제가 아예 발생할 여지가 없어 가장 단순하고 확실하다.
  - 모든 데이터를 메모리에 올릴 수 있을 만큼 작고, 트랜잭션 자체가 매우 짧게(보통 저장 프로시저로 미리 작성되어 네트워크 대기 없이) 실행되는 경우에만 실용적이다. (VoltDB, Redis 등)
  - 트랜잭션이 디스크 I/O나 다른 네트워크 호출을 기다리면 그 시간 동안 전체 처리량이 멈추므로, 상호작용형(Interactive) 트랜잭션에는 부적합하다.
- 2. 2단계 잠금(Two-Phase Locking, 2PL)
  - 여러 트랜잭션이 같은 데이터에 동시에 접근하려 할 때, 공유락/배타락(기존에 정리한 `DB Lock` 참고)을 이용해 충돌을 방지하는 전통적인 방식이다. 이름의 "2단계"는 트랜잭션 도중에는 계속 락을 확장(Growing)해 나가고, 커밋/롤백 시점에 한꺼번에 모든 락을 해제(Shrinking)한다는 의미이다.
  - 공유락 간에는 동시 접근이 가능하지만, 읽기 락과 쓰기 락, 쓰기 락과 쓰기 락은 서로를 블로킹한다는 점에서 일반적인 락보다 훨씬 더 강하게 동시성을 제한한다.
  - 팬텀을 방지하기 위해, 특정 레코드가 아니라 조건에 해당하는 범위 자체에 락을 거는 서술어 락(Predicate Lock) 또는 그 구현체인 인덱스 범위 락(갭 락, Next-Key Lock 등)을 함께 사용한다. (MySQL InnoDB가 Repeatable Read에서 Phantom Read를 방지하는 원리와 동일하다.)
  - 락 경합이 많아지면 성능이 크게 저하되고, 교착상태(DeadLock)가 발생할 수 있으며, 응답 시간의 변동성(Latency Variance)이 커지는 단점이 있다.
- 3. 직렬성 스냅샷 격리(Serializable Snapshot Isolation, SSI)
  - 낙관적(Optimistic) 동시성 제어 방식으로, 트랜잭션들이 각자 스냅샷을 기준으로 락 없이 자유롭게 실행된 뒤, 커밋하는 시점에 "이 실행 순서가 실제로 직렬 실행과 동치였는가"를 검증한다. 검증에 실패하면 트랜잭션을 중단(abort)시키고 재시도하게 한다.
  - 2PL처럼 매번 락을 걸어 기다리는 대신, 충돌이 실제로 자주 발생하지 않는다면 락 없이 동시에 실행해 처리량을 높일 수 있다는 것이 핵심 아이디어이며, 읽기 성능이 중요한 워크로드에서 2PL보다 유리할 수 있다.
  - 커밋 시점에 "트랜잭션이 읽은 데이터가 그 사이 다른 트랜잭션에 의해 변경되었는지"와 "쓰기가 다른 트랜잭션이 읽은 데이터에 영향을 주는지"를 모두 추적해 위반 여부를 판단한다. 충돌이 잦은 워크로드에서는 중단/재시도가 빈번해져 오히려 비효율적일 수 있다. PostgreSQL(9.1+), FoundationDB 등이 지원한다.

## 선형성(Linearizability)과 직렬성의 차이
- 선형성(Linearizability)이란?
  - 여러 복제본/노드가 있더라도 시스템 전체가 마치 데이터의 복제본이 단 하나만 있는 것처럼 동작하도록 보장하는 성질이다. 즉 하나의 쓰기가 완료된 순간부터는, 그 이후의 모든 읽기는 (어느 노드에 요청하든) 반드시 그 최신 값을 봐야 한다.
  - 핵심은 "최근성(Recency)" 보장이다. 한 연산이 끝난 시점과 다른 연산이 시작된 시점이 겹치지 않는다면, 나중에 시작된 연산은 앞선 연산의 결과를 반드시 반영해야 한다.
  - 단일 리더 복제에서 동기 복제를 쓰거나, 쓰기 직후 항상 리더에서 읽도록 라우팅하면 선형성에 가까워질 수 있지만, 비동기 복제나 리더 없는 복제에서는 일반적으로 선형성이 보장되지 않는다.
- 직렬성(Serializability)이란?
  - 여러 트랜잭션을 동시에 실행한 결과가, 그 트랜잭션들을 어떤 순서로든 하나씩 순차적으로 실행한 것과 동일함을 보장하는 성질이다. (앞서 정리한 `직렬성 구현 방식` 참고)
  - 선형성과 달리 직렬성은 "그 순서가 실제 시간 순서(Real-Time Order)와 일치해야 한다"는 것을 요구하지 않는다. 즉 트랜잭션들을 재배열한 어떤 가상의 순서에서 결과가 맞아떨어지면 충분하며, 그 순서가 실제로 트랜잭션이 발생한 시간 순서와 다를 수 있다.
- 두 개념의 차이와 관계
  - 선형성은 단일 객체(레코드)에 대한 연산 하나하나의 최신성에 대한 보장이고, 직렬성은 여러 객체에 걸친 여러 연산(트랜잭션) 묶음에 대한 격리성 보장이다. 즉 선형성은 "하나의 변수를 읽고 쓸 때의 보장"에 가깝고, 직렬성은 "여러 데이터를 아울러 실행되는 트랜잭션의 보장"에 가깝다.
  - 선형성을 만족한다고 해서 직렬성이 보장되는 것은 아니고, 역으로 직렬성(일반 직렬성)을 만족한다고 해서 선형성이 보장되는 것도 아니다. 다만 두 성질을 모두 만족하는 더 강한 모델인 엄격한 직렬성(Strict Serializability)도 존재하며, 분산 트랜잭션에서 요구되는 경우가 있다.
  - 선형성은 구현을 위해 모든 쓰기/읽기가 합의를 거쳐야 해서 비용이 크고, 네트워크 파티션 상황에서는 가용성을 포기해야 한다(CP 선택)는 근본적인 제약이 있다.

## 2단계 커밋(2PC)과 한계
- 2단계 커밋(Two-Phase Commit, 2PC)이란?
  - 여러 노드(또는 여러 DB)에 걸친 하나의 트랜잭션을 원자적으로 커밋하기 위한 프로토콜이다. 분산 트랜잭션에서 "모든 참여자가 전부 커밋하거나, 전부 롤백한다"는 원자성(Atomicity)을 보장하는 것이 목적이다.
  - 애플리케이션이 직접 조정하는 것이 아니라, 코디네이터(Coordinator, 트랜잭션 매니저)가 각 참여자(Participant) 노드들의 커밋 여부를 중재한다.
- 동작 과정
  - 1단계(준비, Prepare) : 코디네이터가 모든 참여자에게 "커밋할 준비가 되었는가?"를 묻는 준비 요청을 보낸다. 각 참여자는 자신의 로컬 트랜잭션을 커밋할 수 있는 상태까지 처리해두고(디스크에 기록), 반드시 커밋할 수 있다고 "예"로 응답하거나, 문제가 있으면 "아니오"로 응답한다.
  - 2단계(커밋/중단) : 모든 참여자가 "예"로 응답하면 코디네이터는 커밋 결정을 내리고 모든 참여자에게 커밋 명령을 보낸다. 하나라도 "아니오"거나 응답이 없으면 중단(abort) 명령을 보낸다. 참여자는 1단계에서 "예"라고 응답한 이상, 2단계에서 받는 명령(커밋/중단)을 반드시 따라야 한다.
- 2PC의 핵심 보장과 한계
  - 1단계에서 "예"라고 응답한 참여자는 그 이후에는 스스로 결정을 바꿀 수 없다(돌아올 수 없는 지점, Point of No Return). 코디네이터의 최종 결정만을 기다려야 한다.
  - 코디네이터 장애가 가장 큰 문제다. 모든 참여자가 "예"로 응답한 뒤 코디네이터가 커밋 결정을 기록하기 전에 죽으면, 참여자들은 커밋도 중단도 못하고 코디네이터가 복구될 때까지 무기한 락을 쥔 채 대기(Blocking)해야 한다.
  - 이 문제를 완화하기 위해 코디네이터는 결정을 반드시 디스크(트랜잭션 로그)에 기록해, 자신이 복구된 뒤 그 로그를 읽어 참여자들에게 최종 결정을 다시 전달할 수 있어야 한다.
  - 참여자가 "예"로 응답한 이후 락을 쥔 채로 응답을 기다리는 동안 다른 트랜잭션들이 블로킹되어, 시스템 전체의 처리량과 지연시간에 부정적인 영향을 줄 수 있다.
- 실무에서의 대안
  - 2PC의 블로킹 문제와 코디네이터 단일 장애점 문제 때문에, 분산 트랜잭션보다는 비동기 메시징과 보상 트랜잭션을 활용한 SAGA 패턴, 또는 하나의 메시지 큐 트랜잭션에 DB 변경을 함께 묶는 트랜잭셔널 아웃박스 패턴(앞으로 정리할 항목 참고)을 선호하는 경향이 있다.

## 이중 쓰기(Dual Write) 문제와 CDC(Change Data Capture)
- 이중 쓰기(Dual Write) 문제란?
  - 하나의 데이터 변경을 서로 다른 두 시스템(예: DB와 캐시, DB와 검색 엔진, DB와 메시지 큐)에 각각 따로 써야 할 때 발생하는 정합성 문제이다. (예: `DB에 저장` → `캐시 갱신` 또는 `메시지 큐에 이벤트 발행`)
  - 두 번의 쓰기 사이에 애플리케이션이 죽거나 네트워크 장애가 발생하면, 한쪽에는 반영되고 다른 쪽에는 반영되지 않는 상태가 될 수 있다. 쓰기 순서를 바꾸거나 재시도 로직을 추가해도, 두 시스템에 걸친 쓰기를 원자적으로 만들 수 없다는 근본적인 한계는 해결되지 않는다.
  - 2단계 커밋(2PC)으로 이 문제를 해결할 수도 있지만, 앞서 정리했듯 코디네이터 장애 시 블로킹 문제와 운영 복잡도 때문에 실무에서는 잘 쓰이지 않는다.
- CDC(Change Data Capture)
  - 애플리케이션이 직접 두 시스템에 쓰는 대신, 하나의 원천 데이터베이스(Source of Truth)에만 쓰고, 그 DB에 반영된 변경 사항을 비동기로 감지해 다른 시스템들에 전파하는 방식이다.
  - DB가 이미 내부적으로 기록하는 복제 로그(앞서 정리한 `복제 로그 구현 방식`의 논리적 로그, 예: MySQL의 binlog, PostgreSQL의 논리적 디코딩)를 읽어들여, 그 변경 내용을 Kafka와 같은 메시지 큐로 흘려보내는 방식이 대표적이다. (Debezium 등의 도구가 이 역할을 한다.)
  - 애플리케이션은 DB 하나에만 쓰기 때문에 이중 쓰기 문제가 사라지고, DB에 실제로 커밋된 변경만이 하류 시스템(캐시, 검색 엔진, 데이터 웨어하우스 등)에 전파되므로 "DB에는 반영됐지만 캐시에는 반영 안 됨"과 같은 불일치가 발생하지 않는다.
  - 다만 CDC는 비동기이므로, 하류 시스템에 변경이 반영되기까지는 약간의 지연(최종적 일관성)이 있을 수 있다는 트레이드오프가 있다.
- 트랜잭셔널 아웃박스 패턴(Transactional Outbox)과의 관계
  - CDC와 유사한 목적을 위해, DB에 트랜잭션을 커밋할 때 변경 사항을 같은 트랜잭션 내의 아웃박스 테이블에도 함께 기록하고, 별도의 프로세스가 그 아웃박스 테이블을 읽어 메시지 큐로 전달하는 방식도 널리 사용된다. (별도 항목으로 정리 예정)
